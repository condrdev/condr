# Agent Support Is Official, in Two Levels, One Spec per Agent

Condr supports the agent CLIs it ships an integration for, and no others. A person cannot declare an agent CLI of their own, in configuration or through a plugin; a CLI Condr does not support arrives through an Issue or a pull request that adds it. Each supported agent is either fully supported or recognized only, and everything Condr knows about one agent lives in one module of `condr-core`.

The roadmap had planned Agent Profiles, a declarative entry naming a CLI's executable, its launch and resume arguments and its icon. They are declined for three reasons. The set of agent CLIs changes slowly, and the common ones fit in Condr itself. What makes an agent worth recognizing is its state, which comes only from its hooks (ADR 0014), and every integration so far has needed what a declaration cannot carry: a format to write the CLI's hook configuration in, native events renamed or dropped (Claude's `AskUserQuestion`, Copilot's `initialPrompt`, Antigravity's `fullyIdle`), a rule for the shell that runs the hook command on Windows, and a real session to find where the CLI's documentation is wrong. A declared agent would be recognized and resumed, with either no state or a state nobody verified. Other tools that allow one show the same split, as surveyed on 2026-10-06: a custom agent in Superset or a Terminal profile in Paseo launches with its icon but reports no state unless it wraps a built-in CLI; cmux's `vault.agents` recognizes and resumes one without a lifecycle state; Herdr lets a hook report an agent it does not know, but neither recognizes its process nor launches it. Orca, Emdash and Vibe Kanban refuse unknown agents, and T3 Code, Paseo's chat agents and Zed accept them only over ACP, which Condr does not speak (ADR 0014). Finally, an open set would change the wire: `AgentKind` would become a string, and every Server, hook process and remote GUI would need a way to find the declarations. A closed set keeps `AgentKind` a protocol enum, and a new agent is a new value, which ADR 0028 already lets an older peer read as `OTHER`.

A fully supported agent's hooks report a turn starting and the main agent's turn ending, told apart from a subagent's, so its `Working` and `Idle` can be trusted. An agent with no event for a permission prompt or a question is still fully supported, as Cursor and Antigravity are; its note, reported by `condr agent hooks`, says it never shows `Blocked`. The level says what an agent's hooks can report, not how far its integration has been tried. Which agents have run a real session through the whole chain, from the CLI's hook through `condr agent-hook` and OSC 777 to the Server's state, and on which platforms, is recorded in `docs/research/additional-agent-hooks.md`; a gap there is a known limitation to close, not a reason to change an agent's level.

A recognized-only agent is named by the process table: its mark shows in the sidebar, it clears when its process exits, and `agent start` launches it. Its hooks are not installed, because they cannot report a state worth trusting, so it stays `Unknown`, and without a session ID from a hook it is not resumed after a Server restart. Kimi is the first: ADR 0014 explains why its hooks cannot tell its subagents' Stop from its own. The level follows from the spec, an agent with no hook integration being recognized only, so there is no separate flag. Settings → Server → Agents shows `Recognition only` where it showed `Unavailable`, and `condr agent hooks` gives the reason; the wire's `HOOKS_STATE_UNSUPPORTED` keeps its number and name. The documentation lists the two levels apart, and the sidebar shows a recognized-only agent's mark without a state. `agent wait` and `agent prompt --wait` refuse a recognized-only agent at once with `agent_reports_no_state` rather than waiting out their timeout. `agent prompt` without `--wait` already delivers to it, as to any agent that reports nothing before its first turn, and `agent start` already returns once the process is identified.

Each agent has a module, `condr-core/src/agent/<id>.rs`, holding one `AgentSpec`: its id, display name, mark and brand colour; the executable Condr looks for on PATH, the other process names it goes by and the npm packages its entry point lives under; the resume arguments around the session ID; whether its hooks report before the first turn; and its hook integration, or none. The hook integration names a format, the configuration directory and the environment variable that moves it, the file, the table mapping native events to Condr's, and the note `condr agent hooks` reports. No field has a default. Today `reports_at_startup()` answers yes for every agent it does not list, so an agent added without a thought for it would make `agent start` wait until its timeout for a SessionStart that never comes; with a spec, an agent that does not say does not compile.

The formats are code shared by the agents that use them: a nested JSON hook map merged beside the person's own entries (Claude's `settings.json`, Codex's `hooks.json`, Grok's `hooks/condr.json`); the same map as a plugin Condr owns, with its manifest (Antigravity); a flat list of command entries under a version field (Cursor's `hooks.json`, Copilot's `hooks/condr.json` as `exec` and `args`); and a script Condr owns (OpenCode's TUI plugin, registered in `tui.json`, and Pi's and Oh My Pi's extensions). What a single agent alone needs stays in its module, as a field where a value says it (the tool that asks a question, `AskUserQuestion` for Claude) and as a function where it takes logic (enabling Codex's hooks feature, Copilot's `initialPrompt`, Antigravity's `fullyIdle` and the `{}` it requires on stdout).

`AgentKind` remains the identity, in the protocol and the Session Snapshot alike, and `AgentKind::spec()` is the one `match` on it. The GUI draws every mark through one icon variant that takes its file from the spec. Adding an agent is then a module, a value in `AgentKind` and in the proto enum (the compiler names each `match` that misses it), its mark under `assets/agents/` with its NOTICE line and the GUI's asset table, and the documentation. A page under `docs/agents/` will say so, with the two levels, and an Issue template asks whoever requests an agent for its hook documentation and event list.

Two other structures were declined. A trait implemented per agent lets each hide arbitrary code behind default methods, and a default is how `reports_at_startup()` went wrong. Keeping `AgentKind` with its `match`es and only splitting the files by agent leaves each `match` where it is, so adding an agent still touches every one.

Not in this decision: which agents join next, which a survey of the CLIs other tools support informs but each addition decides; a launch menu in the GUI, which the roadmap's Agent Profiles assumed and which does not exist; and writing hooks for CLIs that share Claude's format from a declaration, which the shared nested-map format makes cheap for a new official agent without exposing it to people.

ADR 0014 stands. Its Kimi paragraph describes the first recognized-only agent, and what the GUI showed as unavailable it now shows as `Recognition only`.

Tests: before the move, a snapshot of every file each agent's installation writes, byte for byte, which must not change, because Settings reports `Installed` only for exactly what this `condr` would write and any drift would show every existing installation as `Outdated`; the spec table covering `AgentKind::ALL`; `agent wait` and `agent prompt --wait` refusing Kimi without waiting.
