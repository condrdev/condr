# The Android Companion Draws the Grid Itself and Takes Material 3 Expressive from Its Beta

Status: accepted 2026-10-22. Settles what ADR 0039 left to Android's start and what the roadmap deferred to it, the terminal's rendering first among them. Android keeps API 29 as its floor (ADR 0042) and targets API 36.

The Android app has the iOS app's feature set, which ADR 0040, ADR 0041 and ADR 0047 decide once for both phones, drawn in Android's own vocabulary: Jetpack Compose with Material 3, the system's dynamic colour, a navigation bar with the three screens (Agents, Devices, Settings), Material dialogs for renaming and forgetting a Device, the biometric prompt for the lock, Navigation 3 for the back stack, and the Google code scanner for the Invite. The two apps share one Rust library and differ only in how they look; a person who knows one should find the other native, not familiar. The app is phone-only, one layout in either orientation, as the iOS app is iPhone-only.

The terminal is drawn by the app itself, from the cells `condr-mobile` hands it, with Android's `Canvas` and one `Paint` per run of one style: no terminal emulator library. The Server owns the VT, and the library delivers a finished screen, every cell with its colours, attributes and link, the Pane's selection already in its colours and the cursor placed, so what a phone needs is a renderer for a grid, and every candidate library bundles its renderer with an emulator. Taking one means encoding the cells back into escape sequences, as the iOS app does to feed SwiftTerm (`ScreenEncoder`), parsing them a second time on the phone, and then suppressing the library's own selection, gestures and keyboard so that the Pane's one selection and the library's touch mapping (ADR 0041) win. Termux's `terminal-view`, the mature one, is GPLv3 in the parts Termux added and cannot be linked into an Apache-2.0 app; jackpal's `emulatorview`, Apache-2.0, was archived in 2022; ConnectBot's `termlib`, Apache-2.0 over MIT libvterm and what ConnectBot ships, is the one that could be linked, but at 0.3 it documents no way to turn its selection or gestures off, keeps OSC 8 on its plan, and adds one more native library per ABI. Its rendering code is Apache-2.0 and may be read and borrowed, which Termux's may not. The renderer redraws the viewport whole on every frame; damage by row waits for a measurement. The font is JetBrains Mono, bundled as two variable files with its ligatures off so every glyph keeps to its cell; a system monospace differs by manufacturer, and the columns a Pane gets must not depend on the phone's brand. Font size, pinch and the one Resize after a size settles follow the iOS app. The key row is Material's floating toolbar with the keys ADR 0041 lists, counted as a bottom inset so it covers no row; the field with Send is a docked bar beneath it.

The app is drawn with Material 3 Expressive, which on this date exists only in Compose Material 3's 1.5.0 betas: 1.4.0, the stable line, removed every Expressive API before it shipped, and 1.5.0 stands at beta02 with stable expected around the turn of the year. Waiting was declined: before the first stable release the Android app goes out as a signed APK on GitHub Releases, not through Google Play (ADR 0041), and drawing it in 1.4.0 would mean drawing it twice. The version is pinned exactly, with the beta BOM it belongs to, and no module opts into `ExperimentalMaterial3ExpressiveApi` as a whole: a component that still carries the annotation is opted into where it is used, with the reason beside it, so the compiler lists what may still move before stable. The pin moves once, to 1.5.0 stable; a beta library does not hold the Play listing back, which waits on the first stable release as ADR 0041 says. Dynamic colour applies from Android 12; on 10 and 11 a scheme generated from a neutral seed stands in, since the brand has no hue. The Agent status colours do not follow the wallpaper, and the terminal keeps the library's dark scheme whatever the system theme.

The app has no ViewModel. The library is the state (ADR 0039): an Application-scoped `Session` answers `changed()` on the main thread with `take_changes()` and re-reads the scopes that changed into Compose state, so a recreated Activity reads what the process already holds, and the back stack is the only state saved across it. Android's guidance expects a ViewModel between data and Compose; here it would hold nothing the library does not.

Pushes reach the phone as FCM notification messages (ADR 0047), which the system displays while the app is in the background, so the app declares one notification channel at high importance and Condr Cloud names none. Android's convention is a channel per kind of notification, so that a person can silence one kind, and three kinds exist (`push_blocked`, `push_finished`, `push_failed`). One channel was chosen because every push is something the person asked to be told, there are few of them, and splitting later costs a `channel_id` in Condr Cloud's message and two more constants in the app, with the old channel carrying anything older. The permission is asked after the first pairing, when there is a Device to be told about. On a phone without Google Play services the scanner and the push are both absent: pairing offers only the pasted link, and the notification setting shows disabled with one sentence saying so.

The lock is Android's biometric prompt, accepting a weak biometric or the device credential, with the iOS app's timing (ADR 0041). The recents screen shows no snapshot of the app: on Android 13 and later through `setRecentsScreenshotEnabled(false)`, below it with the veil the iOS app draws as it leaves the screen. `FLAG_SECURE` was declined: it also stops the person's own screenshots, and terminal output is the kind of thing people screenshot.

Gradle runs the library's build before every app build (ADR 0039). The app targets API 36, which Google Play requires of new apps from 2026-08-31, keeps API 29, and links `libcondr_mobile.so` and JNA 5.17 or later, both aligned for 16 KB pages. The nightly and release pipeline builds a signed APK beside the desktop packages, with the version name the iOS app carries and the run number as the version code; the upload key is generated once and lives in the repository's secrets, to become the Play upload key when the listing exists. One APK: a build without Firebase waits for someone to ask.

Left for later, each with its trigger: damage by row in the renderer, when a measurement shows the whole-viewport redraw dropping frames under an Agent's animation; a channel per kind of push, when someone wants to silence one kind; a list-detail layout, when there are tablet users; a build without Firebase, when F-Droid or a phone without Google Play services asks for it; the Play listing, with the first stable release (ADR 0041).

Tests: on the JVM, `Session` re-reading only the scopes `take_changes()` named, and the push registration against a fake sender; on the emulator, the grid a viewport and font size give matching the size sent in `show_pane`, a wide character taking two columns with its spacer drawing nothing, and selection colours coming from the cells as sent; the demo scenes under UI tests as the iOS app has them, and a pairing flow against a real Server behind an environment variable. The `condr-mobile` tests ADR 0039 and ADR 0041 list stay as they are.
