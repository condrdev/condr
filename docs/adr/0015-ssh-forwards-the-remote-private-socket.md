# SSH Forwards the Remote Private Socket

SSH is a Client connection mode. A Client launches system OpenSSH with `-T`, runs `condr server bridge` on the remote host, and carries the existing framed protocol over stdin/stdout. The bridge connects only to that user's private local socket or named pipe. Server listeners remain Local and optional TCP, serving the same Session (ADR 0013). Condr's existing `EndpointStream` accepts SSH pipes directly, so no extra local IPC proxy or TCP forwarder is needed. This follows the transport boundary in the [Herdr SSH research](../research/herdr-ssh-v0.8.2.md), without porting its installer.

OpenSSH owns authentication, host-key verification, aliases, keys and jump hosts. The GUI uses batch authentication with keys or ssh-agent; initial trust and interactive login setup happen in the user's terminal. Condr clears inherited port forwards (`ClearAllForwardings=yes`) and overrides `RemoteCommand`, `SessionType`, `StdinNull` and `ForkAfterAuthentication` so the foreground bridge owns stdin/stdout. Host/User/Port, identity files and ProxyJump still come from SSH config unless the URI supplies the address. SSH grants the remote login user's existing local Server permissions. Noise pairing, `authorized-clients` and TCP revocation (ADR 0011) do not apply to SSH; SSH access is managed through the host's SSH account and keys. No extra plaintext TCP listener is introduced.

Add Server identifies the connection by its scheme: `tcp://<server key>[.<invite>]@host:port` or `ssh://[user@]host[:port][?bin=/absolute/path]`. SSH `bin` is a percent-encoded executable path, quoted as one POSIX shell word in the remote command. With no `bin`, the remote noninteractive PATH must contain `condr`. Saved Client entries contain name and address; TCP addresses retain only the public key, never the invite. No migration of the old development config format is provided. If the saved Server list cannot be loaded, adding, editing, removing and writing that list are disabled until the file is fixed and Condr restarted; unrelated preferences can still be saved without replacing Server entries.

The remote binary must already be installed and its Server already running. The bridge does not start, restart, install or update a Server. Automatic remote Server startup is deferred to the future install workflow, as recorded in the roadmap. Protocol mismatches remain errors. Disconnect ends the SSH connection and bridge while the independent Server, Session and PTYs continue; reconnect opens a new SSH process and fetches an authoritative Bootstrap. Native pipes add no visual event queue, stderr capture is bounded, and failed handshakes and explicit disconnects terminate and reap the SSH child and its owned helpers (Unix process group / Windows Job). A cancellation handle belongs to the GUI Server connection from before SSH spawn through connected I/O; it interrupts blocked writes without waiting for Detach. SSH/Welcome has a 15-second inactivity timeout; after Welcome, Bootstrap uses a 4-second inactivity timeout renewed by received bytes, with no total-transfer deadline. Diagnostic collection never waits indefinitely for a helper to close stderr.

The initial remote target is Linux/macOS with a POSIX login shell; the Client transport uses portable Rust pipes and system OpenSSH, including Windows OpenSSH. The local bridge endpoint code also uses the existing named-pipe adapter on Windows, but Windows SSH server shells and remote command quoting are outside this initial support scope.
