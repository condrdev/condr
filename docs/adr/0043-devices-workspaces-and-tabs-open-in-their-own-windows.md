# Devices, Workspaces and Tabs Open in Their Own Windows

Status: proposed 2026-10-14, planning only. Nothing here is built, and nothing here is final: the design is still under discussion, and any part of it may change or be broken before it is accepted. When accepted, it amends ADR 0020 (a third kind of page in the content area), ADR 0021 (a View also says which window shows what), ADR 0023 (the state file gains a list of windows), ADR 0036 and ADR 0041 (one Client with several windows).

A person developing with two screens has one Condr window, and every mainstream tool is a single-window application. A Device, a Workspace or a Tab can be opened in a window of its own, moved to the other screen, and brought back. This is the GUI's own affair: the protocol, the Server, the Session and the Companion do not change, and the `condr` CLI gains no surface.

## Windows

The GUI process has one main window and any number of detached windows, all in the one process, opened with `open_window` as Settings is (ADR 0038); the single-instance lock stands. A second GUI process was declined: it would be another Client to every Server, with its own subscription of every Pane's frames and its own claim on the terminals' size (ADR 0036), and it could share neither theme, update check nor state file with the first.

A window shows one scope of the Session tree: everything, which is the main window; one Device; one Workspace; or one Tab. A Tab window holds exactly one Tab and draws neither Tab strip nor sidebars; a Workspace window has the left sidebar listing only that Workspace, collapsible, and the Changes and Files sidebar as usual; a Device window is the main window's chrome filtered to one Device. The OS title and the drawn title bar read `Condr – <name>`. One window view type carries the scope as a field, so every action handler and keybinding the main window has, a detached window has too. A Pane is not a unit of its own in this version, and a Tab window cannot hold more than one Tab; both wait, below.

Detaching moves, it does not mirror. A Tab, Workspace or Device is drawn in exactly one window at a time, so a `TerminalPanel`, its focus handle and its IME composition belong to one window, and ADR 0036's single terminal size has no second window of the same Client to fight. The place it left keeps listing it, in the sidebar or the Tab strip, and selecting it there shows a page in the content area, in the family of ADR 0020's connection pages: it says the item is shown in another window and offers to go to that window or to bring it back; the Changes and Files sidebar is hidden with it. The moment something is detached, its home keeps it selected and shows that page at once, so the person sees where it went.

Bringing back is closing the detached window. It returns to the nearest ancestor that has a window: a Tab to its Workspace's window if one is open, else its Device's window, else the main window, and it becomes the shown item there. A Workspace may be detached from a Device window, and returns to it while it is open. A Tab window outlives its Workspace being detached or brought back, and a Workspace window closing brings back the Workspace and leaves the Tab windows alone. A Tab moved to another Workspace by `MoveTab` keeps its window, whose scope follows the move. A window closes itself and drops its state entry when its Tab closes, its Workspace closes, its Device is removed under Settings, or a Bootstrap no longer has its id; a Device that merely disconnects keeps its windows, which show ADR 0020's connection state. Closing the main window quits and takes every window with it, as it takes Settings today.

A new window opened from the menu appears on the display the menu was on, at the main window's size, cascaded from it, with no minimum size, as the main window has none; one opened by dragging appears with its top-left corner at the cursor. After a restart the main window opens first, then the detached windows, and the main window is activated last. Stacking order is not remembered.

## One Client, several windows

A GUI process stays one Client per Server, so the Server still has one holder of the terminals' size (ADR 0036, ADR 0041), and a `Resize` from any of this Client's windows applies while it holds the sizing. The focus the Client reports follows the window last activated: "the window is active" means any of this Client's windows is, the focused Pane is the one focused in that window, and switching windows reports `Focus(false)` for the old Pane and `Focus(true)` for the new one, as leaving and returning to the one window do today. A window in the background sends no sizes again, as ADR 0041 requires of a background window, and has nothing to send: its Panes' grids are the size it measured, since the same Client sized them. Sizes still go back and forth only against another Client, which the existing rules cover.

An `Activated` event (ADR 0021), a click on an OS notification or on the "Needs you" list, and a click in the main window on a detached Workspace's Tab or Pane all activate the window that shows the target and show it there. Keyboard navigation between Workspaces in the main window does not skip detached ones; it lands on their page, so the keys and the sidebar agree on the order. "New Tab" inside a Tab window creates the Tab in its Workspace, which shows it in the Workspace's home window without activating that window. A failed operation is still one `report_error` toast (ADR 0020), now in the window where the person acted; a failure with no window behind it, a connection result, the update check, a configuration save, goes to the main window.

## Detaching

Every unit detaches from its context menu: a Tab in the Tab strip, a Workspace row and a Device row in the sidebar, as "Open in new window". No keyboard shortcut and no CLI command: a window is this Client's own state (ADR 0021), which the CLI cannot see, and `--focus` reaching the right window is what the CLI needs.

Every unit also detaches by dragging it out of its window, with the drag sources that exist today (`DraggedTab`, `DraggedWorkspace`, `DraggedServer`). GPUI's drag is confined to a window, but on every platform the window that saw the button go down still receives the moves and the release after the pointer leaves it: Windows takes `SetCapture` on the press, AppKit sends `mouseDragged` and `mouseUp` to the view of the `mouseDown`, X11 holds an implicit grab, and Wayland compositors keep pointer focus while a button is held, which the code does not enforce. So a release outside the source window's bounds, read from a `Window::on_mouse_event::<MouseUpEvent>` listener while the GUI remembers what `on_drag_move` last carried, opens the unit's window at the cursor. GPUI exposes the dragged value only during moves, so the GUI keeps its own copy, and clears it on the next press if no release ever came, since GPUI's Windows backend does not handle `WM_CAPTURECHANGED`. Nothing is drawn outside the window while dragging: GPUI paints the drag image inside the window only, and a ghost window waits. A release over another Condr window counts as outside and opens a new window; dropping into that window's Dock would need the drop zones Kit resolves only inside its own window, and is left for later. A maximized window on one screen has no outside; the menu covers that. A Pane dragged out of its window is still a cancelled drag, as today. The gesture is accepted on Windows, verified by hand on macOS, and not promised on Linux, where development is headless.

GPUI's cross-window drag, `external_drag_payload`, was declined for this: it carries file paths only and is implemented for macOS and Wayland, not Windows.

## State

The state file (ADR 0023) keeps the main window as it does and gains the list of detached windows, each with its scope, bounds and display. A scope names its Device by `ServerId` and its Workspace or Tab by the ids the Snapshot persists, never by `ConnectionKey`, which is numbered by load order. A detached window restored before its Server bootstraps shows the Device's connection state until then.

## What this means for the GUI

`Condr` is today both the application and its window. It splits into an application-level entity, which owns the connections and their `SessionModel`s, the `TerminalPanel`s, pending sizes and geometry, fonts and theme, the update check, Settings and the state file, and a window view with a scope, which owns the focus handle, sidebar widths, the Files view, the directory browser, drop targets, Tab-strip scroll and the window subscriptions. Dock surfaces stay keyed by Tab and are rendered by whichever window shows the Tab; Kit's `DockArea` keeps no window handle, and its subscriptions follow the window that last rendered it, but a surface that changes window is rebuilt through `rebuild_dock`, since an event between the move and the first frame would still reach the old window.

CONTEXT.md gains two entries when this is accepted: Main window, the one window that is the application, whose closing quits; and Detached window, a window showing one Device, Workspace or Tab moved out of its place, which closing brings back. "Open in new window" and "Bring back" are the interface's words; float and pop-out are avoided.

## Delivery

In order, each its own change: this ADR; splitting `Condr` with the main window as the one window and no change in behaviour, carried by the existing tests; the menu, the page, the routing and the one-Client rules; the state file; the drag. Tests from the third change on open two windows (`add_window_view`, `VisualTestContext::from_window`, `activate_window` then `run_until_parked`): a detached Tab appearing in the new window and its page in the old; closing bringing it back; `Activated` activating the right window; the `Focus(false)`/`Focus(true)` order when windows switch; the state file round-tripping its windows. Acceptance on Windows with two screens: one window on each, Codex animating in both, at a usable frame rate and with no size going back and forth.

Left for later, each with its trigger: a Pane detached into a window, which would move it into a new Tab on the Server first, when people ask for one Pane on the other screen; a Tab window that holds several Tabs, when dropping into another window exists; dropping into another window's Dock; a ghost window while dragging outside; a Window menu on macOS, which GPUI does not provide (`SystemMenuType` has only Services).
