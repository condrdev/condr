# The Handshake Carries Build Identity

Every connection opens with a `Hello` and is answered by exactly one `Welcome`, and from this decision on those two frames never change. Both carry the protocol number and the binary's build identity, `<crate version>[+<12-character commit>]`, so any two builds of Condr, released or nightly, can finish the exchange and say in words how they relate. A different protocol is a refusal the person can read; a different build under the same protocol is a mark to look at, not a reason to stop.

The frames live in `protocol::handshake`, apart from `ClientMessage` and `ServerMessage`. (ADR 0028 moved them to protobuf, froze field numbers instead of bytes and replaced the equality below with a protocol range; the rest stands.) bincode is positional: a field added, moved or removed shifts every byte after it, and an enum's variant index shifts with the variants before it. While `Hello` was variant zero of `ClientMessage`, any reordering of the big enum would have broken the one frame that has to be readable by every version. As their own types, `ClientHandshake { Hello, Credential, Tunnel }` and `Welcome { protocol, build, server_id, session_id, refusal }` are frozen by construction, and a wire snapshot test in `condr-core` pins their bytes. `Welcome` lost `runtime_epoch`, which no Client read (the Bootstrap header carries it), and kept `session_id`, which is always `1` because one Server serves one Session (ADR 0013); the Session-addressed messages after the handshake need it from somewhere, and a fixed field is cheaper than a second source of truth. `Refusal` is the one part that may grow, by appending variants: `IncompatibleProtocol`, `NotAuthorized`, `PairingFailed`, `DeviceRevoked`, `Malformed`, `TunnelFailed`. Every way a Server closes a handshake is one of them, sent inside `Welcome`; nothing during the handshake is free text a Client has to match on. The Client turns a refusal into an `io::Error` wrapping `Refused`, which carries the Server's protocol and build, and callers classify by type: the CLI answers `protocol_mismatch` and `not_authorized`, the GUI keys its advice on the variant.

The build identity is `condr_core::build_identity()`: the workspace version, plus the commit `build.yml` passes as `CONDR_BUILD_COMMIT` when CI built it. A local `cargo build` has no commit and reports the bare version. `condr --version`, `condr-gui --version`, the Server's start log, `Status` and `condr server install --json` all report the same string, and the package checks run `condr --version` against `BUILD-COMMIT` so a build that lost its identity cannot ship. `--version` alone adds `(nightly)` after a nightly's identity (`CONDR_RELEASE=0`), so a person can tell the channel; it is not part of the identity, since a semver pre-release such as `0.1.1-nightly` would sort before the `0.1.1` release it follows. Two identities compare in three steps: protocol number, then version as three integers, then the whole string. A different protocol refuses. A different version names the older side, so the message says which Device to update. Same version and a different commit are two nightlies, or a release beside a dev build; commits have no order, so the message says only that they differ and to update both to the same version. Any difference at all is shown, patch releases included: the protocol number is the only compatibility Condr promises, and a build that differs is another program until proven otherwise.

The GUI keeps the Server's build on the connection. When it differs from the window's own, the Device's heading in the sidebar carries a warning mark whose tooltip has both identities and the sentence above; a click puts it away for as long as that Server keeps that build. Nothing is stored, and no page is blocked: the Session is as usable as before and the local Device gets no special treatment, since its Server is normally the same build and a mark there means the window was updated while the old Server kept running. A protocol refusal shows on the Device's disconnected page (ADR 0020) with advice that says retrying does not help, and the automatic reconnect keeps its cadence, so a Device updated on the other side comes back on its own. The CLI says nothing about a build difference; its output is read by programs. The Server logs a build difference once per connection at `info`.

Not decided here: no check against published releases, so Condr makes no network request to learn whether something newer exists (ADR 0029 later added one, in the GUI only); no compatibility layer for old wire formats, since before the first release `PROTOCOL_VERSION` stays `1` and afterwards every change to a message after `Welcome`, a field added or an enum reordered, bumps it. A CI guard that pins the post-handshake message bytes to the protocol number is worth adding at the first release, not now while the protocol changes weekly; the roadmap's release gate lists it. `condr server install` still does not judge whether a running Server is stale (ADR 0016), though it now could; a person who has just updated is told by the GUI's mark.

Tests: the wire snapshot of `Hello` and `Welcome`; the three-step comparison; a refused protocol arriving as `Refusal::IncompatibleProtocol` over a socket and over the SSH bridge; the Server reporting its identity in `Welcome`, `Status` and `install --json`; the package checks comparing `condr --version` to `BUILD-COMMIT`.
