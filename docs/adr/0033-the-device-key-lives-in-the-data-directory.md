# The Device Key Lives in the Data Directory

`device-key`, `authorized-clients` and `pending-invite` live in the platform data directory, with `identity.lock` beside them: `~/.local/share/condr` on Linux (`XDG_DATA_HOME`), `%LOCALAPPDATA%\condr` on Windows and `~/Library/Application Support/condr` on macOS. `CONDR_DATA_DIR` overrides it, as `CONDR_CONFIG_DIR` overrides the configuration directory. `config.toml` stays in the configuration directory, alone. On macOS the two directories are one, so nothing there moves.

Releases up to 0.1.6 kept the identity files beside `config.toml` (ADR 0011, ADR 0025). That put a private key into the two places a person deliberately copies around. `~/.config` is what dotfiles tools track, and someone who adds `~/.config/condr` to sync `config.toml` publishes the key with it; GitHub CLI's token in `~/.config/gh/hosts.yml` is the same problem, and dotfiles repositories exclude that file by hand. On Windows the configuration directory is Roaming AppData, which a roaming profile copies to every machine the person signs in to, so two machines end up with one key and the relay serves whichever bound its endpoint last (ADR 0025). XDG draws the same line: configuration is what the person edits, data is what the program owns for this machine. Nothing in `config.toml` is secret: appearance, editors, and `tcp://<id>@host:port` addresses whose `<id>` is a public key.

The move is a rename, not a new key. 0.1.x runs on machines that are paired with each other, and a new key would void every pairing and every saved address for no gain. So the first process that asks for the identity directory after the update, Server, GUI or CLI, moves the three files from beside `config.toml` under the store lock, `device-key` last so that a process which sees the key also sees the list, and leaves `config.toml` where it is. A machine that already has a key in the data directory keeps it and ignores whatever is left in the old place. On one volume this is a rename; across volumes a copy and a delete. A key kept somewhere private through `CONDR_CONFIG_DIR` moves too, since that is where the previous release looked; `CONDR_DATA_DIR` is the override for the new location.

The directory decides where the file lives, not who may read it. Any process of the same user still reads the key, on every platform; that is the threat model of `~/.ssh` as well, and an OS keychain stays deferred (ADR 0011). On Windows a file used to carry only the ACL it inherited from its directory, and a tool that widens the profile's ACL (a sandbox user group, for example) widened the key's too; `AppData\Local` inherits the same entries as `Roaming`, so the directory is no answer there. `device-key` and `pending-invite` are therefore created with the local endpoint's protected DACL, generic all for the owner and LocalSystem and nothing inherited, set at creation so no handle can be opened before it applies; a file from an older release gets the same DACL the first time it is read, which repairs every updated machine rather than refusing it, as the Unix mode check does for a file the person made world-readable by hand.

Both accommodations are transitional and marked `compat(0.1.6)` in `crates/condr-server/src/noise/identity.rs`, its tests and the `Win32_Security_Authorization` feature in `crates/condr-server/Cargo.toml`: the move from beside `config.toml`, and the DACL repair on read. Once 0.1.6 installs no longer update in place, the first minor release after this is a fair point, delete them, which leaves `identity_directory()` a plain lookup and `read_secret_file` without a Windows branch, and drop the sentences in the configuration and security pages that describe them. A person updating across that boundary pairs again, as ADR 0025 already asks of anyone holding an older key.

> ADR 0040: a Companion keeps its key in the iOS Keychain, or encrypted under an Android Keystore key, and hands it to the library; no data directory is involved.
