# Blocked Says What It Waits For

A `Blocked` Agent carries a short description of what it is waiting for: the tool it wants permission to run, or the question it asked. The hook that already reports the state (ADR 0014) takes that description from the native payload it reads anyway, the OSC 777 event carries it, the Server keeps it on the `AgentSnapshot`, and every surface that shows `Blocked` shows it too: the sidebar row, the OS notification, and the `condr agent`/`pane` JSON. On top of that the GUI gets one list of every Agent that needs the user, across Workspaces and Devices, where a click lands in the Pane.

Today the sidebar shows a dot and the OS shows "Claude needs your input"; the user has to switch to the Pane to learn whether it is a `rm -rf` waiting for approval or a multiple-choice question. That is exactly the information the hooks have and screen classification never had: Claude Code's `PermissionRequest` and `Notification(permission_prompt)` name the tool, `AskUserQuestion` carries the question text, Codex's `PermissionRequest` names the tool, OpenCode's TUI state holds the pending permission and question objects, Pi and OMP report `toolName` on `tool_approval_requested` and a `title` on `ui_prompt_start`. `condr agent-hook` parses `tool_name` from stdin already, to tell a question tool from an ordinary one, and throws it away.

`AgentEvent` gains `detail: Option<String>`, present only on `permission-request` and `question-asked`; the hook never attaches it to other events. The hook builds it from the native JSON in a fixed order: the question text when the event is a question, else the tool name, and for a shell tool the first line of the command after it, so `Bash: cargo test` reads better than `Bash`. Where the native event only has a notification message, the message is the detail. The value is bounded before it is encoded: control characters removed, whitespace collapsed, cut at 200 characters with an ellipsis, so it fits the PTY scanner's OSC size cap beside a 256-byte session ID and never carries a newline into the grid. The exact native fields per agent belong in [additional-agent-hooks.md](../research/additional-agent-hooks.md) next to the events they come from; the OpenCode plugin and the Pi/OMP extension pass the same `detail` field through their stdin JSON, so the Rust side has one place that bounds it. Anything the hook cannot find leaves `detail` absent, and a `Blocked` without detail is still `Blocked`; nothing reads the screen to fill the gap.

`AgentSnapshot` gains `blocked_on: Option<String>`. The Server sets it from the event that produced `Blocked` and clears it on every transition away from `Blocked`, including a second `Blocked` event without detail. `apply_agent_refresh` already publishes `AgentChanged` whenever the snapshot differs, so a new question in an already blocked Agent reaches clients without a new event kind, and the Bootstrap carries it in `PaneAgentSnapshot` like the rest of the snapshot. The Snapshot on disk (ADR 0005) keeps only kind and session ID as before; a restart resumes the conversation and the agent reports again. `PROTOCOL_VERSION` stays `1`; the project is unreleased and keeps no wire compatibility.

The GUI shows `blocked_on` as the Agent row's second line in the sidebar, the way a repository Workspace shows its branch, so the row grows only while something blocks. The OS notification keeps its title, `<agent> needs your input`, and puts the detail first in the body ahead of the Workspace and terminal title, since the body is what the user reads to decide whether to come now. A new `AgentChanged` that only changes `blocked_on` replaces the earlier toast through the existing per-Pane tag and does not ask for window attention again. The CLI exposes it as `blocked_on` (string or null) in `agent list`, `agent wait`, `agent prompt --wait` and `pane list`, so an orchestrating agent that gets `blocked` back knows whether to answer a question or approve a tool before it reads the Pane; the embedded Skill says so.

The "needs you" list is a GUI view over state the client already holds, not a Server feature. It sits at the top of the left sidebar, above the Workspaces, and lists every Agent whose display state is `Blocked` on every connected Device: the Agent mark, the Workspace name with the Device name when more than one Device is connected, and `blocked_on`. Clicking a row runs the same `select_pane` the notification click runs, activating the connection, Workspace, Tab and Pane. The section is absent when the list is empty; it does not collapse and has no settings. `Done` stays where it is, on the Workspace row, because a finished Agent does not need the user.

Not in scope: answering for the user. No approve or deny goes over the wire, no keystroke is synthesized into the Pane by the list, and Condr installs no `PermissionRequest` decision hook; that waits for an interface the vendors expose for it. No screen text is parsed to supply a missing detail, and Agents whose hooks give no waiting event (Cursor, Antigravity permissions) stay as ADR 0014 documents them. No history of past requests is kept; `blocked_on` describes the present.

Tests cover the hook's extraction and bounding from recorded native payloads, the OSC round trip with and without `detail`, the Server clearing `blocked_on` on the way out of `Blocked` and publishing when only the detail changes, the CLI JSON field, the OpenCode and Pi/OMP plugin harnesses carrying `detail`, and a GUI visual test where a blocked Agent appears under "Needs you" ahead of the Devices, a click on its row selects the Pane, and Working removes it.
