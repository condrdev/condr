# The Companion Binds Its Own iroh Endpoint

Status: accepted 2026-10-10. Amends ADR 0025's "the Server is its machine's only iroh endpoint" and ADR 0033's place for the Device key, for a phone; adds a reachable host to the TCP Invite the GUI shows.

The Companion is a Device without a Server. It has one key like every Device, is paired through an Invite, is listed in each Server's `authorized-clients` under a name the person gives it, and reaches Servers over `p2p://` and `tcp://`. With no local Server to send `Tunnel` to, the app binds its own iroh endpoint, through `condr-client`'s `P2pNode` (ADR 0039), and dials each Server directly. It connects only while it is in the foreground. Its key is kept by the platform's secure storage and handed to the library by the app; there is no data directory on a phone.

ADR 0025 routes a desktop's Peer-to-peer connections through its Server because a key may live in only one iroh endpoint at a time: a second endpoint with the same id takes the relay route and the first silently receives nothing more. The rule it protects is one endpoint per key, and on a phone the app is that one endpoint. The Notification Service Extension that the push work adds later reads the key to decrypt a notification and never binds an endpoint, since binding one would take the route from the app whenever both run. The phone's endpoint only dials, like a desktop Server's with `[server.p2p] enabled` off: it accepts nothing and publishes no address, and it is bound only while at least one `p2p://` Device is paired or being paired, so a person with only `tcp://` Devices gets no UDP socket and no relay connection. A desktop machine still has its Server as its only endpoint; nothing about `Tunnel` changes.

Pairing needs nothing new on the wire. Settings shows the Invite (ADR 0038) as a QR code as well as text, and the Companion scans it: `p2p://<id>.<invite>`, or `tcp://<id>.<invite>@host:port`. The Server's `Invite` answer carries the TCP form with a literal `<host>`, because a Server listening on `0.0.0.0` or behind NAT cannot know which of its addresses another device reaches; today the GUI tells the person to replace it before pasting. Before it draws a TCP code, the GUI asks for that host instead, listing this machine's local network addresses and accepting any name or address typed, so the code holds an address the phone can dial; a `p2p://` code needs none. Over Peer-to-peer the app sends `Credential { invite }` before `Hello`, the frame a desktop Server sends today when it dials for a tunnelled pairing; over TCP the invite is the Noise pre-shared key (ADR 0011). A Server reached Peer-to-peer must have `[server.p2p] enabled`, and when the dial finds no endpoint for the id, the pairing screen says to turn it on. `Hello.client_name` is what a Server records as the paired Device's name; the GUI sends its host name there. The Companion sends a name the person types while pairing, filled in with the device model, "iPhone 17 Pro" say, because since iOS 16 `UIDevice.name` returns only the model unless Apple grants the user-assigned device name entitlement, per App ID, through a request form with screenshots. If that entitlement is granted later, the name the person gave the phone becomes the default in that field and nothing else changes. The app, not the library, keeps its list of paired Devices, each an address without its invite and the name the Server goes by, in its own storage beside the key, and hands the list to the library at every start, as it does the key; the invite, as on the desktop, is never stored.

The Companion holds connections only while it is in the foreground. When it goes to the background it calls the library's `suspend()`, which cancels any dial still in progress, then closes every connection and the iroh endpoint without waiting for the other side to acknowledge, since iOS allows only a few seconds after the app leaves the screen; the iOS app runs it inside `beginBackgroundTask`. A Server sees the connection end at once, and with it the phone's focus and terminal sizing (ADR 0036), rather than after the 30-second read timeout. iOS reclaims a suspended app's sockets anyway, and Android may cut a background app's network at any time. `resume()` waits for a `suspend()` still running, binds the endpoint again when it is needed, reconnects every paired Device and fetches a new Bootstrap from each, the path every Client already takes after a reconnect. Each platform feeds its own network monitor, `NWPathMonitor` on iOS and `ConnectivityManager`'s callback on Android, into the library's `network_changed()`, which calls iroh's `Endpoint::network_change()` and checks its TCP connections; iroh has no route monitor of its own on Android. No Android foreground service keeps a connection alive: Android 15 caps the `dataSync` type at six hours a day, iOS has nothing like it, and the two apps should behave alike. In the background, notifications carry what matters, as the roadmap plans.

Each platform needs a few things for iroh. On Android the library installs iroh's JNI context before it creates the endpoint; without it iroh falls back to a public DNS resolver, or panics under `panic = "abort"`. On iOS the app links `Network.framework` and `SystemConfiguration`. iroh (n0-computer/iroh#3474) and a `tcp://` address on the local network both trigger iOS's Local Network privacy prompt. The pairing flow therefore shows one screen first, explaining that on the same Wi-Fi the phone connects to the computer directly, faster and without the relay, and only then lets the prompt appear; a person who declines still connects over the relay or a public address, but not to a `tcp://` address on the local network. The prompt cannot be asked twice, which is why it gets an explanation instead of appearing on the first dial. Condr builds iroh with `default-features = false` (ADR 0026), so `fast-apple-datapath`, the default feature that calls Apple's private `sendmsg_x` and `recvmsg_x`, is off.

The key is the same kind of key: an Ed25519 seed, from which iroh's identity and the Noise key are derived (ADR 0025). Neither platform's hardware key store can hold it in a usable form. The Secure Enclave supports only P-256, and an Android Keystore key never leaves the Keystore, while iroh and Noise both need the seed's bytes. So the seed itself is stored, under the platform's protection. On iOS it is a Keychain item in a keychain access group the app will share with its extension, with `kSecAttrAccessibleAfterFirstUnlockThisDeviceOnly`: readable while the phone is locked once it has been unlocked since boot, so the extension can decrypt a notification on a locked phone, and never restored to another phone, since an encrypted backup holds it only for the device it came from. On Android an AES-GCM key generated in the Keystore, which cannot be exported, encrypts the seed, and the ciphertext lives in the app's no-backup directory. The library generates the seed and returns it once; the app stores it, and passes it in at every start; the library keeps it in memory only and never touches a file for identity. The threat model is ADR 0033's with the boundary moved: there, any process of the same user reads the key; here, only the app and its extension do. A new phone is a new Device and pairs again, and so does a phone restored without its Keychain item. The desktop's OS keychain stays deferred (ADR 0011).

A lost phone has to be revoked on every Device it was paired with. Each Server keeps its own `authorized-clients`, and no Server speaks for another (ADR 0013, ADR 0022), so revoking it under one Device's Paired devices (ADR 0038) ends it on that Device only, and the Companion's help and the security page say so. A key copied off the phone could also have done what any paired Device may over TCP and Peer-to-peer, including creating an Invite and pairing another machine, so after revoking the phone the person checks each Device's Paired devices for one they do not know. A revoked Companion is refused when it reconnects, with `NotAuthorized` once it is gone from the list, or `DeviceRevoked` if the revocation lands while it connects, and over TCP the handshake may fail before either; the app treats all of these as "pair again".

The Companion appears in a desktop's Paired devices and nowhere else, since it runs no Server to connect to. It is never a local connection, so the commands ADR 0013 and ADR 0038 keep to local connections are refused to it as to any remote Device. `ssh://` is not supported; it would need an SSH client inside the app.

One point is left to the push ADR, with a note. The roadmap encrypts the notification's text to the phone's key. The end-to-end encrypted messengers studied (Signal, Element X, Delta Chat) do the opposite: they send a notification with no content, and the extension fetches the message itself. The Companion's extension cannot fetch, because it must not bind an endpoint, so encrypting the payload stays the plan. Whether the extension does that in Rust, and so whether ADR 0039's static iOS library becomes a shared framework, is that ADR's to decide.

Tests: a `condr-client` endpoint pairing with a Server over loopback with `RelayMode::Disabled` by sending `Credential` before `Hello`, recorded under the name it sent, then refused after revocation; a phone endpoint that publishes nothing and refuses an incoming connection; `suspend()` during a dial, and `suspend()` followed at once by `resume()`, against an in-process Server, ending with the Server's sizing released and a fresh Bootstrap; a key handed in as bytes producing the same fingerprint as `DeviceKey::from_seed` does on the desktop; the GUI's TCP code carrying the host the person chose and no `<host>`. Manual on devices: the Local Network prompt and pairing with it declined, pairing by a TCP code with a wildcard listen address, switching between Wi-Fi and cellular, and the share of connections that fall back to the relay on cellular, the roadmap's risks to measure.
