# Logging Uses `tracing`, Written Off the Hot Path

Condr has had no logging. The Server prints 57 `eprintln!` lines with a `condr-server: ` prefix and no timestamp, level or origin; the detached Server's stderr is redirected by the process that spawned it into `<log dir>/<endpoint stem>.log`, appended forever; the GUI, a windows-subsystem binary, prints nothing anyone can see; warnings that `alacritty_terminal`, `portable-pty` and `notify` emit through the `log` facade go to no logger at all; and a panic leaves no backtrace. Reconnect, hook pairing and PTY shutdown faults have already had to be guessed at during dogfood, and no report from another machine could be acted on. This record decides how both processes log, chosen so that logging can never cost the terminal a frame.

Both binaries use the `tracing` facade and `tracing-subscriber`, with `tracing-appender` for files. The alternative of the `log` facade with `env_logger` was measured and was cheaper: `log` is already compiled into the headless build, `env_logger` adds two crates where the `tracing` stack adds sixteen (`tracing-core`, `tracing-attributes`, `tracing-subscriber`, `tracing-log`, `tracing-appender`, the `time` family, `sharded-slab`, `thread_local`, `matchers`). `tracing` is chosen anyway for what only it gives: spans, so a Pane's or a connection's lines group under their id without every call site repeating it, and a straight path to opt-in telemetry later through OpenTelemetry layers without touching call sites. The sixteen are counted for the headless `condr` build; the GUI build already carries `tracing-subscriber` through gpui and gains eight. The surveyed projects split evenly (Alacritty, ripgrep, Zed and Helix on `log` with their own or `fern` sinks; Herdr, Codex, Lapce and COSMIC on `tracing`); there is no idiom to follow, so the decision goes by Condr's own needs. `tracing-subscriber`'s `tracing-log` feature makes `try_init` install `LogTracer`, so records from the `log`-based crates, gpui included, arrive in the same pipeline; it also pins `log::max_level()` to the filter's ceiling (`info` by default), so those crates' `debug!` and `trace!` are rejected by `log`'s own gate before any bridging, and `CONDR_LOG=alacritty_terminal=trace` raises it.

The facade `tracing` is a dependency of `condr-core`, `condr-server` and `condr-gui`; `condr-core` has no output today but its PTY and VT code will speak `tracing` directly rather than fall back to `log`. The subscriber and the appender belong only to the `condr-server` library, in a `logging` module with `init(file_stem)` and the panic hook; `condr-gui` already depends on that library for `ClientConnection` and calls the same function, so the two processes cannot drift apart in format or policy. `condr-core` keeps no I/O-side dependency. Only `condr server run` and the GUI's `main` initialize logging: CLI subcommands keep printing their headline-and-details errors for a person, and never install a subscriber.

The subscriber is `fmt` layers behind one `EnvFilter`. The file layer writes one line per event in `fmt`'s default text format: an RFC 3339 UTC timestamp, level, span fields, target and message, ANSI off. A stderr layer always exists. When stderr is a terminal it carries everything with ANSI on, so a foreground `condr server run` on any platform, and `cargo run -p condr-gui` on Linux and macOS, show the log in the terminal; on Windows the GUI is a windows-subsystem binary with no console even under `cargo run`, and the file is the only place to read it. When stderr is not a terminal the layer passes `error` only, whatever the process: a detached Server's stderr is the file its parent redirected, so that file keeps its role as the place where fatal failures and anything that bypasses the logger (an abort, a stack overflow) land, and the start-up code that tails it when the Server does not come up keeps working; a Server run as a service or a desktop-launched GUI on Linux puts its errors in the session journal; a closed handle discards the writes. The same rule for both processes means `init` takes nothing but the file stem. That redirect file is named `<stem>.stderr`, not `<stem>.log`, because the appender prunes every `<stem>*log` in the directory as an old day's file and would delete it on the seventh day. JSON, `pretty` and `#[instrument]` are not enabled; the feature list is `fmt`, `std`, `env-filter`, `ansi`, `tracing-log`.

`CONDR_LOG` holds an `EnvFilter` directive string and replaces, rather than extends, the default `warn,condr_core=info,condr_server=info,condr_gui=info`. `RUST_LOG` is deliberately not read, so a developer's shell-wide setting for other Rust programs does not turn Condr's debug output on. Third-party crates stay at `warn` in both processes: the rendering stack's warnings are exactly what a stutter investigation wants, and a noisy target is silenced by name when it shows up.

Files go through `tracing-appender`'s rolling appender, daily, seven files kept, in the platform log directory that `condr_core::log_directory()` already defines, now overridable with `CONDR_LOG_DIR`. The Server's file stem stays the endpoint-derived one the stderr redirect uses, so helper Servers in tests do not share a file; the GUI's is `condr-gui`. Pruning is per stem, so a stem that is used once is never cleaned up: every integration test that spawns `condr server run`, directly or through the launcher, therefore sets `CONDR_LOG_DIR` to its temporary directory and reads the redirect file from there. The appender is wrapped in `non_blocking`, lossy: an event that passes the filter is formatted on the calling thread and handed to one writer thread over a bounded channel, and if the channel is full the line is dropped and counted rather than the caller waiting. The worker writes as soon as it dequeues, so what is at risk is only the in-flight tail. The `WorkerGuard` is returned from `init` and held by `main` until it returns, never in a static; its drop gives the worker a bounded moment to drain, which a normal exit and a main-thread unwind reach, while an abort, a panic on another thread that takes the process down, or a GPUI `run` that never returns (macOS terminates the app from inside it) do not. The synchronous `error` stderr layer and the accepted absence of stderr capture in the GUI already bound that loss. A size-based rotation was declined because the appender has none and a daily file with a seven-day cap already bounds disk use; a blocking `RollingFileAppender` was declined because a `write` under a mutex on a PTY or render thread is the one cost this record exists to rule out.

The performance rule, which is the substance of the decision and which review enforces: the per-chunk and per-frame paths (PTY reads, VT parsing, terminal frame preparation and publication, `prepaint` and `paint`) may carry `debug!` and `trace!` only, which a disabled level rejects at the call site for a few nanoseconds without formatting or allocating; `info!` and above appear at connection, Pane and Workspace lifecycle, Agent state changes, recovery, configuration and errors. Spans are opened in two places, one per client connection carrying its id and transport kind, one per Pane's terminal runtime carrying its `pane_id`, and nowhere else; broad `#[instrument]` was declined for its overhead on hot functions and its noise. The terminal burst benchmark that the roadmap's diagnosability direction calls for will install a counting subscriber and assert that a high-frequency output burst produces no event at `info` or above.

Both processes install one `std::panic::set_hook` from the same module. The hook logs the payload, the location and `std::backtrace::Backtrace::force_capture()` at `error`, then calls the previous hook, so the default message still reaches stderr. It shows no dialog and attempts no recovery; a GPUI main-thread panic ends the process as before, now with a backtrace on disk. `tracing-panic`, `color-eyre` and `human-panic` were not added. Nor were `thiserror` or `anyhow`: the four error types in `condr-core` are stable hand-written ones, the CLI's error codes come from protocol types, and the binaries already format failures uniformly; a future error enum with several variants and a `source()` chain may bring `thiserror` into that one crate, and `anyhow` stays out of the libraries.

Tests install no subscriber. An unsubscribed `tracing` event costs a rejected `enabled` check, and a test that wants to read log output calls `init` itself. Out of scope here and left to their own decisions: log rotation by size, redirecting the GUI's file descriptor 2 into the log so aborts are captured, structured JSON output, OpenTelemetry export, a `condr server status --json` that reports runtime health, and any collection of diagnostics from a user's machine, which the roadmap keeps opt-in and free of terminal content.
