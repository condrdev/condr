# Logging Uses `tracing`, Written Off the Hot Path

Condr has had no logging. The Server prints 57 `eprintln!` lines with a `condr-server: ` prefix and no timestamp, level or origin; the detached Server's stderr is redirected by the process that spawned it into `<log dir>/<endpoint stem>.log`, appended forever; the GUI, a windows-subsystem binary, prints nothing anyone can see; warnings that `alacritty_terminal`, `portable-pty` and `notify` emit through the `log` facade go to no logger at all; and a panic leaves no backtrace. Reconnect, hook pairing and PTY shutdown faults have already had to be guessed at during dogfood, and no report from another machine could be acted on. This record decides how both processes log, chosen so that logging can never cost the terminal a frame.

Both binaries use the `tracing` facade and `tracing-subscriber`, with `tracing-appender` for files. The alternative of the `log` facade with `env_logger` was measured and was cheaper: `log` is already compiled into the headless build, `env_logger` adds two crates where the `tracing` stack adds sixteen (`tracing-core`, `tracing-attributes`, `tracing-subscriber`, `tracing-log`, `tracing-appender`, the `time` family, `sharded-slab`, `thread_local`, `matchers`). `tracing` is chosen anyway for what only it gives: spans, so a Pane's or a connection's lines group under their id without every call site repeating it, and a straight path to opt-in telemetry later through OpenTelemetry layers without touching call sites. The surveyed projects split evenly (Alacritty, ripgrep, Zed and Helix on `log` with their own or `fern` sinks; Herdr, Codex, Lapce and COSMIC on `tracing`); there is no idiom to follow, so the decision goes by Condr's own needs. `tracing-subscriber`'s `tracing-log` feature installs `LogTracer`, so records from the `log`-based crates, gpui included, arrive in the same pipeline.

The facade `tracing` is a dependency of `condr-core`, `condr-server` and `condr-gui`; `condr-core` has no output today but its PTY and VT code will speak `tracing` directly rather than fall back to `log`. The subscriber and the appender belong only to the `condr-server` library, in a `logging` module with `init(app, file_stem)` and the panic hook; `condr-gui` already depends on that library for `ClientConnection` and calls the same function, so the two processes cannot drift apart in format or policy. `condr-core` keeps no I/O-side dependency. Only `condr server run` and the GUI's `main` initialize logging: CLI subcommands keep printing their headline-and-details errors for a person, and never install a subscriber.

The subscriber is `fmt` layers behind one `EnvFilter`. The file layer writes compact text, one line per event with an RFC 3339 UTC timestamp, level, target and any span fields, ANSI off. A stderr layer is added when stderr is a terminal, ANSI on, with the same filter, so `cargo run -p condr-gui` and a foreground `condr server run` show everything in the terminal. When the Server's stderr is not a terminal it is the file its parent redirected, and the stderr layer then passes `error` only: that file keeps its role as the place where fatal failures and anything that bypasses the logger (an abort, a stack overflow) land, and the start-up code that tails it when the Server does not come up keeps working. JSON, `pretty` and `#[instrument]` are not enabled; the feature list is `fmt`, `std`, `env-filter`, `ansi`, `tracing-log`.

`CONDR_LOG` holds an `EnvFilter` directive string and replaces, rather than extends, the default `warn,condr_core=info,condr_server=info,condr_gui=info`. `RUST_LOG` is deliberately not read, so a developer's shell-wide setting for other Rust programs does not turn Condr's debug output on. Third-party crates stay at `warn` in both processes: the rendering stack's warnings are exactly what a stutter investigation wants, and a noisy target is silenced by name when it shows up.

Files go through `tracing-appender`'s rolling appender, daily, seven files kept, in the platform log directory that `condr_core::log_directory()` already defines. The Server's file stem stays the endpoint-derived one the stderr redirect uses, so helper Servers in tests do not share a file; the GUI's is `condr-gui`. The appender is wrapped in `non_blocking`, lossy: an event that passes the filter is formatted on the calling thread and handed to one writer thread over a bounded channel, and if the channel is full the line is dropped and counted rather than the caller waiting. The `WorkerGuard` is returned from `init` and held by `main` until it returns, never in a static, so a normal exit and an unwound panic flush the queue; only an abort loses what the worker had not yet written, which the synchronous `error` stderr layer and the accepted absence of stderr capture in the GUI already bound. A size-based rotation was declined because the appender has none and a daily file with a seven-day cap already bounds disk use; a blocking `RollingFileAppender` was declined because a `write` under a mutex on a PTY or render thread is the one cost this record exists to rule out.

The performance rule, which is the substance of the decision and which review enforces: the per-chunk and per-frame paths (PTY reads, VT parsing, terminal frame preparation and publication, `prepaint` and `paint`) may carry `debug!` and `trace!` only, which a disabled level rejects at the call site for a few nanoseconds without formatting or allocating; `info!` and above appear at connection, Pane and Workspace lifecycle, Agent state changes, recovery, configuration and errors. Spans are opened in two places, one per client connection carrying its id and transport kind, one per Pane's terminal runtime carrying its `pane_id`, and nowhere else; broad `#[instrument]` was declined for its overhead on hot functions and its noise. The terminal burst benchmark that the roadmap's diagnosability direction calls for will install a counting subscriber and assert that a high-frequency output burst produces no event at `info` or above.

Both processes install one `std::panic::set_hook` from the same module. The hook logs the payload, the location and `std::backtrace::Backtrace::force_capture()` at `error`, then calls the previous hook, so the default message still reaches stderr. It shows no dialog and attempts no recovery; a GPUI main-thread panic ends the process as before, now with a backtrace on disk. `tracing-panic`, `color-eyre` and `human-panic` were not added. Nor were `thiserror` or `anyhow`: the four error types in `condr-core` are stable hand-written ones, the CLI's error codes come from protocol types, and the binaries already format failures uniformly; a future error enum with several variants and a `source()` chain may bring `thiserror` into that one crate, and `anyhow` stays out of the libraries.

Tests install no subscriber. An unsubscribed `tracing` event costs a rejected `enabled` check, and a test that wants to read log output calls `init` itself. Out of scope here and left to their own decisions: log rotation by size, redirecting the GUI's file descriptor 2 into the log so aborts are captured, structured JSON output, OpenTelemetry export, a `condr server status --json` that reports runtime health, and any collection of diagnostics from a user's machine, which the roadmap keeps opt-in and free of terminal content.
