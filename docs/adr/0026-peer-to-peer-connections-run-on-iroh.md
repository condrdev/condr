# Peer-to-peer Connections Run on iroh

`p2p://<id>[.<invite>]` is a third way to reach a Device, beside `ssh://` and `tcp://`. It is for two machines that are both behind NAT, where today the answer is a VPN or a port forward: a home desktop and a laptop at work, a friend's machine running agents for you. `<id>` is the Device's key in hex (ADR 0025); nothing else is needed, because the Device's address is looked up by its key. The connection is a QUIC connection made by the `iroh` crate, hole-punched when possible and forwarded through Condr's relay when not, end-to-end encrypted and mutually authenticated by both Devices' keys. Everything the person sees says Peer-to-peer or p2p: the scheme, the `[server.p2p]` table, CLI flags and JSON fields, log transport names, error text, Settings and documentation. The name iroh appears once, in the website's "how it works" section with a link, and in code only as the crate in `Cargo.toml` and the `use` lines of the `p2p` module; the module, its types and the `EndpointStream::P2p` variant are named p2p so the codebase does not carry two vocabularies either.

Peer-to-peer does not replace TCP. For a Server with a stable, reachable address, a VPS, a public IP, the same LAN, a Tailscale network, TCP with Noise (ADR 0011) is one port, no third party, no hole punching and code that already works; iroh could dial such an address directly but would trade TCP for UDP, which cloud security groups and corporate networks pass far less readily, and every other thing iroh adds is a cost there. Dropping about a thousand lines of Noise for some hundred and fifty new crates would not be a simplification. The three ways are presented side by side: SSH when you already have SSH, TCP when the machine has a fixed address, Peer-to-peer when neither machine does.

The Server accepts Peer-to-peer connections when `[server.p2p] enabled = true`; like `[server] listen` it is off by default and a change applies on the next Server start. `condr server invite` prints one link per enabled transport, `tcp://<id>.<invite>@host:port` and `p2p://<id>.<invite>`, and with neither enabled says so; `condr server status --json` and the Settings page report `p2p` beside `listen`. Authentication is iroh's own, a TLS handshake between the two Ed25519 keys, so Noise is not layered on top: that would encrypt every byte twice for no gain. After the handshake the Server reads the remote id from the connection and checks `authorized-clients` through the same `ServerIdentity` TCP uses. A Device the Server does not know must send a `Credential` frame carrying the invite before `Hello`; the Server compares it in constant time with the pending invite and, once `Hello` has been read, records the Device with the same `complete_pairing`, first-wins and expiry rules as ADR 0011, then sends `Welcome`. One `condr server invite` thus pairs over either transport. Sending the invite in the clear inside the channel is safe because the channel is already encrypted to the Server's key; it is the same act as pasting a token. Unlike Noise, which rejects an unknown key in the first message, any peer that knows a Server's id can complete the QUIC handshake, since knowing the id is knowing the address; it is then closed for lacking authorization or an invite. That is accepted as a known surface without rate limiting. A `RevokeDevice` closes the Device's Peer-to-peer connections as it closes its TCP ones, from the one peer table ADR 0025 describes. Peer-to-peer connections, like TCP ones, may not administer the Server.

Condr runs the infrastructure iroh needs, and uses none of n0's. `relay.condr.dev` is an unmodified `iroh-relay`, open to any client, with a per-client receive rate limit; an access token can be compiled into Condr later if other iroh applications start using it. Relays forward opaque QUIC packets by endpoint id and help both sides find each other's addresses; once a direct path exists they carry nothing. `dns.condr.dev` is an `iroh-dns-server`: the authoritative server for that zone, delegated from `condr.dev` by an `NS` record, and the pkarr endpoint a Server publishes to. Both run from n0's published container images, pinned to the iroh version in `Cargo.lock`, on one small VM shared with other services, whose Caddy already owns ports 80 and 443. Caddy terminates TLS for both names and proxies them to the containers; the relay's own HTTPS listener sits behind it, and the relay reuses Caddy's certificate (its `Reloading` certificate mode, re-read daily) for the QUIC address-discovery socket on UDP 7842, the one port the relay exposes directly, because a client learns its public address from that socket and a proxy in front of it would defeat hole punching. The DNS server exposes port 53 directly and its pkarr endpoint through Caddy. The compose file, both configurations and the Caddy site blocks live in the `condr-p2p` repository. A Server with Peer-to-peer enabled periodically publishes a record signed with its own key that names its relay; iroh publishes relay URLs only by default, never IP addresses, and Condr keeps that default. A Client resolves `<id>` there, and if resolution fails it tries the compiled-in relay once, so the default deployment works while the DNS server is down. Both addresses are compiled into the binary; there are no `relay` or `dns` configuration keys, because self-hosting is out of scope for now and the way a self-hosted address would be carried is a decision for when someone asks. Relay protocol changes ended with iroh 0.91 and Condr ships both the client and the relay, so versions are under one hand. QUIC's keep-alive every five seconds and thirty-second idle timeout replace TCP keepalive at roughly the sensitivity of today's probes.

This is Condr's first hosted service, so the documentation says what it is and is not. It is optional and used only by Devices that connect Peer-to-peer. The relay cannot read terminals, but it sees which Devices connected to which and when, and the VM sees from which addresses: the relayed stream reaches the relay from Caddy, so client addresses appear at the address-discovery socket and in Caddy, not in the relay's connection log; the DNS zone shows which relay a Server with Peer-to-peer enabled uses, and a Device that only connects out appears nowhere. Nothing is stored and there are no accounts. If the relay is down, Peer-to-peer connections fail while TCP and SSH are unaffected. These points go into `SECURITY.md` and the website; the README links to them. The two promises made for Peer-to-peer are "No port to open, no VPN to install. Paste one link." and "End-to-end encrypted; Condr's relay never sees your terminals."

The cost is dependency weight: iroh with `default-features = false, features = ["tls-ring"]` adds some hundred and fifty crates to `condr-server` and minutes to a full build, and `condr-gui` carries them too because it depends on the `condr-server` crate for `Endpoint` and the Device key. It is accepted rather than hidden behind a feature flag, which would fork the build of an unreleased project. iroh is 1.x with a stated MSRV of 1.91, MIT or Apache-2.0, and a single upstream, n0, whose QUIC stack `noq` is its own fork of quinn.

Left for later, each with its trigger: self-hosted relays and how an address carries one, when someone wants to run their own; mDNS discovery on a LAN, a separate feature, when people ask to find Devices without exchanging a link; an access token on the relay, when it is used by software that is not Condr; a second relay region, when user distribution asks for it; capability levels (`observe`/`control`), which the roadmap already owns and which apply to Peer-to-peer exactly as to TCP, since the relay takes no part in authorization. The `RelayMode::Disabled` in-process test setup, where two iroh endpoints connect over loopback, is how pairing, `Hello`/`Welcome` and revocation are tested headlessly; Windows acceptance, including the firewall prompt the Server's UDP socket may raise, is manual.
