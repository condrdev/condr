# A Supervisor Restarts a Crashed Server

Status: accepted 2026-11-02. Builds on ADR 0053, whose abort it recovers from, answering its "has no one to start it until Server autostart lands"; ADR 0057, whose service managers only start the Server; and ADR 0031, whose desktop-shell parent the Supervisor takes in the Server's place. Detecting a Server that hangs rather than exits was considered and left out.

A poisoned Server lock aborts the Server (ADR 0053). Its Panes' programs end with it, and the Session comes back from the Snapshot with its Agent Conversations resumed once something starts a new Server (ADR 0005). Locally, the GUI's reconnect does that. A Device reached only over TCP, Peer-to-peer or from the Companion has no one to do it, and ADR 0057's service managers only start the Server at login. Condr now starts every local Server through a Supervisor, which starts it again when it crashes.

`spawn_server`, the one place a local Server is spawned, starts a hidden `condr server supervise` instead of `condr server run`, with the same arguments. The Supervisor takes over the detaching `spawn_server` did for the Server: `setsid` on Unix, and `DETACHED_PROCESS` with the desktop shell as its parent on Windows. It then runs `condr server run` as its own child and waits for it. `spawn_server` still waits until the Server answers on its socket. So the GUI, `condr server start` and `restart`, the SSH bridge, the restart helper and the login item of ADR 0057 all get one, and nothing that waits on them changes. The Supervisor takes its own path once at startup, which is the binary `spawn_server` chose, and starts that path every time. Asking again later would not do: once an update has replaced the binary, Linux reports the running image as `condr (deleted)`. A Server restarted after a crash therefore runs the newest installed build. The Supervisor holds no Session state and starts no threads. If it ends for any reason, the Server it started keeps running, just without a Supervisor.

How the Server ended decides what the Supervisor does:

| The Server | The Supervisor |
| --- | --- |
| exits with 0: `condr server stop`, or the old Server of a restart | exits |
| returns an error and exits with 1: another Server holds the endpoint, the TCP address is taken | exits |
| on Unix, is ended by SIGTERM, SIGKILL, SIGINT or SIGHUP: shutdown, `kill`, `systemctl --user stop`, the OOM killer | exits |
| crashes: on Unix another signal, SIGABRT from ADR 0053's abort above all; exit code 101, a panic on its main thread or on the task that runs it, which is unwound out of `main`; on Windows an exception code, `0xC0000000` to `0xCFFFFFFF`, which `process::abort` and an access violation give and `Stop-Process`'s `0xFFFFFFFF` is not | waits one second, then starts it again |

An error the Server returns is not a crash. Restarting it would only find the same taken port again, and a Server that exits with 1 because another one won the bind needs no restart. This also settles the race with the GUI. Ending `condr.exe` in Task Manager gives exit code 1 too, so it is not started again.

After four restarts within 60 seconds, a fifth crash is not restarted: the Supervisor logs that it gave up and exits. These are Syncthing's numbers. Every restart restores the Panes and resumes their Agents, so a Server that crashes at startup must not do that forever.

Condr's own restarts stay as they are. The GUI's Restart makes the Server start `condr server restart` as its child and then exit with 0, which ends the Supervisor. The helper waits for the old Server to finish and spawns a new Supervisor through `spawn_server`. `condr server restart` from a terminal and `condr server install --restart` stop the Server, which also ends its Supervisor, and spawn a new one. So no restart needs to tell the Supervisor anything. A GUI that reconnects during the Supervisor's one-second wait may start its own Server. Whichever binds first serves. The other `server run` finds the bind lock held and returns that error, so its Supervisor exits too. Until then two Supervisors run, which is why the Supervisor lock below is shared.

A stop can arrive while a Supervisor waits to restart a crashed Server. `condr server stop` then finds nothing listening, and the Supervisor would start the Server again while the stop waits for it to exit. So `wait_for_shutdown` notes when the listener is free while a Supervisor still runs, and stops the Server that binds after that as well. `restart`, `uninstall` and Setup's upgrade stop through the same wait.

A crash should not pass unseen. The Supervisor logs each restart to the Server's stderr log, and hands the new Server how the old one crashed on its command line, as the hidden `--restarted-after`. An environment variable would reach every Pane. The new Server logs that as an error, which puts it among the recent errors that `condr server status` and the GUI show.

The Supervisor is `condr.exe` too, so on Windows it keeps that file in use for a moment after the Server exits. Setup upgrades by running `condr server stop` and then replacing `condr.exe`, and `condr server uninstall` deletes it. If either finds the Supervisor still running, the file is locked. The Supervisor therefore holds a shared lock on a file of its own beside the Server's bind lock, and `wait_for_shutdown` waits for both.

Letting the service managers of ADR 0057 restart the Server, as VS Code's tunnel service does with `Restart=always` and `KeepAlive`, was rejected. It would cover only the Server they started, not one started by the GUI, an SSH Client or a person. Every restart and start path would have to go through `systemctl` and `launchctl`, because a service manager that sees its process exit cleans up after it and takes the restart helper with it. Windows would still need a Supervisor of its own, since a login item supervises nothing. Syncthing ships its own monitor process for the same reasons and lets a systemd unit only start it. A switch to turn the Supervisor off, like Syncthing's `--no-restart`, was left out until someone needs it. Tests that need a bare Server run `condr server run` directly.

Consequences: each machine runs one more small process. An error the accept loop returns, such as running out of file descriptors, ends the Server with exit code 1 and is not restarted, as before this decision. A crash still ends every Pane's programs and any turn in progress, as ADR 0053 accepted. Only the wait before Condr comes back is shorter. A Server that deadlocks without exiting is not restarted, since the Supervisor sees only exits.

Tests: whether an end is a crash, and whether a crash may still be restarted, are pure functions, tested with exit codes, Unix signals, a Windows exception code and the 60-second window. The lock is tested as two Supervisors holding it and `wait_for_shutdown` seeing it until the last one ends. On Unix an integration test covers the whole cycle. A Server started through `spawn_server` and sent SIGABRT answers again under a new Runtime Epoch, and `condr server status` reports the crash. Sent SIGTERM, it stays down, and both locks are released. Sent SIGABRT and then `condr server stop` at once, it stops for good although its Supervisor restarted it. On Windows, Setup's upgrade with a Server running is checked by hand.
