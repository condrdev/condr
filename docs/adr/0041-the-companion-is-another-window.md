# The Companion Is Another Window

Status: accepted 2026-10-10. Amends ADR 0036 (the sizing is released when its holder reports `Focus(false)`, and a GUI takes it back by interacting), ADR 0004 (a Client may limit its visual stream to some Panes), ADR 0021 (the Companion ignores `Activated`), ADR 0024 (the "Needs you" list on the phone) and ADR 0027 (the build mark is the desktop GUI's); adds `WatchTerminals` and leaves ADR 0028's Client hints reserved.

Inside a Pane, the Companion is one more window in the sense of ADR 0036. Typing, scrolling, selecting and copying, opening links, and touches while a program tracks the mouse all go over the wire as the GUI's do, and opening a Pane reports focus and sends the phone's size, so the terminal reflows to the phone's width until a desktop window takes the sizing back. Outside a Pane, the Companion shows every paired Device's Workspaces and Agents and one "Needs you" list across them, changes no Session structure, and holds no sizing. It receives terminal frames only for the Pane it shows.

The roadmap gives the Companion one job: telling the person, away from the computer, which Agent finished and which waits for them, and letting them answer. Answering means first reading what the Agent did, and that output was drawn at the desktop's width: 180 columns on a 390-point screen is about two points a character. A phone that drew the Server's grid without sizing it, as ADR 0036 has a window that does not size a Pane draw it, would need zooming and sideways panning for every line. So the Companion takes the size the way a window does, and Claude Code, Codex and the rest redraw for some fifty columns while the scrollback reflows. That also lets it acknowledge a bell, which only `Focus(true)` does. A Companion that never reported focus and drew the desktop's grid was declined for those reasons; per-Client sizes and scroll positions stay declined as ADR 0036 declined them. Input from the phone scrolls every viewer to the bottom and clears the shared selection, as typing in the GUI does, and scrolling on the phone moves the desktop's scroll position, because a Pane has one (ADR 0008, ADR 0036).

The sizing ADR 0036 describes belongs to one Client per Server, not one per Pane: while the phone holds it, every desktop window's `Resize` on that Server is dropped, for every Pane, including a Pane the CLI opens. Under ADR 0036 as written the holder kept it until another Client reported focus or it left, so a phone that had looked at one Pane and gone back to its list would go on blocking every Resize, and a desktop window that was already focused had no way to take the sizing back, since the GUI reports focus only when its focused Pane changes. Three rules close that, for every Client alike. First, a `Focus(false)` from the Client that holds the sizing releases it, so until someone reports focus again any Client's `Resize` applies, as before anyone has; a window that loses activation already reports `Focus(false)`, so a desktop window in the background no longer holds back the window in use, which is the case ADR 0036 worried about for Panes the CLI opens. Second, a Client whose window is active sends its size again for each Pane it shows whose frames carry a grid other than the size it measured, at most once per heartbeat interval (10 s): while another Client holds the sizing the Server drops it, and once that Client releases it the next one applies, so a Pane the phone let go returns to the size of the desktop window in use within seconds and with no one clicking. A window in the background sends nothing of the kind, so two desktop windows do not trade the terminals' size back and forth while the person is away from both. Third, a click or a key in a focused Pane, while any Pane this Client shows on that Server has a grid other than the size it measured, reports `Focus(true)` again and measures again, so the desktop takes the sizing back the moment someone uses it, and the phone does the same on a tap. Until then a Pane the phone sized shows on the desktop as ADR 0036 draws an unsized one, from the top-left corner and cut off. Holding the sizing for every Pane on the Server, not only the one it shows, is the cost of keeping ADR 0036's single holder; a per-Pane holder was declined with the per-Client sizes.

While a Pane's terminal is on screen and the app is active, the Companion sends `Focus(true)` for it and `Resize` for the grid its font and the visible area give, and `Focus(false)` when the Pane leaves the screen or the app goes inactive, which by the rules above hands the sizing back. When the soft keyboard appears or goes, or the phone rotates, it sends one `Resize` after the change settles rather than one per animation frame, since every resize reflows the terminal and clears the shared selection. It never sends `FocusPane`, which is Session structure (ADR 0021) and would move the focused Pane in every desktop window. Text goes as `Text`, pasted text as `Paste`, and a row above the soft keyboard adds the keys it lacks as `Key`: Esc, Tab, a sticky Ctrl, and the arrow keys, which is what a permission prompt or a numbered question needs. When the view says the program tracks the mouse, a tap is a click and a swipe is wheel motion, as the GUI maps a trackpad; otherwise a swipe scrolls, and a long press starts a selection that Copy puts on the phone's clipboard. A link opens in the phone's browser. Of the OSC 52 copies that reach every subscribed Client (ADR 0007), the Companion applies only those from the Pane it shows, using the `pane_id` the message carries: ADR 0007's reason to fan them out is that every Client shows the same Pane, which a phone resting on its "Needs you" list does not.

Replies happen only inside a Pane, with its screen in view. The "Needs you" list, and the notifications the push work adds, open the Pane; nothing in them answers. That is ADR 0024's rule, unchanged: "no keystroke is synthesized into the Pane by the list". A key the person taps on the row above the keyboard is input like any keyboard's. One-tap approve and deny from the list or a notification was declined: it would synthesize keystrokes chosen by Agent kind, would break the day a CLI rearranges its prompt, and answering for the user waits, on the roadmap, for an interface the vendors expose.

Outside the terminal the Companion changes nothing. It creates and closes no Workspace, Tab or Pane, starts no Agent and adds or removes no worktree; the roadmap stops short of moving the desktop onto the phone. Its View is its own (ADR 0021), and it ignores `Activated`: a phone shows one screen at a time and its person navigates by Agent, so a CLI's `--focus` elsewhere should not move it. Its Done is its own as well, an `AgentTracker` fed by the Pane it has on screen, so finishing an Agent the person watched on the desktop still shows as Done on the phone, as it would in a second desktop window. Done marks only a change the Companion saw happen: `AgentTracker` starts an Agent that is already `Idle` as `Idle`, so an Agent that finished while the app was in the background or not running shows as `Idle` after the next Bootstrap, not as Done. Notifications are what tell the person about those, and whether a phone should carry finished-but-unseen across its absences is the push ADR's question. "Needs you" heads the first screen and lists every `Blocked` Agent on every paired Device with its `blocked_on`; a tap opens the Pane. Errors keep ADR 0020's places: a connection state on its Device, and a failed operation as one error the person can read, copy and dismiss.

Today every subscribed Client receives frames for every Pane: subscribing marks all terminals pending for it, every terminal change marks it again for every subscriber, and the Bootstrap carries a full `TerminalView` per Pane. On a phone reaching several Devices through the relay, that is every busy Agent's animation, in bytes and battery, for Panes it does not show. `ClientMessage` gains `WatchTerminals { panes }`, the set of Panes whose frames this Client wants. A Client that never sends it gets every Pane, as now, so the desktop is unchanged. The set belongs to the connection, not to its subscription: it can be sent right after `Welcome`, before `SnapshotRequest`, and it survives a `SubscriptionRejected` and the Bootstrap and `Subscribe` that follow, so a rejected phone does not fall back to every Pane. The Server's per-subscriber state starts from the set, marking only watched Panes pending. The Bootstrap still carries a terminal record for every Pane, with its title, its exit and its bell, and only watched Panes' records carry a view: the record's view becomes optional, so a phone outside any Pane still knows every Pane's title and attention, and a Pane it starts watching later keeps the exit state the Bootstrap gave it rather than taking one from its first frame. When the set changes, the Server stops marking a removed Pane and drops its baseline, and marks an added Pane pending with no baseline, so the next render the slot takes carries a full frame for it (ADR 0004); a Pane that stays in the set keeps its baseline. A change that arrives while a Bootstrap is being sent is applied when that Bootstrap finishes: baselines outside the set are dropped there, and a watched Pane without a baseline is marked pending. Frames already in the slot or on the wire still arrive. The Client ignores frames and chunks for a Pane outside its set and drops its chunk assembly for a Pane it removed; for a watched Pane it holds no baseline for, it ignores a delta until a full frame arrives, since after a change of set that is an old frame in flight, not a revision gap, and asking for a Bootstrap there would loop. A revision gap on a Pane that has a baseline still asks for exactly one Bootstrap, as before. The Companion connects to every paired Device with an empty set, so outside a Pane it receives only reliable events, and opening a Pane sets the set to that Pane.

Reliable events still include `WorkspaceGitChanged`, with up to two `GitChanges` per Workspace, and `WorkspaceFilesChanged`, and the Bootstrap still carries every Workspace's Git state, though the phone shows neither Changes nor Files. That traffic is accepted until it is measured: how much of a phone's bytes over cellular and the relay it accounts for joins the roadmap's risks to measure, and widening `WatchTerminals` into a set of interests that covers Git waits for that measurement. No frame-rate cap is added either: one slot per Client already paces frames to what the Companion reads, and ADR 0028's reserved Client hints in `Hello`, a frame-rate cap and a viewport, wait for measurements over cellular and the relay.

`WatchTerminals` is the first message a Client must not do without, so it is gated at the connection, not per feature. The Companion keeps the protocol `Welcome` names and checks it before it sends anything else; on a Server too old for `WatchTerminals` it sends neither `SnapshotRequest` nor `Subscribe`, so not one frame is fetched, and the Device shows that it needs an update where ADR 0020 puts a connection state. This is an exception to ADR 0028's rule that a feature an older Server lacks is hidden or muted while the connection goes on, for the reason it exists: going on would stream every Pane to the phone. One protocol number cannot tell builds with and without the message apart, and before the first stable release the protocol stays `1` (ADR 0028), while Companion builds ship through store review and cannot follow the desktop's weekly changes. So until that release the Companion goes out only through TestFlight and Android's internal testing, alongside desktop builds of the same day, and the first stable release raises the protocol to `2`, fixes both minimums, and makes `WatchTerminals` its first gated message. The roadmap's release gate says so.

A paired Companion may do what every paired Device may: the whole Session, and the Settings commands ADR 0038 allows over TCP and Peer-to-peer, though the app offers no Settings. The `observe` and `control` levels wait for their trigger on the roadmap, a second person sharing a Server, and a phone is not a second person. What protects a lost phone is where its key is kept (ADR 0040) and an app lock: the app asks for Face ID, a fingerprint or the device passcode when it starts and when it returns after more than five minutes in the background. A lost phone is revoked under Paired devices on each Device it was paired with, since there is no revocation that reaches every Server at once (ADR 0040).

ADR 0027's build mark belongs to the desktop GUI. The Companion shows no build difference: a store build waits days for review, so its build would almost never equal a Server's and the mark would never go out. A protocol refusal still shows on that Device, and a feature a Server is too old for is muted as "not available" (ADR 0028). The Companion's build still travels in `Hello`, and the Server logs a difference as for any Client.

CONTEXT.md changes with this decision: a Device is any machine with a Device key, and only a computer's Device runs a Server; a Client is the GUI, the CLI or the Companion; and the Companion, "Needs you" and Done get entries of their own.

Left for later, each with its trigger: per-Client scroll positions in the scrollback, when people need to read history on the phone without moving the desktop's view; pasting an image from the phone through ADR 0012's staging, when people want to send a screenshot to an Agent from the phone; Session structure from the phone, which the roadmap rules out; a desktop `WatchTerminals` for Panes it does not show, when hidden Panes on a remote Device are measured crowding the shown one over the relay; Git and file events left out for a Client that shows neither, when they are measured as a real share of a phone's traffic; the frame-rate cap and viewport hints, after measurements on cellular; Done that outlasts the phone's absences, with the push ADR; approving for the user, when a vendor exposes a way.

Tests, on the Server: a Client with an empty `WatchTerminals` receiving events and no frames; a Pane added to the set arriving as a full frame and then as deltas; a Pane removed producing no new frames and losing its baseline while a Pane kept in the set goes on with deltas; a set sent before `SnapshotRequest` giving a Bootstrap whose records carry title, exit and bell for every Pane and a view only for watched ones; a set changed during a Bootstrap reconciled when it finishes; the set surviving `SubscriptionRejected` and the resubscription; a Client that never sends it receiving every Pane, as the existing tests already require; the holder's `Focus(false)` releasing the sizing so another Client's `Resize` applies, and a stale `Focus(false)` from a Client that does not hold it releasing nothing. On the Client: frames for a Pane outside the set ignored, an old delta for a newly watched Pane ignored without a Bootstrap, and a real gap still asking for one; an active GUI whose frames show another grid sending its size again at most once per heartbeat interval, a background GUI sending nothing, and a click in its focused Pane reporting focus again; the Companion sending neither `SnapshotRequest` nor `Subscribe` to a Server too old for `WatchTerminals`; the key row and touch mappings in `condr-mobile` producing the `TerminalCommand`s the GUI sends for the same keys and wheel motion; an OSC 52 copy from another Pane left off the phone's clipboard. Manual on a phone: reading a Claude Code session at phone width and answering its permission prompt while the desktop window stays open and active, then clicking into the desktop's Pane and seeing it take the size back, and going back to the list and seeing the desktop's size return within ten seconds without a click.
