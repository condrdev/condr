# The Companion Is Another Window

Status: accepted 2026-10-10. Limits ADR 0027's build mark to the desktop GUI; adds `WatchTerminals` and leaves ADR 0028's Client hints reserved.

Inside a Pane, the Companion is one more window in the sense of ADR 0036. Typing, scrolling, selecting and copying, opening links, and touches while a program tracks the mouse all go over the wire as the GUI's do, and opening a Pane reports focus and sends the phone's size, so the terminal reflows to the phone's width until a desktop window takes the focus back. Outside a Pane, the Companion shows every paired Device's Workspaces and Agents and one "Needs you" list across them, and changes no Session structure. It receives terminal frames only for the Pane it shows.

The roadmap gives the Companion one job: telling the person, away from the computer, which Agent finished and which waits for them, and letting them answer. Answering means first reading what the Agent did, and that output was drawn at the desktop's width: 180 columns on a 390-point screen is about two points a character. A phone that drew the Server's grid without sizing it, as ADR 0036 has a window that does not size a Pane draw it, would need zooming and sideways panning for every line. So the Companion takes the size the way a window does, and Claude Code, Codex and the rest redraw for some fifty columns while the scrollback reflows. That also lets it acknowledge a bell, which only `Focus(true)` does. A Companion that never reported focus and drew the desktop's grid was declined for those reasons; per-Client sizes and scroll positions stay declined as ADR 0036 declined them. The cost is the one two desktop windows already pay: while the phone holds a Pane, the desktop draws it from the top-left corner, cut off, until someone clicks into it, and that window measures again. Input from the phone scrolls every viewer to the bottom and clears the shared selection, as typing in the GUI does, and scrolling on the phone moves the desktop's scroll position, because a Pane has one (ADR 0008, ADR 0036).

While a Pane's terminal is on screen and the app is active, the Companion sends `Focus(true)` for it and `Resize` for the grid its font and the visible area give, again whenever the soft keyboard appears or the phone rotates, and `Focus(false)` when the Pane leaves the screen; a late `Focus(false)` takes nothing from a window that has the focus since. It never sends `FocusPane`, which is Session structure (ADR 0021) and would move the focused Pane in every desktop window. Text goes as `Text`, pasted text as `Paste`, and a row above the soft keyboard adds the keys it lacks as `Key`: Esc, Tab, a sticky Ctrl, and the arrow keys, which is what a permission prompt or a numbered question needs. When the view says the program tracks the mouse, a tap is a click and a swipe is wheel motion, as the GUI maps a trackpad; otherwise a swipe scrolls, and a long press starts a selection that Copy puts on the phone's clipboard. A link opens in the phone's browser. OSC 52 copies reach the Companion as they reach every subscribed Client (ADR 0007).

Replies happen only inside a Pane, with its screen in view. The "Needs you" list, and the notifications the push work adds, open the Pane; nothing in them answers. That is ADR 0024's rule, unchanged: "no keystroke is synthesized into the Pane by the list". A key the person taps on the row above the keyboard is input like any keyboard's. One-tap approve and deny from the list or a notification was declined: it would synthesize keystrokes chosen by Agent kind, would break the day a CLI rearranges its prompt, and answering for the user waits, on the roadmap, for an interface the vendors expose.

Outside the terminal the Companion changes nothing. It creates and closes no Workspace, Tab or Pane, starts no Agent and adds or removes no worktree; the roadmap stops short of moving the desktop onto the phone. Its View is its own (ADR 0021), and it ignores `Activated`: a phone shows one screen at a time and its person navigates by Agent, so a CLI's `--focus` elsewhere should not move it. Its Done is its own as well, an `AgentTracker` fed by the Pane it has on screen, so finishing an Agent the person watched on the desktop still shows as Done on the phone, as it would in a second desktop window. "Needs you" heads its first screen and lists every `Blocked` Agent on every paired Device with its `blocked_on`; a tap opens the Pane. Errors keep ADR 0020's places: a connection state on its Device, a failed operation as one transient message.

Today every subscribed Client receives frames for every Pane: subscribing marks all terminals pending for it, every terminal change marks it again for every subscriber, and the Bootstrap carries a full `TerminalView` per Pane. On a phone reaching several Devices through the relay, that is every busy Agent's animation, in bytes and battery, for Panes it does not show. `ClientMessage` gains `WatchTerminals { panes }`, the set of Panes whose frames this Client wants. A Client that never sends it gets every Pane, as now, so the desktop is unchanged. Sent before `SnapshotRequest`, it limits the Bootstrap's terminal views to that set; sent later, a Pane added to the set gets a full frame with no baseline through the one visual slot (ADR 0004), and a Pane removed stops being marked and loses its baseline. The Companion connects to every paired Device with an empty set, so outside a Pane it receives only reliable events, Agent states, layout and titles, and opening a Pane sets the set to that Pane. Before the first release the protocol stays `1` (ADR 0028). From then on, against a Server whose protocol predates `WatchTerminals` the Companion does not subscribe and says to update that Device, since the alternative is every Pane over a phone's link. No frame-rate cap is added: one slot per Client already paces frames to what the Companion reads, and ADR 0028's reserved Client hints in `Hello`, a frame-rate cap and a viewport, wait for measurements over cellular and the relay.

A paired Companion may do what every paired Device may: the whole Session, and the Settings commands ADR 0038 allows over TCP and Peer-to-peer, though the app offers no Settings. The `observe` and `control` levels wait for their trigger on the roadmap, a second person sharing a Server, and a phone is not a second person. What protects a lost phone is where its key is kept (ADR 0040) and an app lock: the app asks for Face ID, a fingerprint or the device passcode when it starts and when it returns after more than five minutes in the background. Revoking the phone under Paired devices ends it everywhere.

ADR 0027's build mark belongs to the desktop GUI. The Companion shows no build difference: a store build waits days for review, so its build would almost never equal a Server's and the mark would never go out. A protocol refusal still shows on that Device, and a feature a Server is too old for is muted as "not available" (ADR 0028). The Companion's build still travels in `Hello`, and the Server logs a difference as for any Client.

CONTEXT.md changes with this decision: a Device is any machine with a Device key, and only a computer's Device runs a Server; a Client is the GUI, the CLI or the Companion; and the Companion, "Needs you" and Done get entries of their own.

Left for later, each with its trigger: per-Client scroll positions in the scrollback, when people need to read history on the phone without moving the desktop's view; pasting an image from the phone through ADR 0012's staging, when people want to send a screenshot to an Agent from the phone; Session structure from the phone, which the roadmap rules out; a desktop `WatchTerminals` for Panes it does not show, when hidden Panes on a remote Device are measured crowding the shown one over the relay; the frame-rate cap and viewport hints, after measurements on cellular; approving for the user, when a vendor exposes a way.

Tests: a Client with an empty `WatchTerminals` receiving events and no frames; a Pane added to the set arriving as a full frame and then as deltas; a Pane removed sending nothing more and dropping its baseline; a Bootstrap after `WatchTerminals` carrying only those views; a Client that never sends it receiving every Pane, as the existing tests already require; the key row and touch mappings in `condr-mobile` producing the `TerminalCommand`s the GUI sends for the same keys and wheel motion. Manual on a phone: reading a Claude Code session at phone width and answering its permission prompt while the desktop window stays open, then clicking back into the desktop and seeing it take the size back.
