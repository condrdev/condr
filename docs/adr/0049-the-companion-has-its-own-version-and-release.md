# The Companion Has Its Own Version and Release

Status: accepted 2026-10-23. Takes the APK out of the desktop's release (ADR 0048) and the iOS upload off the maintainer's Mac.

The Companion is released apart from the desktop, on its own version, one for the iPhone and the Android app. Until now the APK came out of `build.yml` with every desktop package, so it shipped only when the desktop did, and the iPhone build went to TestFlight from the maintainer's Mac. Their numbers had drifted three ways: the APK's file carried the desktop's version (`condr-companion-0.1.14.apk`), the app itself said `0.1`, and the integer Android compares was the run number of whichever workflow built it, counted apart for nightlies and releases. A nightly at `76` and the next release at `20` meant a phone that took the nightly could not install the release. The iPhone's build number was bumped by hand, a commit per upload.

Nothing ties the two releases together. Whether a Companion and a Server work together is the protocol range in the handshake (ADR 0028), not their versions, and the Companion shows a protocol refusal and features a Server is too old for, never a build difference (ADR 0041). So a fix to the phone need not wait for the desktop, nor a desktop release carry an unchanged phone.

The version is `mobile/version.xcconfig`'s `MARKETING_VERSION`, three integers, starting at `0.1.15` after the last APK the desktop shipped. XcodeGen gives the file to the app target; Gradle reads the same line. Each platform also needs a number its system compares, and both follow from the version, so nobody keeps a second one: Android's `versionCode` is `major × 1,000,000 + minor × 1,000 + patch` (`0.1.15` is `1015`, above every code shipped so far), and the iPhone's build number is the version itself, which App Store Connect requires to rise only within one version. Every release bumps the patch, even one that changes a single platform: the other simply skips that number. The cost is on the iPhone: a version's first build for external testers goes through Beta App Review, so every Companion release waits for one.

Pushing a `companion-v<version>` tag runs `companion.yml`. It checks the tag against the file, builds the APK, signed with the upload key it refuses to go without, since an APK signed with another cannot install over the last, and publishes it with `SHA256SUMS` as "Condr Companion <version>", never marked Latest, which stays the desktop's for `condr.dev/download` and every update check. It also archives the iPhone app on `macos-26` and uploads it to TestFlight, signed through an App Store Connect team key with the Admin role (`APPLE_ASC_KEY`, `APPLE_ASC_KEY_ID`, with the team's `APPLE_NOTARY_ISSUER`), which may create the cloud-managed distribution certificate and the App Store profile; the notary key's Developer role cannot. The archive is signed for development before the export signs it for the App Store, so the runner imports one Apple Development certificate kept for CI (`APPLE_DEVELOPMENT_P12`); without it, every run had the API create a new certificate. The APK is published only after the iPhone build is uploaded, so the two ship together. Run on demand, on any ref, the workflow builds and signs both and publishes nothing, which checks the secrets before a tag depends on them. Sending a processed build to the public TestFlight group and through Beta App Review stays in App Store Connect. The nightly builds the desktop alone: a phone that wants a change sooner gets a Companion release, which costs one tag.

The release notes are git-cliff's, split by path. The Companion's take the commits that touch `mobile/`, `crates/condr-mobile/`, `crates/condr-client/`, which both apps link, or the two mobile scripts, since its previous tag, or since `v0.1.14` for the first; the desktop's and the nightly's leave out the commits that touch only the Companion's files and documentation, so a change on both sides, such as pushes, is in both. A path filter costs git-cliff the tags in a range, so both releases name their version with `--tag`.

Not decided here: the build identity the Companion's library sends in `Hello`, still the desktop's workspace version plus the commit (ADR 0027), which only a Server's log shows; it should carry the Companion's version once anything reads it. Google Play and the App Store wait for the first stable release (ADR 0048); their uploads join `companion.yml` then, keyed by the same version.
