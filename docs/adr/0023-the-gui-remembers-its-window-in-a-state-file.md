# The GUI Remembers Its Window in a State File

The GUI keeps what it showed when it last ran in a file of its own, `condr-gui.state` in the platform state directory, beside the Servers' `condr-server-<id>.snapshot` files (ADR 0005), and opens the next run the same way: the window's bounds and whether it was maximized or fullscreen, the left sidebar's width and collapse, the right sidebar's width, and per Device the Workspace it showed, per Workspace the Tab it showed, whether the Workspace was unfolded in the left sidebar, and whether the right sidebar was open and on Changes or Files. The file is one protobuf message (ADR 0028), rewritten whole through a sibling temporary file and a rename after every change with a half-second debounce, and flushed once more on quit. A missing, unreadable or undecodable file is an empty state, never a reason not to start.

Before this, a GUI restart opened a centred 1280×720 window on the first Workspace of the local Server with every Workspace folded and the right sidebar closed, and the person put it all back by hand every morning. ADR 0021 had left the door open: which Workspace and Tab a client shows is that client's own state, "a client preference that can be added when it is missed". It was missed.

Everything in the file is Client presentation, so nothing here touches the protocol, the Session or its Snapshot; ADR 0005 and 0021 stand as written. The highlighted agent Pane in the left sidebar needs no entry: it is derived from the Tab's `focused_pane`, which the Server persists, so restoring the Workspace and Tab brings it back. Files-tree unfolding and Changes-tree folding are not remembered: they are shallow navigation the working tree invalidates on its own.

Per-Device state is keyed by the Server's `ServerId` from the Bootstrap, not by the sidebar position or the `[[client.servers]]` name: connection keys are numbered by load order and the local Server has no saved entry, while a `ServerId` outlives Device renames, address changes and Server restarts, and `WorkspaceId`s are persisted in the Snapshot so they match again after a Server restart. The state is applied when a Server first bootstraps in a run, ids the Session no longer has are skipped, and a Server not connected this run keeps its entry unchanged for the next.

`config.toml` was declined as the home for this. That file is shared with the Server and hand-editable (ADR 0022 keeps GUI-only preferences there because a person may want to edit them); window coordinates, pixel widths and per-Workspace bits are written by the machine many times an hour and would bury the settings a person reads, and every write takes the cross-process config lock. Configuration is what a person meant; state is what the machine last saw. The Server's own split, TOML for configuration and a binary file in the state directory for the Snapshot, is the one the GUI follows.
