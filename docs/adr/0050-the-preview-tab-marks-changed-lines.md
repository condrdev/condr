# The Preview Tab Marks Changed Lines

Status: accepted 2026-10-27. Builds on ADR 0045, whose Source view is the editor that gains the marks, and ADR 0034, whose per-Client comparison they follow.

IDEA, VS Code and Zed mark the lines a file changed beside the line numbers and on the scrollbar, so a person sees at a glance what an agent touched and where it sits in a long file. The Diff Tab answers the same question line by line, but only in its own Tab. The Preview Tab's Source view now shows it too: a bar for each added or modified line in the gutter, a mark where lines were deleted, and the same changes on the scrollbar track. It only shows them. A click does nothing, there is no peek diff, and no hunk is reverted. Condr is still not an IDE (ADR 0045) nor a source-control client (ADR 0046).

## What is marked

The editor's own text is compared, unsaved edits included, against what the Workspace's Changes view compares with: `HEAD`, or the merge base with the Base Branch, per this Client's choice (ADR 0034). So the marks agree with the Changes list and the Diff Tab, and switching the comparison moves them. A file compared only once it is saved was declined, since unsaved lines would shift every mark below them, so the marks would be wrong or hidden exactly while the person edits. Comparing against the index, as Zed does, was declined because Condr folds the index and the worktree into one status (ADR 0017).

Within each changed run, lines with nothing on the old side are added and lines with nothing on the new side are deleted. A run with both is modified. Added and modified lines take a bar. A deletion takes a pill on the boundary at the top of the line after it, or after the last line when the end of the file was deleted, which is where IntelliJ and Zed put it. Colours are the Changes status colours (`status_color`), so one status has one colour across the GUI. The scrollbar mark is the same colour at 60% opacity, as VS Code draws it.

Only the Source view shows marks, read-only text included. Rendered Markdown and SVG have no lines to mark. A file the old side lacks, such as an untracked or newly added file, is wholly added, as the Diff Tab shows it. An ignored file, a Workspace outside a repository, and a file that is binary, too large or a symlink on either side show none.

## The old side

`GitOldFile { workspace_id, path, against }` is a Client request beside `GitDiff`, with `against` meaning the same. It resolves the old side the way `GitDiff` does: the same base tree, and a renamed file's old path taken from the comparison's own changes. It then returns that side's text, converted as a checkout would write it (end-of-line and filter attributes), so the GUI can compare it with the editor's text as it is. The converted text is decoded lossily, as `ReadFile` decodes. `GitDiff` converts the other way, worktree to Git, but only the Server can apply filters, and the editor's text is in worktree form. The reply is one of `text`, `added` (the old side lacks the path and it is not ignored), `none` (ignored, binary, larger than `MAX_DIFF_BYTES`, or a symlink on either side), or failed with a message. It runs off the Client's request loop, as `GitDiff` does (ADR 0046).

Reusing `GitDiff { full_context }` and rebuilding the old file from its hunks was declined. It sends the new side the GUI already holds. And its hunks pass the 1 MiB limit near a 1 MiB file, where it falls back to three lines of context, so an editable file could not be marked.

The GUI asks when the Preview Tab shows a file or is retargeted, when this Client switches the Workspace's comparison, and on every `WorkspaceGitChanged` for the Workspace, which is one blob read. It never asks on `WorkspaceFilesChanged`, since the working tree moving does not change the old side. It asks only for a Workspace with a Git snapshot, and `against` is the merge base only when that snapshot carries a base.

## Comparing in the GUI

The editor's text changes on every keystroke, and the Server only sees it once it is saved, so the line diff runs in the GUI. It uses `similar`, the version GPUI Kit already builds into the GUI for its `Diff`, so declaring it adds no code. `AGENTS.md`'s dependency rule names it as the second exception. A hand-written Myers diff was declined; it is code to own for nothing.

A diff runs at most once per 200 ms, after the text or the old side changes, on the background executor with a deadline. Only the latest result is applied. A diff that hits the deadline keeps the marks it had. Between diffs Kit moves the marks with the edits, so they stay on their lines while the person types. VS Code throttles the same way (200 ms), and IntelliJ debounces (100 ms).

A failed `GitOldFile`, an older Server answering "does not support that request; update it", and a lost connection all show no marks and log at `debug!`. Nothing is reported with `report_error`. ADR 0045 and ADR 0046 report an older Server's refusal because the person asked for something. Here they asked for nothing, and a toast on every file opened would say only that a decoration is missing. Nothing is lost, and there is no place for the error to belong (ADR 0020).

## Drawing the marks: GPUI Kit

Kit 0.8's `Editor` has no gutter marks and nothing on its scrollbar track, and anything drawn over it from outside would place itself by Kit's private layout constants. So the drawing goes upstream to longbridge/gpui-kit as one PR, as ADR 0046's highlighter did, and Condr ships this decision once a crates.io release has it. Nothing of it ships before. The API is general, not Git's. Kit already splits Monaco's decoration facets into one collection per paint surface (`TextDecorationCollection`, `RangeDecorationCollection`), and IntelliJ's change markers and Zed's do the same per surface. So it adds two more collections, mirroring `RangeDecorationCollection`'s handles (`set`, `append`, `clear`, `dispose`, `get_ranges`), ownership and edit tracking, with their docs linking Monaco's equivalents:

- `create_gutter_decorations_collection(Vec<GutterDecoration>)` draws a bar on every line a non-empty UTF-8 byte range touches, as Monaco's `isWholeLine`. An empty range is a pill on the boundary at the top of its line, so a deletion needs no style enum. Unlike `RangeDecoration`, an empty range is kept and survives edits that empty it. Text typed at its offset goes after it. The strip sits at the far left of the gutter, before the line numbers, as Zed has it. It is 3 px wide by default, set with `gutter_decorations_width`, and reserved while a collection exists, so the text does not shift as the marks change. A decoration whose range starts inside a fold draws as one bar on the fold's row, in its own `with_folded_color` when set, as Zed draws a hunk that folding hides.
- `create_overview_ruler_decorations_collection(Vec<OverviewRulerDecoration>)` draws on the vertical scrollbar track, in Monaco's `OverviewRulerLane { Left, Center, Right, Full }`, with Git conventionally in Left, search in Center and diagnostics in Right, as Monaco, Zed and IntelliJ order them. Marks draw beneath the scrollbar, whether Kit's own or one supplied with `set_scrollbar_renderer`, and stay visible while its thumb fades over them. Each sits at its rows' share of the content height, is at least 6 px tall, and merges with a touching mark of the same colour in its lane.

Both take an `Hsla` through `with_color`, falling back to the editor's foreground as `RangeDecoration` does. For applications that want themed colours, Kit's highlight theme, which follows Zed's theme format, reads Zed's status colours `created`, `modified` and `deleted`, falling back to `success`, `warning` and `error`; most bundled themes already set them. Zed's own `version_control.*` keys were left out: in Kit they would be a new public field of `HighlightThemeStyle`, which Kit's patch releases defer as source-breaking (as v0.8.1 deferred new `MotionTokens` fields), while the status colours have private fields. Condr passes its status colours instead and sets both collections again after each diff and when the GUI theme changes. Clicks, hover and Kit's own search matches on the ruler are left out of the PR. Each can come later without changing the collections.

## Not in this decision

A minimap; acting on a mark (peek, revert, staging); search results, cursors or diagnostics on the scrollbar; marks in the Diff Tab or in Rendered views; the Companion and the `condr` CLI. Bumping Kit for this also brings 0.8.1's `Diff` highlighter (ADR 0046), which is its own change. `CONTEXT.md`'s Preview Tab entry and the website change with the implementation, not before. Mature editors' approaches are compared in `docs/research/editor-line-markers.md`.

Tests, in core and the Server: `GitOldFile` returns the `HEAD` blob, the merge-base blob, and a renamed file's old content; returns `added` for an untracked and a newly added file, and `none` for an ignored untracked file, a binary, an oversized blob and a symlink; converts an `eol=crlf` or `autocrlf` blob to CRLF; refuses an unknown Workspace, and the merge base without a Base Branch; and round-trips through protobuf. In the GUI: a line diff becomes added, modified and deleted decorations, including a deletion at the top and at the end of the file and a CRLF file; a burst of edits diffs once per throttle, and only the latest result applies; the old side is asked for again on `WorkspaceGitChanged` and on a comparison switch, but not on `WorkspaceFilesChanged`; an unsaved edit moves the marks; an older Server's refusal shows no marks and reports nothing; and a visual test with a real Server draws the gutter and scrollbar marks for a file an agent changed.
