# The CLI Reaches Saved Devices Directly

`condr --device <name>` runs any `workspace`, `tab`, `pane` or `agent` command against the Server of a remote Device instead of the Server this Pane or this machine belongs to. `<name>` is an entry of `[[client.servers]]` in the shared `config.toml`, the same list the GUI writes when a person connects a Device, so a Device has one name in the sidebar and on the command line. `CONDR_DEVICE` sets the default for a shell or an agent. The Endpoint is parsed as the GUI parses it: an `ssh://` address runs the system `ssh`, a `tcp://` address speaks Noise with this machine's device key, the one the GUI paired with. Every call connects on its own, exactly as a call to the local socket does today, and disconnects when it exits. `condr device list` names the saved Devices and connects to each at once to report whether it answers and how many Workspaces it holds; `condr workspace list --all-devices` lists the command's own target and then every saved Device's Workspaces, each tagged with its `device`, and names the Devices it could not reach under `unreachable` rather than leaving them out. The result JSON of every other command is unchanged; ids and agent names in it belong to the Device that answered, so the caller passes the same `--device` to each follow-up.

Before this, the GUI could show several Devices but the CLI knew only `CONDR_SOCKET_PATH` and the machine's default socket. An orchestrating agent in a local Pane could not see a remote Workspace, let alone `agent start` there and `agent wait` for it; the value of several machines stopped at looking.

The `[[client.servers]]` decoding and writing moved from the GUI into `condr-server` next to `Endpoint` (`SavedServer`, `load_saved_servers`, `save_saved_servers`), on top of the `config.toml` read and write primitives that `condr-core` already owns. `Endpoint`, `StaticKey` and the SSH target type stay in `condr-server`: `condr-core` keeps no notion of a remote machine. GUI-only keys such as appearance, terminal font and editors stay in the GUI.

An SSH Device costs a full `ssh` handshake per call, and a host with a second factor cannot be reached in `BatchMode` at all. On Unix, Condr therefore adds OpenSSH connection sharing to every `ssh` it spawns, for the CLI and the GUI alike: `ControlMaster=auto`, a `ControlPath` under Condr's runtime directory hashed with `%C`, and `ControlPersist=60`, so consecutive calls ride the master the GUI or the previous call opened and the master lingers a minute after the last one. Before adding these, Condr asks `ssh -G` for the effective configuration of that destination; when the user already set a `ControlPath` for it, Condr adds nothing and rides their master, which is also how a host that prompts for a second factor works: the person opens the session once by hand and Condr reuses it. Windows OpenSSH has no multiplexing, so Windows clients connect per call. No long-lived agent process is introduced: the lingering master is OpenSSH's own.

Three alternatives were declined. Federation, where the local Server proxies other Servers and holds their credentials, would break ADR 0013's boundary of one Server per host owning only its own Session, and would put remote keys and connections into a process that outlives the person's intent. A CLI daemon that keeps connections open would be a second long-lived process to install, supervise and explain, for a saving OpenSSH already provides. Naming Devices anew for the CLI, or by address, would have given one machine two names; the sidebar label is the name.

ADR 0011 and 0015 still describe how a TCP and an SSH connection are made; this ADR only lets the CLI make them. ADR 0013's boundary stands: a Server never speaks for another. Authorization is unchanged, so a CLI that reaches a Device has the same rights as the GUI that paired it; the `observe`/`control` split remains future work. Cross-Device Workspace migration, task queues and schedulers are out of scope.
