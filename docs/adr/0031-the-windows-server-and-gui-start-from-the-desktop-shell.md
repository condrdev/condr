# The Windows Server and GUI Start from the Desktop Shell

On Windows, the Server and the GUI both run with the process state the desktop shell gives a program started from the Start menu, whichever process asked for them. Two entry points make that true. First, the detached Server starts with the session's desktop shell as its parent. `start_local_server` is the one place a local Server is started (the GUI connecting, `condr server start` and `restart`), so this is where it happens. Second, Setup's "Launch Condr" step starts the GUI through `explorer.exe` rather than as Setup's own child.

A Windows process inherits more than its environment from its creator, and a long-lived Server passes all of it on to every shell it starts. Two cases reached users. In the first, Setup enforced the redirection trust mitigation (RedirectionGuard) and launched the GUI after an upgrade. The GUI then started the Server, and every Pane inherited the policy and refused to follow junctions that a standard user had created. pnpm's `.tools` store failed with `ERROR_UNTRUSTED_MOUNT_POINT`, and linked agent skills stopped loading in an agent running in a Pane. In the second, an agent's shell tool that ignores Ctrl+C started a Server, and every Pane inherited the console's ignore flag. Each case looked like a Condr bug in whatever the user happened to run, and each depended only on who had started the Server. Unix daemons avoid this by resetting the state they inherit when they detach; this is the Windows counterpart.

For the Server, `PROC_THREAD_ATTRIBUTE_PARENT_PROCESS` (`windows_spawn::SpawnOptions::parent_process`) makes the shell the parent. Windows documents that the new process then takes its token and job, among other attributes, from that parent rather than from its creator. The documentation says nothing about process mitigations, so an experiment checked them: a launcher that enforced redirection trust passed it to a direct child but not to one it parented to `explorer.exe`. The shell is found through `GetShellWindow` and `GetWindowThreadProcessId`, which name this session's desktop shell rather than guessing at an `explorer.exe` by name. The Server's standard streams are already explicit (null stdin, the stderr log), as a foreign parent requires. The environment and working directory still come from the caller, so `CONDR_*` variables and test endpoints keep working.

For the GUI, Setup's `[Run]` entry is `explorer.exe "<app>\condr-gui.exe"`. The short-lived `explorer.exe` hands the launch to the shell's COM factory (`explorer.exe /factory,… -Embedding`, started by DcomLaunch), so the GUI is no longer a descendant of Setup. The same experiment, run from a launcher that enforced redirection trust, found that a program started this way did not inherit the policy. This keeps the GUI clean too, together with what it starts directly (Open in editors, `ssh`), and not only the Server behind it. Setup's own calls to `condr server stop` and `status` stay direct children; they start nothing.

The consequences follow from what the shell hands down. A Server started from an elevated terminal now runs with the shell's standard token, so its Panes are no longer elevated. A Server is the user's desktop daemon and should not carry privileges that one launcher happened to have. A Server started inside a Job, such as an agent's sandbox, a CI step or an installer, leaves that Job, much as `setsid` leaves a session. The Server's own Jobs for Terminals are unchanged (ADR 0030).

Without a desktop shell, for example a Server started over SSH or from a service, there is nothing to take a clean baseline from. The Server then starts as its launcher's child, as before, and logs that at debug level. The console's Ctrl+C ignore flag is handled separately: it is cleared where each Terminal's shell starts, in `condr-core`, which covers it however the Server was created.

Not in scope: a GUI that someone other than Setup or the shell starts with unusual state keeps that state for itself and for what it starts directly. The Server behind it is still clean. The GUI's own restart after an update relaunches from the running GUI, so it hands on whatever that GUI had, which after either launch path above is the shell's.

A Windows test starts a helper that enforces redirection trust on itself. The helper launches a probe the way the detached Server is launched, and the test asserts that the probe does not inherit the policy. The test skips where the machine has no desktop shell or cannot enforce the policy. The Setup launch was checked once by hand with the same probe. Building and running the installer is not part of the test suite.
