# The Protocol and Snapshots Are Protobuf

Everything Condr puts on the wire or on disk in binary form is Protocol Buffers: the handshake, every `ClientMessage` and `ServerMessage`, Bootstrap records, terminal frames, the Session Snapshot and the GUI's state file. bincode leaves the workspace. The reason is version skew, not language. A Client and a Server of different builds must keep working together: a laptop's GUI updates while the remote Devices it reaches over SSH, TCP or Peer-to-peer (ADR 0022, 0026) keep an older `condr`, and a mobile Client will wait days in store review while its Server is already updated. bincode is positional, so any field added shifts every byte after it and the only safe policy is strict equality, under which one small change disconnects every Device until both sides are updated. Protobuf's numbered fields, ignored unknown fields and default-valued missing fields give additive evolution without a scheme Condr would have to invent. The same holds for Clients that are not Rust: a Swift or Kotlin Client gets its types from the same `.proto` files instead of reimplementing bincode's layout. Web access is a different question and is not decided here; a JSON API would be a separate adapter. The runtime cost in dependencies is `prost` and the `bytes` crate it uses; `prost-build` and `protox` are build-only.

`PROTOCOL_VERSION` becomes a range, not an equality. `Hello` carries the Client's protocol and its `min_server_protocol`; `Welcome` carries the Server's protocol and `min_client_protocol`. The Server checks both directions, so either mismatch is a `Refusal::IncompatibleProtocol` it sends and logs, and ADR 0027's comparison still says which Device to update. A field or a variant added is not a reason to raise a minimum; only a change an older peer cannot survive is, and such changes are collected into rare, announced releases. Each side records the peer's protocol on the connection, and both sides gate on it. The Server never sends a Client a variant newer than the Client's protocol. The Client never sends a `ClientMessage` variant newer than the Server's protocol: a feature the Server is too old for is hidden or disabled on that Device, in the muted "not available" register of ADR 0020, never sent to fail, and the CLI refuses it locally before sending, with the JSON code `feature_unavailable` naming the Device's protocol and a non-zero exit. Each side keeps the peer's protocol from the handshake; the gating itself arrives with the first variant that needs it. How a particular variant degrades is written in the pull request that adds it, within the rules below, not in a framework built ahead of the first need. Before the first release the protocol stays `1`, meaning this protobuf protocol, and both minimums equal it.

This amends ADR 0027. The handshake is still frozen and still lives in `protocol::handshake`, but it is protobuf too, and what is frozen is now field numbers, not bytes: `Hello`, `Welcome` and `Refusal` may gain fields, which is how the two minimums arrive, and never renumber or reuse one. Protobuf encoding is not canonical, so the test that guards the handshake is decode-golden: fixed byte strings from protocol `1`, including one carrying a field number this build does not know, must keep decoding to the expected `Hello` and `Welcome`, beside one encode-golden fixture. `Refusal` grows by adding members to its `oneof`; one this build does not know is shown as "refused for a reason this build does not know; update this Device" and classified like `IncompatibleProtocol`. The split from the big enums, argued in ADR 0027 from bincode's positional layout, stays for a simpler reason: it keeps the frames every version must read in one small file. ADR 0027's "every change after `Welcome` bumps the protocol" is replaced by the range above. A build of Condr from before this decision meeting one from after fails to decode the first frame and disconnects without a readable refusal; that break is accepted once, before release.

The `.proto` files are the single source of truth, in `proto/condr/v1/`. `condr-core`'s `build.rs` compiles them with `prost-build` and `protox`, a pure-Rust compiler, so neither development machine needs a system `protoc` and no generated code is committed. The generated types stay `pub(crate)` inside `protocol::pb` and never reach `condr-server` or `condr-gui`. The domain types keep their shapes; serde derives stay only where JSON still uses them, the OSC 777 hook events and the CLI's `--json` output. `From` and `TryFrom` conversions, one file per area (handshake; session with the agent, Git and file types it carries; terminal input and frames; messages), translate at the boundary, and the terminal view's columns live beside its hyperlink interning in `terminal/view/wire.rs`. This is the one place Condr writes by hand what serde derived before, and it is accepted: prost has no mapping from generated types to domain types, a `oneof` is an `Option` that every `match` would otherwise unwrap, and newtypes do not survive generation. The mapping rules: an `Option` of a scalar or string whose `None` differs from the default is a proto3 `optional` field; `Option<Vec<_>>` is a wrapper message; `Result<T, String>` is `oneof { T ok; string err }`; `RuntimeEpoch` is 16 `bytes` and a device or invite key 32, both length-checked; a `RelativePathBuf` is a string checked to be relative. Every enum reserves `0` as `*_UNSPECIFIED` and numbers its real variants from `1`, so `AgentState::Unknown` and `TerminalMouseTracking::None` are ordinary values; `0` means "not sent", which is malformed for a field the message has always had and, for a field added later, is mapped to the default the adding pull request names.

Decoding has three outcomes, not two: a known value, a malformed one, and one this build does not know. Enums and `oneof`s are treated differently, because they grow differently. Every enum names, in a comment in its `.proto`, the fallback value an unknown value decodes to: `AgentKind` gains `Other`, which the GUI shows as a generic agent, mouse tracking falls back to `None`, a cursor shape to `Block`, and so on, so a newer Server reporting a new agent kind or a new terminal mode costs an older Client one generic label, not a message. An enum with no safe fallback says so, and a value added to it must be gated or raise a minimum. A `oneof` with no member set is unknown, since protobuf cannot tell an unset `oneof` from a member added later; it makes the smallest enclosing message that is a `ServerMessage`, `ClientMessage`, `SessionEvent`, `BootstrapRecord` or `TerminalViewFrame` unknown, and anything else wrong is malformed. Malformed input is a `FramingError` after the handshake and `Refusal::Malformed` during it, and closes the connection as today. Unknown input never closes it; the length prefix keeps the stream in step, and each stream has one answer. A Server that receives an unknown `ClientMessage` answers with its generic error and keeps reading; with the Client-side gating above this is a bug path, and the GUI shows it as one toast. A `SessionEvent` the Server may not send an older Client is sent as `SessionEvent::Omitted` under the same sequence, live and on replay alike, so the Client's cursor stays contiguous and no gap forces a Bootstrap; `Omitted` exists from protocol `1` so every build knows it. When the first gated event exists, the Server frames each event once per distinct peer protocol among its subscribers, not once per Client, and applies the same substitution when it replays history on `Subscribe`; until then every peer is protocol `1` and nothing is gated, so that pull request builds it. An event may be omitted only if it carries state the older Client does not render; otherwise the adding pull request supplies a substitute the older Client understands, or raises the minimum. An unknown event that reaches a Client anyway makes it request one Bootstrap through `request_snapshot`. An unknown outer `ServerMessage` may have been the answer to something the Client is waiting on, a `LayoutApplied` or a `ControlGranted`, so it takes the stronger recovery the GUI already uses for a lost reply of that kind: pending layout projections are cleared, control is reacquired, and the Bootstrap follows. An unknown terminal frame makes it discard its pending visual and chunk state for that Pane and request one Bootstrap, because the Server advanced that Client's visual baseline when it slotted the frame (ADR 0004), so the next delta could not apply and, if output stopped, no later frame would arrive. An unknown `BootstrapRecord` is skipped: the Bootstrap is complete state and the record is one this Client could not have shown, so this is the one place anything is skipped. A Bootstrap forced by unknown input that is followed by another unknown message within ten seconds disconnects with the reason "this Device sends messages this build cannot read; update it", and the GUI does not reconnect to that Device on its own, since that would only fetch the same messages again; the Device's page shows the reason, and connecting by hand retries. A gating mistake therefore cannot become a Bootstrap loop or a reconnect loop. An unknown value nested inside a known message that has no rule of its own, such as a new tab content inside the Session Snapshot, makes that whole message unknown; a Server must not send one to an older Client, and the adding pull request says what it sends instead.

Frames are protobuf's own length-delimited form, a varint length followed by the message, with one `ClientMessage` or `ServerMessage` `oneof` as the envelope. prost reads a delimited message from a buffer, not a stream, so `framing.rs` keeps a short bounded reader: it reads the varint, at most ten bytes, rejects a length above the frame limit before allocating, and only then reads and decodes the body. The read side of every stream is wrapped in a `BufReader`, since local sockets and the SSH stream are unbuffered and a byte-at-a-time varint would otherwise cost extra system calls on every frame. The buffer starts only after the handshake, where nothing hands the stream on any more: the Server's read loop once `Hello` is accepted, and the GUI's reader once the Bootstrap is in. A Client may send `Tunnel` or `Credential` and `Hello` back to back, and the handshake reader takes the varint a byte at a time, so it never reads past the frame it decodes and the raw stream can be spliced to a Tunnel as it is. The chunking in `BootstrapBatch` and `TerminalFrameChunk` stays exactly as ADR 0005 describes, with each chunked payload now a protobuf record: protobuf has nothing like it, and it is what lets a reliable message overtake a large terminal frame. The size limits in `protocol.rs` and `MAX_SNAPSHOT_BYTES` are rederived from the protobuf encoding, each as the largest legitimate message plus a stated margin, with a test that builds that message and asserts it fits; `BOOTSTRAP_BATCH_FRAME_OVERHEAD` gets the same test for the widest `BootstrapBatch` envelope. The limits matter more than they did, because prost materializes a `repeated` field completely before `TryFrom` can check its count, where bincode checked counts during deserialization. The bound is accepted and written down rather than avoided with a preflight scanner of Condr's own. It is stated as peak memory, not as a per-element factor, because vectors grow with spare capacity, nested messages own allocations of their own, and the input buffer, the generated value and the domain value coexist during conversion: decoding any frame within a limit peaks at no more than a stated multiple of that limit, and a test with a counting allocator measures it on adversarial frames (empty `repeated` elements, vectors just past a growth boundary, deeply nested payloads). The multiple is fixed in the implementation with the limits, so the rederived limits, not the domain counts, bound what a peer can make the other side allocate. `TryFrom` still enforces every domain count after decode. Protobuf is the encoding only. gRPC was declined: it needs HTTP/2 over transports that are a Unix socket, Noise over TCP, an `ssh -T` bridge and QUIC; its flow control cannot express one droppable visual slot per Client beside a reliable queue that takes priority (ADR 0004); and it would add hyper, h2 and tower to a project that stays light.

The terminal is Condr's core surface, and its encoding is columnar. A `TerminalView` carries the text of all its cells as one string with a packed column of byte lengths, packed `uint32` columns for foreground and background with the `TerminalColor` kind in the low bits and its value above them, a packed flags column, a packed hyperlink column holding table index plus one with `0` for none, and the per-frame hyperlink table and limits `view/wire.rs` has today. A `TerminalViewDelta` is flattened the same way: the cells of all its runs in one set of columns, with packed run starts and run lengths, so the most frequent frame, a spinner's one-row delta, is a single message decode. The conversion validates what arrives: every column has exactly the cell count; the byte lengths sum to the text's length and each slice is taken with a checked `get`, never an index that could panic off a character boundary; no cell exceeds 256 bytes; the cell count matches the size and `MAX_TERMINAL_CELLS` before any `Vec<TerminalCell>` is allocated; runs are non-empty, ordered, disjoint and in bounds, as `TerminalView` checks today; every hyperlink index is inside the table; every color kind is defined. The Server converts a Pane's frame to its wire form once, in `condr-core`, behind a type that reports its encoded length and encodes into the frame's buffer, so batching by size does not convert twice and each accepted batch is still serialized once (ADR 0004).

A throwaway benchmark on the arm64 machine (220×50 screen, transcript-like content, release, best of five) measured the columnar layout against today's bincode: bytes fell from 264 KB to 89 KB for a full screen and from 5.3 KB to 1.8 KB for a one-row delta, decoding was about 30% faster, encoding 25–60% slower. The same data encoded as one message per cell was three to four times slower, and that layout is rejected. Encoding runs on the Server for every Pane and every Client at display cadence, so encode and decode have separate gates. The switch does not merge until, measured by the benchmark kept in the repository with both sides' conversions and batch sizing counted, bytes are no larger than today for a full screen, a one-row delta and a six-row delta; decoding is no slower; delta encoding, one row and six rows, is within 1.1 times today's and full-screen encoding within 1.2 times; the performance tests AGENTS.md requires still pass; and on Windows, drag-selection, typing and scrolling stay responsive while Codex streams output and animates. Encode is measured on the arm64 machine, where Servers run, and decode on Windows as well. If a gate is missed, the layout is optimized before merging.

The Session Snapshot shares the wire's conversions, since `SessionSnapshot` is the same type on the wire and on disk, and it drops `SNAPSHOT_VERSION` in favour of field evolution; a Server reads a Snapshot written by an older one. A Server normally only meets older Snapshots, so reading a newer one is not designed for: an older Server that reads a newer file keeps what it knows and loses newer fields when it next writes, because prost does not retain unknown fields. What is designed for is never destroying a file the Server did not restore. Today a Snapshot is discarded in four places, when it fails to decode, fails the persistable-size check, names a root this Server rejects, or fails `Session::restore`; each is logged and replaced by an empty Session, and the next durable change overwrites the file. From now on every load that does not end in a restored Session, including a Snapshot whose content is unknown, first renames the file aside with the reason in its name, logs where it went, and only then starts empty. That covers a newer file, a corrupt one, one moved from another machine and the one-time break from bincode alike. The GUI's state file (ADR 0023) is one small protobuf message; losing it costs a window position, so it keeps ADR 0023's rule that an undecodable file is an empty state. With both converted, bincode is removed from every manifest, and the advisory marking it unmaintained no longer applies. The dev-profile `opt-level = 3` entry for bincode in the root `Cargo.toml` is replaced by entries for `prost` and `bytes`, which are now on the terminal hot path. Before the first release, CI runs `buf lint` on `proto/`; at the first release it adds `buf breaking` against `main` and the length of the compatibility window is decided. Breaking changes are allowed until then. The switch lands in one branch, not message group by message group, because the conversion layer already isolates every caller and two encodings side by side would double what has to be tested. The same branch updates what names bincode today: AGENTS.md's Transport and Persistence entries, the `handshake.rs` module comment, the bincode sentences in ADR 0004, 0005 and 0023, and the tests that build bincode fixtures by hand.

What the implementation settled. An unknown `AgentKind` decodes to `Other` where it describes an agent, but a command naming one is unknown, since nothing here could run it, and a Snapshot's resume for one is dropped. An unknown terminal frame drops the whole visual state, because the Bootstrap that restores it is per Session. An empty Snapshot file is a valid empty Session, since a Session with no Workspaces encodes to nothing. The GUI state file's message is declared with prost's derive in `gui_state.rs` rather than in `proto/`: it is the GUI's own file and no other program reads it. `MAX_CHUNKED_RECORD_SIZE` is 24 MiB, from a full-grid Terminal record of about 21 MiB; `MAX_FRAME_SIZE` stays 2 MiB. The decode peaks measured with a counting allocator are 31 times the frame for empty repeated metadata, 91 times for a Snapshot of empty Workspaces and 24 times the record for a table of empty hyperlink strings, and the stated bound is 96. That multiple is why only `PasteImage` may use the 16 MiB image allowance and why a frame over the normal limit is checked to be exactly that one field before it is decoded. The benchmark kept in the repository measured, against bincode on the same machine: a full screen 77.5 KB against 264 KB, encode 470 µs against 508, decode 655 µs against 1230; a one-row delta 1.6 KB against 5.3 KB, encode 10.3 µs against 10.1, decode 13.4 µs against 24.5; a six-row delta 9.4 KB against 31.8 KB, encode 57.5 µs against 61.3, decode 72 µs against 149. Every gate above holds; Windows acceptance is still to be done by hand.

Not decided here, each with its trigger: the Client uploading a matching `condr` to an SSH Device, as Zed and VS Code Remote do, which removes skew on that path and deserves its own ADR; Client hints in `Hello` such as a frame-rate cap and viewport, when a mobile Client exists; a WebSocket transport and a JSON Web API, when a Web Client does; capability lists in the handshake, when features become optional within one protocol version; the length of the compatibility window, at the first release.

Tests: the handshake decode-golden fixtures, one with an unknown field, and one encode-golden; a protocol below either minimum refusing as `IncompatibleProtocol` in both directions, over a socket and the SSH bridge; an unknown `Refusal` shown as "update this Device"; round trips of every message through the conversions, including the rejections `TryFrom` owns and the `UNSPECIFIED` rule; an unknown enum value decoding to its fallback, including a new `AgentKind` and an unknown mouse-tracking value inside a Terminal record that is still applied; the CLI refusing a gated feature with `feature_unavailable`; an unknown `ClientMessage` answered without closing the connection; `SessionEvent::Omitted` keeping the cursor contiguous live and on replay, framed once per peer protocol; an unknown event and an unknown terminal frame each producing exactly one Bootstrap, an unknown layout reply clearing its pending projection, and a second unknown message within the window disconnecting with the readable reason and suspending reconnection until the build changes; an unknown `BootstrapRecord` skipped; `Tunnel` and `Credential` each arriving in one read with `Hello`; the bounded frame reader rejecting an oversized varint length before allocating; each rederived limit fitting its largest legitimate message, and adversarial frames staying inside the stated peak-memory multiple under a counting allocator; malformed columnar frames (unequal columns, a length sum off by one, a slice off a character boundary, an out-of-range hyperlink or color kind, overlapping runs) rejected without a panic; an undecodable Snapshot and a decodable one with a rejected root each renamed aside and not overwritten by the next save; the Session Snapshot and GUI state round trips; the terminal encoding benchmark as an ignored test that reports bytes and times for the three workloads; and the terminal performance tests AGENTS.md lists.
