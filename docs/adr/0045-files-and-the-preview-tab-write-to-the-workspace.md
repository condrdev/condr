# Files and the Preview Tab Write to the Workspace

Status: proposed 2026-10-20. Reverses ADR 0018's "like Changes it edits nothing" and "no create, rename, delete" for the Files view and the Preview Tab. Amends ADR 0017, whose Changes rows gain the Rename, Delete and reveal actions they share with Files but otherwise stay read-only, and ADR 0037, whose Rendered view now draws the editor's text rather than the file on disk.

ADR 0018 kept the Files view and the Preview Tab read-only because the conversation and tool loop belong to the agent CLI. In use, the edits a person wants between turns are small and not worth a prompt: correcting a plan the agent wrote before telling it to go on, changing one value in a config, deleting a scratch file the agent left behind, creating the note an agent should read. Against a local Server the "Open in" editor covers this; against a remote Server there is no "Open in", and the only way to touch a file is a shell editor in a Pane. So the Preview Tab now edits the file it shows, and the Files view creates, renames and deletes entries. Condr still does not become an IDE: no language server, one open file per Workspace (the one its Preview Tab shows), no moving between directories, and Condr runs no Git operation.

## Editing

The Preview Tab's Source view is the editor. Rendered (Markdown, SVG) stays read-only and draws the editor's current text, saved or not, under ADR 0037's rules for what it may load; an unsaved SVG that does not parse shows its error and leaves the text alone, and switching between the two views keeps unsaved text. A second editing Tab, and a Source view that needs an "Edit" toggle first, were declined: one Preview Tab per Workspace already says which file is open, and a toggle is a step the person takes every time for nothing.

`ReadFile` now refuses anything that is not a regular file, such as a FIFO or a link to `/dev/null`, as it already refuses a directory. A file is editable only when the Server can give back exactly the bytes it read: valid UTF-8, at most `MAX_FILE_BYTES`, and neither binary nor an image. `ReadFile` keeps decoding lossily for display, so a stray invalid byte still does not blank the view, but such a file stays read-only, because saving its decoded text would rewrite the bytes the decoder replaced. Whether decoding was lossy is decided from the bytes, never by looking for U+FFFD in the text, since a file may hold that character legitimately. The header says why a file is read-only.

Kit's editor keeps a leading BOM, `\r\n` and a missing final newline as they are, so those round-trip in the text itself; Enter inserts `\n`. The line-ending rule is derived from the bytes each time the file is loaded: when they hold at least one `\r\n` and no other line break, saving writes each bare `\n` as `\r\n`; anything else, including an empty or one-line file, a mixed one, or one with a lone `\r`, is saved as edited. `MAX_FILE_BYTES` limits the bytes saved, after that conversion. The GUI checks it before sending, because a frame too large to encode disconnects the whole Device (`condr-client`'s writer), and the Server checks it again; either refusal keeps the text.

Saving is explicit: `secondary-s` while the editor has focus, with a mark in the Tab header while there is unsaved text. Autosave was declined because the agent beside the person writes the same tree, and an autosave would race it without asking.

The Server writes in place, truncating and rewriting the file, so permissions, ownership, hard links and a symlink all survive. Writing a temporary file and renaming it over the original was declined: it breaks hard links, has to copy ownership and permissions by hand, and on Windows fails while another process holds the file open without delete sharing. The cost is accepted: a write that fails partway, from a full disk, an I/O error or a lost network mount, leaves the file empty or partial, and another reader can see it so while the write runs. The Save then reports the failure and the editor keeps the whole text as unsaved, so the person still holds everything; saving again meets the conflict below, since the file no longer matches, and Overwrite restores it. A successful reply means the bytes were written and the file closed, not that they were flushed to disk. A symlink is written through wherever it points, as `ReadFile` reads through it.

### Concurrent edits

The text a `ReadFile` returns gains two optional fields, in the domain type as on the wire, and the GUI's cache keeps them with the text: `version`, an opaque token of the bytes read, and `lossy`. A Server with this decision sends exactly one of them for every text file, `version` when the file is editable and `lossy` when display decoding replaced bytes. The token is a fixed 64-bit hash of the bytes, the same for the life of a Server; a Server update that changes it costs one needless conflict prompt.

`WriteFile` carries the path, the text and the version the editor started from, and its reply is one of saved (with the new version), conflict, or failed (with a message). The Server compares the file's current bytes to that version and writes only when they match; a mismatch, including a file that no longer exists, is a conflict, and the GUI asks: overwrite, discard my edits and reload, or cancel. Overwrite resends without a version, which skips only the comparison: every other check below still applies, and a deleted file is recreated when its directory still exists.

That comparison is optimistic detection, not an atomic swap. One Server-wide lock, separate from the Session lock, is held by every file write, create, rename and delete from its checks to its last write, so Condr's own changes never interleave, whether they come from two Clients or from two paths naming one file. Against the agent or any other program the lock means nothing: a write that lands between the comparison and Condr's write is overwritten. Condr cannot lock out a process it does not control, and this is accepted.

The GUI saves one file at a time: a second Save waits for the first reply. It remembers the text it sent; on saved, the editor's base version becomes the new one, and the unsaved mark clears only if the editor still holds exactly that text, so typing during a Save stays unsaved. On failure, or when the connection drops before the reply, the text and the base version are left as they were; if the write did land, the next save meets a conflict, and Overwrite is then harmless.

`WorkspaceFilesChanged` names no path (ADR 0018), so the shown file is refetched after every batch and compared by version. A refetch whose version is present and equals the editor's base changes nothing, the refetch after this Client's own save included, even when that save converted line endings. A different version is applied as an edit, as ADR 0018 does, only when there is no unsaved text; with unsaved text the text and base version stay, the header says the file changed on disk, and the next save meets the conflict. Without a version on both sides, as for lossy text or an older Server, the whole result is compared as ADR 0018 does today. A refetch that comes back binary, too large, an image, lossy, gone or failed never replaces unsaved text either. A refetch sent before or during a Save is dropped, since the write runs apart from reads and such a read may catch the file half written, and the file is refetched once the Save replies.

### Unsaved text

Unsaved text belongs to this Client's Preview Tab editor and is owned by the application, not by a window, so a Tab carried into its own window (ADR 0043) carries it along. A Client holds at most one per Workspace, and none outlives the Tab's file: there is no list of detached drafts to manage.

The Preview Tab's path is Session state, so the text can be taken away by this Client or by another. Before this Client shows another file, closes the Tab, closes the Workspace, removes the Device, or quits, it asks: save, don't save, or cancel. The action goes on only once the save succeeds and leaves no unsaved text, so text typed while it ran asks again, and cancelling a conflict prompt cancels the action too. Quitting asks once for each Workspace with unsaved text; while disconnected only don't save and cancel are offered, beside a Copy that puts the text on the clipboard.

When something else takes the text away, this Client asks at once, one file at a time: save to the original path, copy to the clipboard, or discard. That covers another Client showing another file, closing the Tab or closing the Workspace; another Client renaming the file; and a reconnect whose Bootstrap no longer shows that path in a Workspace with the same id and Root Directory. Save is offered only while that Workspace is still open and connected. A deleted file's Tab stays open saying the file no longer exists, and saving recreates it through the conflict path. While disconnected the text is kept and Save is disabled until the connection returns. A crash of the GUI loses unsaved text; that is the price of declining autosave.

## Creating, renaming and deleting

`CreateEntry { path, kind }`, `RenameEntry { from, to }` and `DeleteEntry { path }` are Client requests under a Workspace, beside `ReadFile`, each with one reply: done, invalid (a problem with the name, shown under the dialog's field), or failed (shown with `report_error`). They and `WriteFile` run off the Client's request loop, as `BrowseDirectory` does, because a recursive delete or a slow mount can take long and must not stall terminal input. After each one, including one that failed partway, the Server publishes `WorkspaceFilesChanged` for that Workspace itself and asks for its Git status to be recomputed, as terminal activity does, since the watcher drops batches that touch only ignored paths and may not be watching at all; Changes and an open Diff Tab follow from that.

The Server checks every write, create, rename and delete itself, whatever the dialog checked, since a Client may run on another platform. The path must pass `valid_diff_path`, and no component may be `.git` in any ASCII case. A file written must be a regular file or not yet exist. The last component of every path a request names must not be empty or hold NUL, and on a Windows Server it must not hold `:`, which names an alternate data stream, end in a dot or a space, or be a reserved device name such as `CON` or `COM1`. Paths may pass through symlinked directories, since Files lists and follows them; delete and rename act on a symlink itself, never on what it points to, and `remove_dir_all` does not follow links inside the tree it removes. The Root Directory itself cannot be named, since `valid_diff_path` rejects the empty path.

These checks are a guard against mistakes, not a security boundary: any Client that may write files may also type `rm -rf` into a Pane (Authority below), and a check made before a write cannot stop another process from swapping a link in between. So "Condr runs no Git operation" means exactly that, and that no request names a path through `.git`; it does not stop a symlink that aliases `.git`, nor deleting a directory that holds a nested repository, which the confirmation covers with "and everything in it".

New File… and New Folder… are in the Files view's context menu: on a directory they create inside it, on a file beside it, and on the empty area below the tree in the Root Directory. Changes does not offer them. A dialog takes one name and stays open, holding it, until the reply arrives. `/`, `\`, `.`, `..`, `.git` and a name the directory's listing already holds are refused under the field before sending (ADR 0020), and so is an invalid reply from the Server, such as a name that already exists outside a truncated listing; a failed reply closes the dialog with `report_error`. Inline entry in the tree, as VS Code does, was declined: a dialog gets ADR 0020's field validation for free. Nested names such as `a/b.txt` are refused rather than creating intermediate directories. Creation is exclusive (`File::create_new`, `create_dir`), so it never replaces an entry. Afterwards the parent directory unfolds, and a new file opens in the Preview Tab's Source with the cursor in it.

Rename… is in both views' context menus and renames within the same directory only; the Server refuses a `from` and `to` with different parents, and moving between directories is not offered. The dialog fills in the current name with the part before the extension selected. A rename never replaces another entry: the Server refuses when the target names an existing entry, a dangling symlink included, that is not the source itself by filesystem identity. So a change of case or of Unicode normalization alone works on any volume, while renaming `a` to `DEST` beside a distinct `dest` on a case-insensitive volume is refused. An entry that another program creates at the target between that check and the rename may be replaced; as with writes, this is accepted. Renaming to the same name does nothing.

After a rename the Server retargets any Preview Tab showing the old path, or a path under a renamed directory, as a layout change that asks no Client to show it. The renaming Client knows both paths, so its unsaved text follows the file; another Client sees an ordinary retarget and asks as above. A rename made by the agent or another program is an old path that disappeared. A Diff Tab keeps its path and recomputes against the Client's chosen comparison, with its existing behaviour for a path that is missing or unchanged.

Delete… is in both views' context menus. On a row whose Changes status is deleted, Delete, Rename and the reveal action below are disabled. It always confirms, naming the relative path and, for a directory, "and everything in it", then removes permanently. The system trash was declined: a headless remote Server usually has none, the `trash` crate is one more dependency, and Git or the agent's own history recovers most of what a person deletes by mistake.

## Reveal in the file manager

For a Workspace on a local Server only, both views' context menus gain a reveal action on files and directories: "Reveal in Finder" (`open -R`) on macOS, "Reveal in File Explorer" (`explorer /select,`) on Windows, and "Open Containing Folder" (`xdg-open` on the parent) on Linux, which cannot select the entry without a D-Bus call to the file manager. A directory is selected in its parent, not opened, and a dangling symlink reveals its parent. It runs on the GUI's machine with "Open in"'s launcher and sends nothing to the Server.

## Authority and compatibility

Any attached, authenticated Client may write, create, rename and delete, under the same rule as terminal input (ADR 0012, ADR 0036): a Pane can already run `rm -rf`, and capability-based authorization, when it comes, covers both. Unsaved text is one Client's own state, never a lock on the Session: another Client's retarget or rename is never refused because of it.

Before the first stable release the protocol stays at 1, and one number cannot tell builds apart (ADR 0041), so these requests are not gated; the first stable release raises the protocol to 2 with them included. Until then a Server older than this sends text with neither `version` nor `lossy`, so the GUI keeps that file read-only and the header says the Server needs an update, and it answers each new request with its "does not support that request; update it" error, shown with `report_error`, which also closes the dialog that sent it. This departs from ADR 0028's rule that a feature an older Server lacks is hidden, for the reason ADR 0041 gives: before that release no protocol number marks the builds that have it. An older GUI ignores `version` and `lossy` and never sends the new requests.

## Not in this decision

Downloading a remote file to this machine: it needs chunked transfer past the 2 MiB frame without stalling the terminal stream on the Client's writer (ADR 0037), and waits for its own decision. Moving entries between directories, drag and drop in the tree, multiple selection, keyboard shortcuts for tree actions (the tree has no keyboard navigation), editing in the Diff Tab, the Companion, and the `condr` CLI, which has `ssh` and `scp` beside it. `CONTEXT.md`'s Files, Preview Tab and Changes entries and the website change with the implementation, not before.

Tests, in core and the Server: every text file carries a `version` or `lossy`, a valid literal U+FFFD is not lossy, and a link to a device or FIFO is refused rather than read; a CRLF file, with and without a BOM, saves an added line as `\r\n`, while LF, empty, one-line, mixed and lone-CR files save as edited, and the size limit counts the converted bytes; a stale version, or a versioned save whose file is gone, is a conflict, while a save without a version overwrites, recreates a deleted file, and still refuses `.git`, a non-regular file and an oversized text; two saves from one base give one saved and one conflict; a write that fails after truncating reports failed; the largest legal `WriteFile` frame encodes within `MAX_FRAME_SIZE`; `.git` in any case and component, and on Windows an alternate stream, a trailing dot and a reserved name, are refused; creation never replaces; a rename onto an existing entry, a dangling link or, on a case-insensitive volume, a distinct entry differing only in case is refused, while a case-only or normalization-only rename of one entry succeeds; a Preview Tab under a renamed directory follows it; deleting a directory does not follow a symlink inside it; a change inside an ignored directory, with no watcher running, publishes `WorkspaceFilesChanged` and fresh Git status; and a slow delete does not hold up terminal input. In the GUI: a refetch with the editor's base version leaves its text, selection and undo alone, while lossy text and an older Server's text still refresh; an unrelated change in the Workspace does not say the file changed; typing during a Save leaves the text unsaved, typing during a save-and-close asks again, a refetch that overlaps a Save is dropped, and a lost reply keeps the text; a paste past the limit is refused without disconnecting; another Client retargeting or closing the Tab, closing the Workspace, or a reconnect that no longer shows the file asks to save, copy or discard; quit asks for each unsaved file; unsaved Markdown and SVG render in Rendered; and the reveal action appears only for a local Server.
