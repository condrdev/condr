# Windows Panes Run on the ConPTY Condr Ships

Status: accepted 2026-10-30. Amends ADR 0044, whose protocol now reaches Claude Code on Windows too, and ADR 0054, whose colour answers now reach a program on Windows.

The ConPTY Windows ships, kernel32's `CreatePseudoConsole` and the conhost it starts, stands between a Pane's program and libghostty-vt, and it keeps two things from the program. It drops every OSC sequence written to its input, while CSI and DCS pass, so the answer to `OSC 7501 ; ?` and the colour answers of ADR 0054 never arrive. And it answers DA1 itself the moment the program asks, without the terminal. Claude Code takes a DA1 reply that arrives before the OSC 7501 answer as "unsupported" (ADR 0044), so on Windows it never reports over the protocol, and its state comes from its hooks alone, which fire nothing on an interrupt: an interrupted turn stayed `Working`. Codex never learned the background. This was measured on Windows 11 24H2 with a program in a Pane that writes the queries and prints its raw VT input, and by writing sequences straight into a Pane's input: `A`, an OSC, `B`, a DCS and a CSI arrived without the OSC.

The Server loads Microsoft's own ConPTY instead: `conpty.dll` and the `OpenConsole.exe` it starts, from the `Microsoft.Windows.Console.ConPTY` package on nuget.org. They are built from Windows Terminal under the MIT license, about 1.2 MB together, and Windows Terminal and WezTerm ship them the same way. portable-pty already loads a `conpty.dll` beside the executable in preference to kernel32's, so no Condr code changes. With version 1.25.260930003 the same program reads the OSC 7501 answer ahead of libghostty-vt's own DA1 reply, and the OSC 11 answer, and an interrupted Claude Code shows `Idle` within half a second.

`condr-server`'s `build.rs` pins the package's version and SHA-256, downloads it once with curl into the user's cache directory as libghostty-vt's source is (ADR 0051), unpacks it with Windows' own `tar`, and copies the two files for the target's architecture beside the built `condr.exe`, so `cargo run` and the tests run on them too. Only a Windows host does this; checking the Windows target on another builds a `condr.exe` without them. The headless ZIP and the installer carry both beside `condr.exe`, `condr server install` places them with the binary the way it places the binary, moving a file in use aside, and `uninstall` removes them. A `condr.exe` without them beside it still runs, on Windows' ConPTY, with the losses above. The license notices gain Windows Terminal's license and the third-party notices it publishes. The package moves only when Condr needs a fix, the version, hash and notices in one commit.

Declined: embedding both files in `condr.exe` and writing them out when the Server starts. It spares the packaging, but a program that writes an executable to disk and runs it is what antivirus heuristics flag, and the DLL's directory would have to join the search path before portable-pty's first PTY. Nothing on the terminal's side can help instead: no answer can overtake a DA1 reply the console host already gave, and an OSC it drops never reaches the program.

The new console host replaces Windows' in what ADR 0051 measured against it, the cursor settling after a resize and the scrollback a resize does not pull back among them, so the Windows acceptance of ADR 0051 runs on it. Windows' conhost also splits an SGR 58 underline colour written with semicolons into separate attributes; that is checked again too.

Tests: on Windows, a program in a Pane of a real Server writes the OSC 7501 and OSC 11 queries and DA1, and must read both OSC answers before DA1's reply; without `conpty.dll` beside `condr.exe` it reads only conhost's DA1 reply and fails. The package check requires both files in the headless ZIP, in the installed desktop build and in a headless install.
