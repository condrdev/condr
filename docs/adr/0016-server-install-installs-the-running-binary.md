# `condr server install` Installs the Running Binary

`condr server install` puts the executable that is running it into the user's Condr install directory, makes it reachable from a shell, and, when asked, starts this machine's Server from the installed copy. The command knows nothing about where the binary came from: no network, no archives, no checksums, no SSH. Whatever downloaded or copied `condr` to a temporary path runs `condr server install` once and the binary puts itself in place, the way `rustup` and herdr do. Every installation detail that today lives twice, in `script/install-condr.sh` and `script/install-condr.ps1`, moves into one Rust implementation that both platforms share and that tests can exercise.

The install directory is `CONDR_INSTALL_DIR` when set, otherwise `~/.local/opt/condr` on Unix and `%LOCALAPPDATA%\Programs\Condr` on Windows: the directories the scripts already use, and on Windows the one the GUI package shares. Only `condr` (`condr.exe`) is written; any GUI files beside it are left alone. PATH registration also follows the scripts: on Unix a symlink `~/.local/bin/condr` plus a marked `export PATH` line appended once to `~/.profile` (`~/.zprofile` on macOS, `CONDR_PROFILE` to override); on Windows the install directory appended once to the user `Path` environment variable. Registration is best-effort: it writes what login shells and new Windows sessions read, and does not reach a shell that skips those files. Running `install` from the installed path itself copies nothing and only repairs PATH registration, so the command is idempotent.

Replacing an existing installation never asks: the file changes, but a running Server keeps executing the image it loaded, so nothing a person cares about ends. On Unix the new file is written beside the old one and renamed over it, which is atomic. Windows cannot overwrite a running executable but can rename it, so the old file is first renamed to a `.old` sibling and the new one moved into place; between the two steps there is no `condr.exe`, and running `install` again repairs that. Later installs delete `.old` files that nothing holds any more.

`install` never stops a Server on its own. With `--start` it starts one from the installed path when none is running; with `--restart` it runs the existing stop-then-start sequence after the copy so the new binary serves. Both spawn the installed file by its explicit path: `install` usually runs from a temporary copy, so neither `current_exe()` nor the sibling lookup nor `CONDR_SERVER_EXECUTABLE` may decide which binary becomes the Server. Because `--restart` ends the Server's Sessions and PTYs, it asks for confirmation on a terminal and refuses without `--yes` when there is none. Without either flag `install` only reports whether a Server is running. It does not judge whether that Server is stale, although since ADR 0027 every binary carries a build identity it could compare; the caller decides whether to restart, and the GUI marks a Device whose Server is another build.

The command prints one line per step for a person and, with `--json`, a single object for programs: `install_path`, `version` (the build identity of ADR 0027), `protocol`, `replaced` (whether an older file was displaced), `path_registered` and `server` (`none`, `running`, `started` or `restarted`). Exit status is non-zero when the binary could not be placed, when PATH could not be registered, or when `--start` or `--restart` was given and no Server is running at the end; a stop that succeeded followed by a start that failed leaves the machine worse than before and must not pass as success.

`condr server uninstall` undoes exactly what `install` did. It resolves the install directory by the same rule as `install` (`CONDR_INSTALL_DIR`, then the platform default), never from `current_exe()`, and deletes only inside it: the installed `condr`, any `.old` leftovers, and the directory itself once it is empty; outside it, the `~/.local/bin/condr` symlink and the marked profile lines on Unix, and the install directory's entry in the user `Path` on Windows. It stops this machine's Server first if one is running, even one started from another path such as a development build, and leaves that other binary alone. Stopping ends Sessions and PTYs, so a terminal asks first and a non-interactive run needs `--yes`. GUI files beside the binary stay, and so do the user's config, Session snapshot and logs: uninstall removes the program, not the data, and prints the data directories so a person can decide about them. On Windows the running `condr.exe` cannot delete itself; when uninstall runs from the installed copy it renames that file to `.old`, reports it as a leftover, and is otherwise complete. With `--json` it prints `removed_path`, `path_unregistered`, `server` (`none` or `stopped`) and `leftovers`.

Out of scope for this decision, and left to the callers: choosing and downloading the right build for a platform, verifying `SHA256SUMS`, unpacking archives, installing the GUI, system-wide or `sudo` installs, deleting user data, giving the Server a build identity, and any remote or SSH orchestration. The two install scripts shrink to a bootstrap shell that detects the platform, downloads and verifies the CLI archive, and executes `condr server install` with the user's arguments; the roadmap entry that assigned them the installation logic is superseded by this record. Remote installation over SSH (ADR 0015 defers it) will stream a binary to the host and run this command there, but nothing in `install` is designed for that caller specifically.
