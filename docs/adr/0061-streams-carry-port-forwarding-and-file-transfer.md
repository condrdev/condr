# Streams Carry Port Forwarding and File Transfer

Status: accepted 2026-11-04. Builds on ADR 0011, 0015, 0025 and 0026, whose four connection methods a Stream connection is opened over exactly as the Client's own connection is; ADR 0018 and 0045, whose path rules file transfer reuses; and ADR 0020, whose family of content-area pages gains the Ports page. ADR 0022's boundary stands: no Server holds a forward. Leaves ADR 0012's clipboard images on the terminal connection. Departs from ADR 0028's gating as ADR 0059 does. Replaces the roadmap's SSH-only `ssh -N -L` plan and takes "TCP and Peer-to-peer port forwarding" off its friction list. ADR 0012, 0018, 0020, 0022, 0028 and 0045 carry notes pointing here.

An Agent in a remote Workspace starts a dev server, and the person wants to see it in the browser on their own machine. Today that takes an `ssh -L` typed by hand, and a TCP or Peer-to-peer Device has no way at all. An Agent writes a report, a build or a screenshot, and the person wants the file on their machine; or the person has a file the Agent needs. Files reads and writes text through the terminal connection's ordered stream (ADR 0045), which is no place for megabytes. This decision adds one carrier for both, the Stream, and its first two consumers: forwarding a port of any remote Device to this machine, and downloading and uploading files in the Files sidebar and on the command line.

Two terms. A **Stream** is an ordered, reliable byte stream between a Client and a Server for one forwarded connection or one file transfer. It is an engineering term; the interface says "forward", "download" and "upload". It is not ADR 0004's visual stream. _Avoid_: channel, which collides with Update Channel; tunnel, which is ADR 0025's `Tunnel`; pipe, which is a named pipe. A **Forward** is one listener on the Client's machine for one port of one Device; every connection it accepts opens one Stream. The interface calls it a forward. _Avoid_: tunnel, port mapping. CONTEXT.md gains both entries with the implementation, as this repository does.

## The Stream connection

**Beside the terminal connection.** A Client opens one more connection to a Device, its Stream connection, and every Stream to that Device travels on it. The terminal connection does not change by one byte: its reliable queue, its visual slot (ADR 0004) and its writer's priorities never see Stream data. Three alternatives were declined.

- Multiplexing Streams inside the terminal connection is free to open on every connection method, Windows SSH included, but every Stream byte handed to the kernel is a byte the next keystroke and the next frame wait behind, and no user-space priority can reach into the kernel's send buffer. A 2 MiB burst costs 1.7 s at 10 Mbit/s; today's 16 MiB clipboard image costs about 13 s. Eternal Terminal multiplexes its forwards that way, and its issue "TCP tunnels can freeze terminal" stayed open for six and a half years, its maintainer's workaround being two connections. iTerm2 and kitty carry files inside the terminal's byte stream and pay with tiny requests or a blocked terminal.
- One connection per Stream gives every Stream its transport's own flow control, but a browser opens six to twenty connections per page. On Windows, where OpenSSH has no connection sharing, each would be a full SSH login, and sshd's `MaxStartups` would start refusing them. TCP would pay three round trips and a rewrite of `authorized-clients.json` each time. Orca, which did this for one-shot requests and `ssh -L` per forward, met repeated logins that a second factor cannot answer, a frozen main thread on every socket close and leftover processes holding ports, and is moving back.
- Native QUIC streams on Peer-to-peer would split the four connection methods into two implementations, and measured no better: a bulk stream on the same noq connection raised another stream's round trip from 34 µs to about 4 ms, `set_priority` notwithstanding, against about 80 µs from a second connection.

Orca, the closest tool in shape, runs its terminals on one connection and its forwarding traffic on another, each multiplexed inside with its own windows.

**On each connection method.** A TCP Device gets a second TCP connection and a second Noise handshake with the Device key, which needs no person. A Peer-to-peer Device gets a second `Tunnel` to the local Server, which dials a second QUIC connection; `Tunnel` itself is unchanged. An SSH Device gets a second `ssh -T … condr server bridge`. Where Condr manages the ControlMaster (ADR 0022), the bridge for the Stream connection adds `-o ControlPath=none`, so it is a separate TCP connection and a second login with the same key or agent that logged the terminal connection in under `BatchMode`; riding the master would put both connections back on one TCP connection and one sshd buffer. Where the person configured a `ControlPath` of their own, usually for a host with a second factor, the bridge rides their master. Where the separate login fails, a FIDO key that wants a touch or a server limit on sessions among the causes, Unix falls back to Condr's master and Windows, which has no master, reports a toast naming the Device and ssh's reason; the terminal is unaffected. A local Device's Stream connection is a second local socket.

**Lifetime.** The Stream connection opens when the person starts the first forward or the first transfer to that Device, so a Device that cannot be reached for Streams says so at once, under the Ports page's form, in a toast or as the CLI's exit, and closes when the last forward stops and the last transfer ends. There is no idle timer. It exists only while the terminal connection is up: when that connection is lost, disconnected or removed, the Stream connection closes with it and every Stream on it fails. A Stream connection that drops on its own fails its Streams and is not retried. It is registered in the Server's live peer table beside the terminal connection, so `RevokeDevice` closes it too. The cost of having no idle timer is accepted: a transfer after the last forward stopped opens the connection again, which on Windows SSH is another login.

**Handshake.** `ClientHandshake` gains a member, `streams`, carrying `StreamsHello { protocol, build, min_server_protocol, server_id }`. The first three are `Hello`'s. `server_id` is the Server the Client expects: the GUI fills it from the terminal connection's `Welcome`, the CLI, which has no terminal connection, sends 0 for any, and a mismatch is refused. As before, `Credential` or `Tunnel` precede it on a Peer-to-peer connection. The Server answers with an ordinary `Welcome` and then speaks Stream messages; it sends no Bootstrap, subscribes the connection to nothing, and does not count it as a Client, for the terminal sizes of ADR 0036 or in `condr server status`.

**Older Servers.** ADR 0028 has a Client hide what the Server is too old for, and that needs a protocol number to compare; the protocol stays `1` until the release ADR 0041 names raises it. Until then Streams are not gated, as ADR 0059's request is not. A Server older than this build reads `streams` as an empty `oneof` and refuses the handshake with `Refusal::Malformed`; the GUI shows that as one toast, "<Device> runs a Condr too old to forward ports or transfer files; update it", and the CLI fails with `feature_unavailable`. The entries are not hidden beforehand. When the protocol is raised, Streams are gated with the rest.

**Messages.** The Stream connection keeps ADR 0028's framing, varint-delimited protobuf, with a pair of top-level messages of its own in a new `proto/condr/v1/stream.proto`, so `messages.proto` gains nothing:

- `StreamClientMessage`: `Open`, `Data`, `Credit`, `Finish`, `Reset`, `Ping`.
- `StreamServerMessage`: `Opened`, `OpenFailed`, `Data`, `Credit`, `Finish`, `Reset`, `Pong`.
- `Open { stream, target }`, where `target` is one of `forward_port`, `download` and `upload`. A file is named by a Workspace id and a `RelativePathBuf`; `upload` adds `replace`.

Only the Client opens Streams. It numbers them from 1 upward and never reuses a number on a connection. Each direction ends on its own with `Finish`, as a TCP FIN does, which forwarding needs for responses delimited by closing; a Stream is closed when both directions have finished. `Reset { error }` ends both at once. `Data` or `Credit` for a Stream that was opened and has closed is ignored, since bytes sent before a `Reset` arrive after it; for a number never opened it is a protocol error and closes the Stream connection. Paseo's transfers broke on messages out of order (its issue #8392), so this rule is written down. `Open` is not a round trip: a Stream starts with its initial window in both directions, so a browser's request follows `Open` at once. The Server answers `Opened`, carrying a download's size, or `OpenFailed { error, detail }`, and drops whatever arrived for a Stream it did not open. `error` is an enum whose unknown values decode to `OTHER`: `CONNECTION_REFUSED`, `NOT_FOUND`, `ALREADY_EXISTS`, `NOT_A_FILE`, `INVALID_PATH`, a path through `.git` included, `WORKSPACE_GONE`, `TOO_MANY_STREAMS`, `IO`, `UNSUPPORTED`, `CANCELLED` and `OTHER`; `detail` is for people. `Open.target` only gains members, and an `Open` whose target this Server does not know, an empty `oneof`, is answered `OpenFailed { UNSUPPORTED }` without closing anything, as ADR 0028 has unknown input do.

**Flow control.** Every Stream may have 1 MiB in flight in each direction, and the whole Stream connection 4 MiB; both are protocol constants and the initial windows. A receiver returns credit only once its consumer took the bytes, the browser's socket write or the file write succeeded, so a slow consumer stops its sender reading from the source and the pressure reaches the program at the far end. `Credit { stream, max_offset }` is an absolute offset, "you may send up to byte N", which can be repeated and kept as only the latest value; `stream` 0 is the connection's total. Data beyond credit is a protocol error and closes the Stream connection, so no receive buffer ever exceeds its window. Data moves in chunks of at most 32 KiB, which fit one Noise record, and the sender takes the Streams that have data and credit in turn, one chunk each, so a download holds a browser's small request back by one chunk, about 26 ms at 10 Mbit/s. There are no priorities: the terminal is not on this connection. A Stream connection holds at most 256 Streams; the next `Open` fails with `TOO_MANY_STREAMS`, which a forward answers by closing the browser's new connection. A frame on the Stream connection is at most 64 KiB, against the terminal connection's 2 MiB. Neither end's reader ever blocks on a consumer: it hands a chunk to that Stream's bounded buffer, at most its window, and the Stream's own worker writes the socket or the file. The Server's Stream buffers are counted apart from the terminal connection's queues; Orca dropped terminal output when its connections shared one budget. An idle Stream connection sends `Ping` under the terminal connection's timeouts, and no transfer has a deadline of its own, since an hour-long download is legitimate.

1 MiB gives about 10 MB/s per Stream at 100 ms round trip and 35 MB/s at 30 ms, near noq's default of 1.25 MB; Orca's fixed 256 KB allowed 2.9 MB/s at 89 ms and was raised. Windows that grow with bandwidth were declined for now: they fill the bottleneck queue described next.

**What it does not fix.** Two connections on one network path still share its bottleneck. A large transfer fills a home router's queue, and the terminal's packets wait in it: barely noticeable on a fast link, a few hundred milliseconds on a 10 Mbit/s one, as an `scp` in another terminal would cause. When the SSH bridge falls back to the master or a Peer-to-peer connection goes through the Relay, both connections share one TCP connection anyway. Nothing is added for this now: no rate limit, no setting, and no rate limit on the Server. The follow-up is a window that shrinks as the round trip grows over its idle value, LEDBAT's idea, which iTerm2 uses from 8 KiB up to 4 MiB; it is built if the Windows acceptance under Delivery shows the round trip growing by more than 100 ms.

**Where it lives.** The Stream connection, its flow control and the Forward live in `condr-client`, so the GUI, the CLI and later the Companion use one implementation (ADR 0039). The GUI receives progress and results; Stream bytes never pass through its event channel.

## Port forwarding

**Who holds the listener.** The Client process that started a forward holds its listener: the GUI process for a forward the GUI started, one listener set for all its windows (ADR 0043), and the foreground `condr port forward` for one the CLI started, until Ctrl+C. No Server holds a forward, the local one included. Holding forwards in the local Server would let them outlive the GUI and be shared with the CLI, but it would make that Server a Client of other Servers, holding their connections and, for SSH, spawning `ssh` from a process that Autostart (ADR 0057) may have started without the person's agent or any way to answer a prompt. That is the federation ADR 0022 declined; ADR 0025's exception was forced by iroh's one endpoint per key, and nothing forces this one. VS Code and JetBrains likewise stop forwarding when their window closes, and Coder's and DevPod's CLIs forward for as long as they run. A forward belongs to the GUI's connection to its Device, not to a window: closing a detached Device window leaves it running. Only the process holding a forward sees it: the GUI and the CLI do not see each other's, other Clients see nothing, and the Server has no Forward, only the Streams it carries. The local Device offers no forwarding; its ports are already here.

**What it reaches.** A forward reaches the remote Server's own loopback and nothing else. `Open` carries a port, and the Server connects to `127.0.0.1:<port>` and then `[::1]:<port>`, since many dev servers listen on `::1` alone now that Node resolves `localhost` to IPv6 first. Forwarding to any `host:port` the Server can reach, into its network, is not offered; a person who wants that opens `ssh -L` or socat in a Pane. The local listener binds `127.0.0.1`, and `[::1]` as well when it can, without failing the forward when it cannot, as Coder does; binding to the local network is not offered. Every authenticated connection may forward, as ADR 0038 and 0045 let a paired Device do what a Pane already could.

**Lifetime.** While the GUI's connection to the Device is lost, whether the network dropped, the remote Server's Supervisor restarted it, the local Server restarted under a Peer-to-peer `Tunnel` or the GUI has given up and shows the Device's page, the listener stays bound, so its port and address stay. Connections through it close with the Stream connection; new ones are accepted and closed at once rather than queued; after the reconnect and its Bootstrap the forward works again with nothing to do. Forwards are not persisted: quitting the GUI ends them all, and Disconnect or Remove ends those of that Device, with no record and no restore. A forward is not tested when it is created. When the remote port refuses a connection, the browser's connection is closed and the forward's card says its last connection was refused; there is no toast per connection.

**The Ports page.** Two buttons open it: **⇄ N** at the bottom of the left sidebar, beside its other buttons, for every Device, and **⇄** on the header of each remote Device, with that Device's count when it has forwards, for that Device alone, with "Show all Devices" on the page. It is a page of the content area, in the family of ADR 0020's connection pages and the Start Page, and not a Session Tab, since forwards live in the GUI and belong to no Workspace. It covers the whole content area, the Tab strip included, where it shows "⇄ Ports", and the right sidebar; ✕ or any Workspace in the sidebar returns to the Workspace. The page has two columns. The left lists All Devices and then each remote Device with its count, a Device that is reconnecting marked so. The right holds the scope's form, with a Device choice under All, the Device's port and an optional local port, and one card per forward: the Device's port and the Device, `http://localhost:<port>` as a link, the number of connections, and Open in Browser, Copy Address and Stop. While a Device is reconnecting its cards are dimmed and say "waiting for <Device>". Without a local port, the local port is the Device's port when free, else the next free one up to twenty above, else one the system assigns, and a card whose port differs says so, "localhost:3000 was in use, so 3001 is used", as VS Code does. A local port given by hand that is taken is refused under its field (ADR 0020). Open in Browser opens `http://localhost:<port>`; there is no scheme choice, and a person who needs `https` copies the address. Ports that the later port detection finds but nothing forwards show as a muted line with Forward on it. The page was chosen from prototypes: forwards listed under each Device in the sidebar crowded the projects, a Ports tab in the right sidebar was too far out of reach, and a count in the title bar sat in the wrong place.

**The CLI.** `condr --device <name> port forward <port>...` forwards one or more ports in one process over one Stream connection. Each is `REMOTE` or `LOCAL:REMOTE`, local first as in `ssh -L`; `condr --device box port forward 5173 8080:80`. Local ports are taken as written, because a script needs a known port: one that is taken fails the command, and `0:REMOTE` lets the system choose. Without `--device`, or against this machine's Server, the command fails. Once every listener is bound it prints one line, `{"forwards":[{"device":"box","remote":5173,"local":"127.0.0.1:5173"}]}`, and then nothing more on stdout while it runs; a refused connection is one line on stderr. Ctrl+C exits 0. A lost connection prints its reason on stderr and exits non-zero, without reconnecting: `condr-client` has no reconnection, and a script learns from the exit code.

## File transfer

**What moves.** Single regular files inside a Workspace's Root Directory, named by the Workspace id and a `RelativePathBuf`, in both the GUI and the CLI. A download follows `read_file`'s rules: a regular file, symlinks followed. An upload follows ADR 0045's write rules: `valid_diff_path`, no `.git` component, a target that is a regular file or does not exist. As there, these guard against mistakes and are not a security boundary. Directories are not transferred in either direction; an Agent can archive one first. Paths outside a Workspace are not offered either; that directory can be opened as a Workspace. There is no size limit beyond the disk, since both ends stream.

**Writing.** An upload without `replace` creates its file exclusively, and an existing target answers `ALREADY_EXISTS`, so the question "replace it?" is asked after the Server found the conflict and there is no window between a check and a write. With `replace` it overwrites; a directory or anything but a regular file is refused. The Server writes `.<name>.condr-upload-<random>` beside the target, so the rename stays on one filesystem, calls `sync_all` and renames it over the target; on failure, cancellation, a full disk, a lost connection, a closed Workspace, a stopped Server or a revoked Device it deletes the temporary file, and the original is untouched. An Agent therefore never reads half a file. A replacement copies the old file's permission bits, its Unix mode or its Windows read-only flag; hard links and ownership are not kept, and on Windows a target another process holds open fails as in use. This differs from ADR 0045's save in place on purpose: a save that fails leaves the whole text in the editor, an upload that fails would leave nothing. A download is written the same way beside the destination the person chose, and replacing an existing destination was already asked by the save dialog. A file open in a Preview Tab and replaced by an upload meets ADR 0045's conflict on its next save.

**Completion and progress.** `Opened` carries a download's size, a guide for progress only, since an Agent may be rewriting the file; the Stream's end decides. The Client counts progress itself: bytes written for a download, bytes credited for an upload, since credit returns only once the Server wrote them. An upload is complete when the Server, after its `sync_all` and rename, answers the Client's `Finish` with its own; a failure is `Reset` with the error. A download is complete when the Client, after its own, answers the Server's `Finish`. Only the Client that started a transfer can cancel it, with `Reset { CANCELLED }`; other Clients do not see it. A lost connection fails the transfer and nothing retries it; resuming is not offered.

**In the GUI.** Download… is on a file's context menu in Files and in Changes, where it takes the working tree's version and is disabled on a deleted row, and on the Preview Tab's menu. History has none, since a past version is a Git object and not a file on disk; a directory has none either. Upload is a drop from the system file manager onto a directory row, or onto the space below the tree for the Root Directory, the row highlighting as the drop target, and Upload Files… on the context menu of a directory or that space, which opens the system's picker with several files allowed. A download opens the system save dialog in the directory last used this run, Downloads the first time. Files dropped or picked together are one batch: the ones without conflict start at once, and the conflicts are asked in one dialog listing them, Replace or Skip These, Skip for one. A folder in a drop is refused with a toast saying only files can be uploaded and to archive it first, while the batch's files proceed. Progress collects in a strip at the bottom of the right sidebar, under whichever of Changes, Files and History it shows: hidden with nothing to show, one line such as "⇅ 2 transfers · 45%" while transfers run, unfolding into a row per file with its direction, bar and ✕, then "⇅ 2 finished" until Clear. It lists this Client's transfers in this Workspace. A finished download raises a toast with the reveal action of ADR 0045, Show in Finder, Show in File Explorer or Open Containing Folder; every failure raises one with its reason (ADR 0020); a finished upload says so in the strip alone. With the right sidebar closed a transfer runs on and its toast still comes; the sidebar does not open by itself. A local Device offers the same entries with the same behaviour and goes through the same Stream connection, so ADR 0045's checks, its write lock and `WorkspaceFilesChanged` are never bypassed. The strip was chosen from prototypes over progress drawn inside the tree and a toast per transfer, as simpler and in one place.

**The CLI.** `condr [--device <name>] file download <path> [<dest>] [--workspace <id>] [--replace]` and `condr [--device <name>] file upload <file> <path> [--workspace <id>] [--replace]`. The words match the interface; `get` and `put` would read like `workspace get`, and `cp` would need a way to write a Workspace into `host:path`. `--workspace` follows the existing rule: it defaults to the calling Pane's Workspace when there is no `--device`, and is required otherwise. `<dest>` defaults to the file's name in the current directory. An existing target, remote or local, fails with `exists` unless `--replace` is given. A directory fails. While stderr is a terminal one line there shows the file, bytes done of total and the speed; otherwise nothing. The result is JSON on stdout, `{"download":{"path":"report.pdf","dest":"/Users/me/report.pdf","bytes":50331648}}`. Ctrl+C cancels and removes the temporary file. Failures use the CLI's error format and a non-zero exit.

**Clipboard images stay where they are.** Moving ADR 0012's images onto the Stream connection was considered and declined: pasting an image is a frequent, quick gesture, and opening a Stream connection for it, a second login on Windows SSH, is heavy for it. Its cost stays: on a slow link a large image holds back the keys after it, about 13 s for 16 MiB at 10 Mbit/s and under a second for a screenshot of a few hundred kilobytes.

## Authority

Every authenticated connection may open Streams, Local, SSH and paired TCP and Peer-to-peer Devices alike, under ADR 0038's rule: a paired Device can already run `nc`, `cat` or `curl` in a Pane, so refusing it guards nothing. When `observe` and `control` exist, opening a Stream needs `control`. The security model does not change. SECURITY.md gains a paragraph with the implementation: a forward binds only the loopback and reaches only the Device's loopback; while it runs, any process on the Client's machine, other users' included, can reach the forwarded port through it, as with `ssh -L`; and opening a Stream takes the same rights as typing into a Pane. Its scope list gains nothing about leaving a Workspace, since those checks are not a boundary.

## Observability

`condr server status` reports one more count, `streams`, the Streams open now, and its text output a line `Streams: N open`; `clients` does not count Stream connections. Nothing per Stream is reported; which ports and files are the Client's affair and on its screen. Logging follows ADR 0019: `info!` for a Stream connection opening and closing, with its Device and reason; `warn!` for a protocol violation and for the Server failing to read or write a file; `debug!` for each Stream opening and closing, with its port or Workspace-relative path, so paths appear only there; `trace!` for chunks and credit. The GUI logs nothing more than it shows.

## Not in this decision

Port detection, finding the ports a Pane's process tree listens on and badging them, is its own roadmap item; it calls this forwarding when a detected port is clicked. Forwarding to arbitrary hosts, binding the listener to the local network, reverse forwarding from the Server, UDP, persisting forwards across GUI runs, transferring directories, paths outside a Workspace, resuming or synchronizing transfers, transfers between two remote Devices, dropping a file onto a remote terminal to upload it and paste its path as Paseo does, the Companion's forwarding and transfer, and larger previews in the Preview Tab are all left out. The design keeps the Companion open: it would use `condr-client`'s Stream connection.

Consequences:

- **A second connection per Device.** A TCP Device sees a second handshake, a Peer-to-peer Device a second QUIC connection, an SSH Device a second login unless the person's own master carries it; each happens when the first forward or transfer starts.
- **Slow links.** A large transfer on a slow link still delays the terminal by the bottleneck's queue, as described under What it does not fix.
- **Older Servers.** They refuse the Stream connection, and the person learns it from a toast or `feature_unavailable` when they first try, not from a hidden entry.
- **Forwards end with the GUI.** Quitting, Disconnect and Remove end them, and the person forwards again next time.
- **Clipboard images.** Unchanged, with ADR 0012's cost on slow links.

Tests:

- **The terminal is untouched.** A Stream whose consumer never reads, on the Client and on the Server in turn, leaves the same Client's terminal output arriving at cadence, its keys reaching the Pane and another Stream on the same connection flowing. The four terminal performance tests AGENTS.md names, burst coalescing, the final frame, unchanged cells not reshaped and real GPUI drag-selection, pass unchanged. An ignored benchmark, run like `terminal_wire_bench`, reports the keystroke echo's p50 and p99 on loopback with and without a concurrent 1 GiB download, for observation without a gate.
- **Flow control and protocol**, in `condr-client` and core. Windows of 1 MiB and 4 MiB hold, data beyond credit closes the connection, and repeated or reordered `Credit` is harmless. A closed Stream's messages are ignored and a never-opened Stream's close the connection. The 257th Stream fails with `TOO_MANY_STREAMS`, an unknown `target` answers `UNSUPPORTED` without closing, a slow Stream does not hold back a fast one, and after one direction's `Finish` the other still flows.
- **Writing files.** An exclusive upload onto an existing file answers `ALREADY_EXISTS`, and `replace` replaces it keeping its permission bits. Temporary file, `sync_all` and rename happen in that order, and cancellation, a failed write, a closed Workspace and a lost connection each remove the temporary file and leave the original. A path through `.git` and a directory are refused.
- **Local port choice.** The same port, then up to twenty above, then the system's.
- **End to end, on Local, TCP over Noise loopback, the SSH bridge and Peer-to-peer over `Network::Loopback`.**
  - Forwarding: a round trip to an echo server; a response delimited by closing arrives whole; a refused port answers `CONNECTION_REFUSED`; while the terminal connection is down the listener stays bound and new connections close at once, and after the reconnect it works.
  - Transfers: a download and an upload round trip.
  - Lifetime: the Stream connection opens with the first forward or transfer and closes with the last, closes with the terminal connection and on `RevokeDevice`, and refuses a wrong `server_id`. A simulated older Server's `Malformed` becomes `feature_unavailable` in the CLI and a toast in the GUI.
  - CLI: `port forward` prints its line once bound, `0:` lets the system choose, a taken local port fails, and a lost connection exits non-zero. `file download` and `file upload` work with `--replace` and fail on a directory.
- **GUI**, with `gpui-kit/test-support`. The Ports page opens for every Device from the sidebar's button and for one Device from its header, and the local Device has no button. A changed local port is noted and a taken one is refused under its field. A batch with conflicts asks once, a dropped folder is refused, and the transfer strip unfolds and clears.
- **By hand, on Windows.** A Linux Server limited with `tc qdisc … tbf rate 10mbit`, reached over TCP and over SSH, sends a 1 GB download while a Pane runs Codex streaming and animating and another window pings the Server. Typing, scrolling and drag-selection are observed, and the ping's growth over idle is recorded. Unlimited, nothing may feel slower than without a transfer. At 10 Mbit/s, growth up to 100 ms passes; more starts the delay-based window above. Also by hand: the Stream connection's second SSH login on Windows and the toast when it fails, a drop from Explorer into Files, the Ports page, the transfer strip, and clipboard images unchanged.

Delivery, each step merged on its own:

1. The Stream connection: `stream.proto`, the handshake, flow control and lifetime in `condr-client` and the Server, with the unit, end-to-end and isolation tests.
2. Forwarding's core and CLI: the Forward in `condr-client` and `condr port forward`. Forwarding is usable from here.
3. The GUI's Ports page.
4. File transfer's core and CLI: the Server's reading and writing, `condr-client`, and `condr file`.
5. The GUI's entries in Files, Changes and the Preview Tab, and the transfer strip.
6. Finishing: the Windows acceptance above; `condr --skill`, which tells an Agent that `port forward` keeps running and is started in the background or another Pane, its first JSON line meaning ready, that file paths are Workspace-relative, and that an existing target needs `--replace`; the Stream and Forward entries in CONTEXT.md; the website, whose `using/remote.md` gains a section on forwarding ports and whose `reference/cli.md` gains `port forward` and `file`; SECURITY.md's paragraph; and the roadmap's section marked done.
