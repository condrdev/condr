# Streams Carry Port Forwarding and File Transfer

Status: accepted 2026-11-04, revised 2026-11-05 after an independent review. Builds on ADR 0011, 0015, 0025 and 0026, whose four connection methods a Stream connection is opened over as the Client's own connection is; ADR 0018 and 0045, whose path rules file transfer reuses; and ADR 0020, whose family of content-area pages gains the Ports page. ADR 0022's boundary stands: no Server holds a forward. Leaves ADR 0012's clipboard images on the terminal connection. Like ADR 0059, departs from ADR 0028's gating until the protocol is raised. Replaces the roadmap's SSH-only `ssh -N -L` plan and takes "TCP and Peer-to-peer port forwarding" off its friction list. ADR 0012, 0018, 0020, 0022, 0028 and 0045 carry notes pointing here.

An Agent in a remote Workspace starts a dev server, and the person wants to see it in the browser on their own machine. Today that takes an `ssh -L` typed by hand, and a TCP or Peer-to-peer Device has no way at all. An Agent writes a report, a build or a screenshot, and the person wants the file on their machine; or the person has a file the Agent needs. Files reads and writes text through the terminal connection's ordered stream (ADR 0045), which is no place for megabytes. This decision adds one carrier for both, the Stream, and its first two consumers: forwarding a port of any remote Device to this machine, and downloading and uploading files in the Files sidebar and on the command line.

Two terms. A **Stream** is an ordered, reliable byte stream between a Client and a Server for one forwarded connection or one file transfer. It is an engineering term; the interface says "forward", "download" and "upload". It is not ADR 0004's visual stream. _Avoid_: channel, which collides with Update Channel; tunnel, which is ADR 0025's `Tunnel`; pipe, which is a named pipe. A **Forward** is one listener on the Client's machine for one port of one Device; every connection it accepts opens one Stream. The interface calls it a forward. _Avoid_: tunnel, port mapping. CONTEXT.md gains both entries with the implementation, as this repository does.

## The Stream connection

**Beside the terminal connection.** A Client opens one more connection to a Device, its Stream connection, and every Stream to that Device travels on it. The terminal connection does not change by one byte: its reliable queue, its visual slot (ADR 0004) and its writer's priorities never see Stream data. Three alternatives were declined.

- Multiplexing Streams inside the terminal connection is free to open on every connection method, Windows SSH included, but every Stream byte handed to the kernel is a byte the next keystroke and the next frame wait behind, and no user-space priority reaches into the kernel's send buffer. A 2 MiB burst costs 1.7 s at 10 Mbit/s; today's 16 MiB clipboard image costs about 13 s. Eternal Terminal multiplexes its forwards that way, and its issue "TCP tunnels can freeze terminal" stayed open for six and a half years, its maintainer's workaround being two connections. iTerm2 and kitty carry files inside the terminal's byte stream and pay with tiny requests or a blocked terminal.
- One connection per Stream gives every Stream its transport's own flow control, but a browser opens six to twenty connections per page. On Windows, where OpenSSH has no connection sharing, each would be a full SSH login, and sshd's `MaxStartups` would start refusing them. Orca, which did this for one-shot requests and `ssh -L` per forward, met repeated logins that a second factor cannot answer, a frozen main thread on every socket close and leftover processes holding ports, and is moving back.
- Native QUIC streams on Peer-to-peer would split the four connection methods into two implementations, and measured no better: a bulk stream on the same noq connection raised another stream's round trip from 34 µs to about 4 ms, `set_priority` notwithstanding, against about 80 µs from a second connection.

Orca, the closest tool in shape, runs its terminals on one connection and its forwarding traffic on another, each multiplexed inside with its own windows.

**On each connection method.** A TCP Device gets a second TCP connection and a second Noise handshake with the Device key, which needs no person. A Peer-to-peer Device gets a second `Tunnel` to the local Server, which dials a second QUIC connection; `Tunnel` itself is unchanged. An SSH Device gets a second `ssh -T … condr server bridge`. The GUI's must not share the terminal connection's TCP connection, so where Condr manages the ControlMaster (ADR 0022) that `ssh` gets none of Condr's multiplexing options and `ControlMaster=no` and `ControlPath=none` instead; OpenSSH takes the first value it reads for an option, so appending would not work. That is a second login with the key or agent that logged the terminal connection in under `BatchMode`. Where the person configured a `ControlPath` of their own, usually for a host with a second factor, the bridge rides their master, which shares one TCP connection (see What it does not fix). When the separate login fails, for a FIDO key that wants a touch, `MaxStartups`, a PAM login limit or any other reason, the GUI reports it under the Ports page's form or in a toast, naming the Device and ssh's reason, and does not fall back to Condr's master: two connections on one TCP connection are what this decision declines. A FIDO key may wait for its touch until ADR 0015's timeout. The CLI has no terminal connection to keep apart, so its Stream connection rides Condr's master as every other `condr --device` call does. A local Device's Stream connection is a second local socket.

**Lifetime.** In the GUI the Stream connection opens when the person starts the first forward or the first transfer to that Device, so a Device that cannot be reached for Streams says so at once, and closes when the last forward stops and the last transfer ends. It exists only while the terminal connection is up: when that connection is lost, disconnected or removed, the Stream connection closes with it and its Streams fail. While forwards remain and the terminal connection is up, a Stream connection that is lost or fails to open is reopened by itself: at once after the terminal connection's Bootstrap, else after 2 s, doubling to 30 s. The Device's forward cards say it is reconnecting and why the last attempt failed. A `Refusal`, from an older Server or a revoked Device, ends the retries and stays on the cards until the person forwards again. A transfer is not retried; a transfer whose Stream connection is lost fails. In the CLI the Stream connection is the process's only connection and lives as long as the command. It is registered in the Server's live peer table beside the terminal connection, so `RevokeDevice` closes it too. Retrying a failing SSH login every 30 s can trip a host's fail2ban; that is accepted.

**Handshake.** `ClientHandshake` gains a member, `streams`, carrying `StreamsHello { Hello hello = 1; }`. The Server applies `Hello`'s protocol range and logs its `client_name`, which is the only name a local or SSH connection has. As before, `Credential` or `Tunnel` precede it on a Peer-to-peer connection. The Server answers with an ordinary `Welcome` and then speaks Stream messages. It sends no Bootstrap and subscribes the connection to nothing. It does not count the connection as a Client, for the terminal sizes of ADR 0036 or in `condr server status`. It does not record the peer as seen, so `authorized-clients.json` is not rewritten and a Device's push setting (ADR 0047) is not overwritten by a connection that carries none.

**Older Servers.** ADR 0028 has a Client hide what the Server is too old for, and that needs a protocol number to compare; the protocol stays `1` until the release ADR 0041 names raises it. Until then Streams are not gated, as ADR 0059's request is not, though the mechanism differs: a Server older than this build reads `streams` as an empty `oneof` and refuses the handshake with `Refusal::Malformed`, closing the connection. The GUI shows "<Device> runs a Condr too old to forward ports or transfer files; update it", under the Ports page's form or in a toast, and stops retrying; the CLI fails with `feature_unavailable` naming the Device's build. The entries are not hidden beforehand. When the protocol is raised, Streams are gated with the rest.

**Messages.** The Stream connection keeps ADR 0028's framing, varint-delimited protobuf, with a pair of top-level messages of its own in a new `proto/condr/v1/stream.proto`, so `messages.proto` gains nothing:

- `StreamClientMessage`: `Open`, `Data`, `Credit`, `Finish`, `Reset`, `Ping`, `Close`.
- `StreamServerMessage`: `Opened`, `OpenFailed`, `Data`, `Credit`, `Finish`, `Reset`, `Pong`, `Close`.
- `Open { stream, target }`, where `target` is one of `forward_port`, `download` and `upload`. A file is named by a Workspace id and a `RelativePathBuf`; `upload` adds `replace`.

Only the Client opens Streams. It numbers them from 1 upward and never reuses a number on a connection. Each direction ends on its own with `Finish`, as a TCP FIN does, which forwarding needs for responses delimited by closing; a Stream is closed when both directions have finished. `Reset { error }` ends both at once. Any message for a Stream that was opened and has closed is ignored, `Data`, `Credit`, `Opened`, `OpenFailed`, `Finish` and `Reset` alike, since what was sent before a `Reset` arrives after it; a message for a number never opened is a protocol error and closes the Stream connection. Paseo's transfers broke on messages out of order (its issue #8392), so this rule is written down. `Open` is not a round trip: a Stream starts with its window in both directions, so a browser's request follows `Open` at once. The Server answers `Opened`, carrying a download's size, or `OpenFailed { error, detail }`, and drops whatever arrived for a Stream it did not open; since only Streams have windows, dropped bytes owe no credit to anything. `error` is an enum whose zero is `STREAM_ERROR_UNSPECIFIED` and whose unknown values decode to `OTHER`: `CONNECTION_REFUSED`, `NOT_FOUND`, `ALREADY_EXISTS`, `NOT_A_FILE`, `INVALID_PATH`, a path through `.git` included, `INVALID_PORT`, for 0 or above 65535, `WORKSPACE_GONE`, `TOO_MANY_STREAMS`, `IO`, `UNSUPPORTED`, `CANCELLED` and `OTHER`; `detail` is for people. Both top-level `oneof`s and `Open.target` only gain members. An `Open` whose target this Server does not know is answered `OpenFailed { UNSUPPORTED }`, and any other top-level message this build does not know is ignored; neither closes the connection, as ADR 0028 has unknown input do.

**Flow control.** Every Stream may have 1 MiB in flight in each direction; that is a protocol constant and the initial window. There is no window for the connection as a whole: with one, a few Streams whose consumers stopped reading, a paused video or a background tab's open request, would hold it and stall every other Stream. Memory is bounded instead by the number of Streams: a Stream connection holds at most 64, so a receiver buffers at most 64 MiB; the next `Open` fails with `TOO_MANY_STREAMS`, which a forward answers by closing the browser's new connection and which the GUI's transfer queue below never reaches. A receiver returns credit only as its consumer takes the bytes, one chunk ahead of the browser's socket write or the file write, so a slow consumer stops its sender reading from the source and the pressure reaches the program at the far end. `Credit { stream, max_offset }` is an absolute offset, "you may send up to byte N", which can be repeated and kept as only the latest value. Data beyond credit is a protocol error and closes the Stream connection, so no receive buffer ever exceeds its window. Data moves in chunks of at most 32 KiB, and the sender takes the Streams that have data and credit in turn, one chunk each. That turn-taking orders only what the sender has not yet handed to the transport: up to a Stream's whole window can already sit in kernel buffers and the network, so a browser's small request behind a download waits up to about 0.8 s at 10 Mbit/s, and longer behind several. There are no priorities: the terminal is not on this connection. A frame on the Stream connection is at most 64 KiB, a chunk and its header with room to spare, against the terminal connection's 2 MiB. Neither end's reader ever blocks on a consumer: it hands a chunk to that Stream's bounded buffer, at most its window, and the Stream's own worker writes the socket or the file. The Server's Stream buffers are counted apart from the terminal connection's queues; Orca dropped terminal output when its connections shared one budget. The Client sends `Ping` every heartbeat of the terminal connection, whatever else it sends, and the Server answers `Pong`, so each end hears the other at least that often even while data flows one way only, a server-sent event stream for one; three heartbeats of silence end the connection. No transfer has a deadline of its own, since an hour-long download is legitimate. An end that closes the connection sends `Close` last and the peer closes its own on hearing it, since a local socket or a Peer-to-peer tunnel cannot wake a read blocked on it; a peer too old to know `Close` ignores it and waits for the end of the transport.

1 MiB gives about 10 MB/s per Stream at 100 ms round trip and 35 MB/s at 30 ms, near noq's default of 1.25 MB; Orca's fixed 256 KB allowed 2.9 MB/s at 89 ms and was raised. Windows that grow with bandwidth were declined for now: they fill the bottleneck queue described next.

**What it does not fix.** Two connections on one network path still share its bottleneck. A transfer fills a router's queue with up to its window, and the terminal's packets wait behind it: barely noticeable on a fast link, up to about 0.8 s per active transfer on a 10 Mbit/s one, as an `scp` in another terminal would cause. Where the bridge rides the person's own master, or a Peer-to-peer connection goes through the Relay, both connections share one TCP connection and a busy transfer delays the terminal by seconds. On the Relay the transfer also counts against the Relay's per-client rate limit, which the terminal shares, and its bandwidth is Condr's (ADR 0026). Nothing is added for this now: no rate limit, no setting, no Relay-specific rule. The follow-up is a window that shrinks as the round trip grows over its idle value, LEDBAT's idea, which iTerm2 uses from 8 KiB up to 4 MiB, possibly with `TCP_NOTSENT_LOWAT` on the Stream connection's socket; it is built if the Windows acceptance under Delivery shows the round trip growing by more than 100 ms, which at 10 Mbit/s it likely will.

**Where it lives.** The Stream protocol, its flow control, the Forward and the transfers live in `condr-client`, so the GUI, the CLI and later the Companion use one implementation (ADR 0039). Dialling stays where ADR 0039 put it: `condr-server`'s `Endpoint` supplies the connector, which for the GUI's SSH Stream connection drops the multiplexing options and for Peer-to-peer sends a new `Tunnel`. Workers are std threads, as connections are: a Stream's worker writes its consumer, and a forwarded connection has one more thread reading its socket, so a full Stream connection runs about 130 threads. A worker that panics becomes its Stream's `Reset { OTHER }` and nothing else, as ADR 0053 has a thread that holds no lock drop only its own work. The data path takes no Server state lock: a transfer looks up its Workspace's Root Directory once, at `Open`. The GUI receives each transfer's progress as a latest-value slot that is overwritten rather than queued, reads it at most ten times a second and notifies only the views that show it, the transfer strip and the Ports page; Stream bytes never pass through its event channel.

## Port forwarding

**Who holds the listener.** The Client process that started a forward holds its listener: the GUI process for a forward the GUI started, one listener set for all its windows (ADR 0043), and the foreground `condr port forward` for one the CLI started, until Ctrl+C. No Server holds a forward, the local one included. Holding forwards in the local Server would let them outlive the GUI and be shared with the CLI, but it would make that Server a Client of other Servers, holding their connections and, for SSH, spawning `ssh` from a process that Autostart (ADR 0057) may have started without the person's agent or any way to answer a prompt. That is the federation ADR 0022 declined; ADR 0025's exception was forced by iroh's one endpoint per key, and nothing forces this one. VS Code and JetBrains likewise stop forwarding when their window closes, and Coder's and DevPod's CLIs forward for as long as they run. A forward belongs to the GUI's connection to its Device, not to a window: closing a detached Device window leaves it running. Only the process holding a forward sees it: the GUI and the CLI do not see each other's, other Clients see nothing, and the Server has no Forward, only the Streams it carries. The GUI offers no forwarding on the local Device, whose ports are already here.

**What it reaches.** A forward reaches the remote Server's own loopback and nothing else. `Open` carries a port, and the Server connects to `127.0.0.1:<port>` and then `[::1]:<port>`, since many dev servers listen on `::1` alone now that Node resolves `localhost` to IPv6 first. Forwarding to any `host:port` the Server can reach, into its network, is not offered; a person who wants that opens `ssh -L` or socat in a Pane. The local listener binds both `127.0.0.1:<port>` and `[::1]:<port>`. A port is free only when nothing on this machine answers a connection to it and both binds succeed; `[::1]` may be missing only when the system has no IPv6 loopback. A `[::1]` already in use makes the port taken, because a browser opening `localhost` would otherwise reach the other program. Binding to the local network is not offered. Every authenticated connection may forward, as ADR 0038 and 0045 let a paired Device do what a Pane already could.

**Lifetime.** While the GUI's connection to the Device is lost, whether the network dropped, the remote Server's Supervisor restarted it, the local Server restarted under a Peer-to-peer `Tunnel` or the GUI has given up and shows the Device's page, the listener stays bound, so its port and address stay. Connections through it close with the Stream connection; new ones are accepted and closed at once rather than queued; after the reconnect the Stream connection reopens by itself and the forward works again. Forwards are not persisted: quitting the GUI ends them all, and Disconnect, Remove or editing a Device's address ends those of that Device, with no record and no restore. A forward is not tested when it is created. When the remote port refuses a connection, the browser's connection is closed and the forward's card says its last connection was refused; there is no toast per connection.

**The Ports page.** Two buttons open it: **⇄ N** at the bottom of the left sidebar, beside its other buttons, for every Device in the window's scope, and **⇄** on the header of each remote Device, with that Device's count when it has forwards, for that Device alone, with "Show all Devices" on the page. It is a page of a window's content area, in the family of ADR 0020's connection pages and the Start Page, and not a Session Tab, since forwards live in the GUI and belong to no Workspace. Its scope follows the window's (ADR 0043): the main window shows every Device and a Device window its Device; a Tab window has no left sidebar and no entry. It covers the whole content area, the Tab strip included, where it shows "⇄ Ports", and the right sidebar. ✕, any Workspace in the sidebar and an activation that shows a Workspace (ADR 0021) leave it. The page has two columns. The left lists All Devices and then each remote Device with its count, a Device that is reconnecting marked so. The right holds the scope's form, with a choice of the Device to forward from under All once more than one remote Device is connected, the Device's port and an optional local port, and one card per forward: the Device's port and the Device, `http://localhost:<port>` as a link, the number of connections, and Open in Browser, Copy Address and Stop. While a Device or its Stream connection is reconnecting its cards are dimmed and say so, with the last reason. Without a local port, the local port is the Device's port when free, else the next free one up to twenty above, else one the system assigns, and a card whose port differs says so, "localhost:3000 was in use, so 3001 is used", as VS Code does. Everything that fails when the form is submitted shows under the form (ADR 0020): a local port given by hand that is taken, a Stream connection that cannot open, an older Server. Open in Browser opens `http://localhost:<port>`; there is no scheme choice, and a person who needs `https` copies the address. The page was chosen from prototypes: forwards listed under each Device in the sidebar crowded the projects, a Ports tab in the right sidebar was too far out of reach, and a count in the title bar sat in the wrong place.

**The CLI.** `condr --device <name> port forward <port>...` forwards one or more ports in one process over one Stream connection. `--device`, or `CONDR_DEVICE`, is required; the CLI cannot reliably tell that a saved Device is this machine, so it does not try. Each port is `REMOTE` or `LOCAL:REMOTE`, local first as in `ssh -L`; `condr --device box port forward 5173 8080:80`. Local ports are taken as written, because a script needs a known port: one that is taken, by the rule above, fails the command, and `0:REMOTE` lets the system choose. Once every listener is bound it prints one line, `{"forwards":[{"device":"box","remote":5173,"local":"127.0.0.1:5173"}]}`, and then nothing more on stdout while it runs; a refused connection is one line of text on stderr. Ctrl+C exits 0. A lost connection prints its reason on stderr and exits non-zero, without reconnecting: a script learns from the exit code.

## File transfer

**What moves.** Single regular files inside a Workspace's Root Directory, named by the Workspace id and a `RelativePathBuf`, in both the GUI and the CLI. A download follows `read_file`'s rules: a regular file, symlinks followed. An upload follows ADR 0045's `check_path`, and its target must be a regular file or not exist; a symlink is refused with `NOT_A_FILE`, since replacing it would turn the link into a file and writing through it could leave the Workspace. As in ADR 0045, these guard against mistakes and are not a security boundary. A download's name is checked on the Client against the Client's platform too, with the same rules ADR 0045 applies on a Windows Server, so `a:b.txt`, `CON` or `report.` from a Linux Server does not land in an alternate data stream or a device on Windows: the CLI then fails and asks for `<dest>`, and the GUI's save dialog suggests the name with those characters replaced by `_`. Directories are not transferred in either direction; an Agent can archive one first. Paths outside a Workspace are not offered either; that directory can be opened as a Workspace. There is no size limit beyond the disk, since both ends stream.

**Writing.** The Server writes `.<name>.condr-upload-<random>` beside the target, so the final step stays on one filesystem, shortening `<name>` when the whole would pass 255 bytes, and holds no lock while it does. When the Client finishes, the Server takes ADR 0045's mutation lock for the final step alone: it checks the path and the target again, `sync_all`s the temporary file and places it. Without `replace` it places by `hard_link` onto the target, which fails if anything appeared there since `Open`, answering `Reset { ALREADY_EXISTS }`, and then removes the temporary name; on a filesystem without hard links it renames after checking under the lock, which only another program can race. With `replace` it copies the old file's permission bits, its Unix mode or its Windows read-only flag, and renames over it; hard links and ownership are not kept, and on Windows a rename that meets a sharing violation, from an antivirus or an indexer opening the new file, is retried for up to a second before it fails as in use. It then publishes one `WorkspaceFilesChanged` and Git refresh, as every ADR 0045 mutation does. Saves, renames and deletes elsewhere therefore never wait on a transfer. The Git watcher ignores the temporary names, so a long upload does not refresh every Client's Files and Changes over and over. On failure, cancellation, a full disk, a lost connection, a closed Workspace, a stopped Server or a revoked Device the Server deletes the temporary file, and the original is untouched. An Agent therefore never reads half a file under its real name. This differs from ADR 0045's save in place on purpose: a save that fails leaves the whole text in the editor, an upload that fails would leave nothing. A download is written the same way beside the destination the person chose, and replacing an existing destination was already asked by the save dialog. A file open in a Preview Tab and replaced by an upload meets ADR 0045's conflict on its next save.

**Completion and progress.** `Opened` carries a download's size, a guide for progress only, since an Agent may be rewriting the file; the Stream's end decides. The Client counts progress itself: bytes written for a download, bytes handed to the Stream for an upload, which run at most a window, 1 MiB, ahead of what the Server wrote. An upload is complete when the Server, after its final step, answers the Client's `Finish` with its own; a failure is `Reset` with the error. A download is complete when the Client, after its own, answers the Server's `Finish`. Only the Client that started a transfer can cancel it, with `Reset { CANCELLED }`; other Clients do not see it. A lost connection fails the transfer and nothing retries it; resuming is not offered.

**In the GUI.** Download… is on a file's context menu in Files and in Changes, where it takes the working tree's version and is disabled on a deleted row, and on a Preview Tab's context menu in the Tab strip. History has none, since a past version is a Git object and not a file on disk; a directory has none either. Upload is a drop from the system file manager onto a directory row, onto a file row for that file's directory, as ADR 0045's New File is, or onto the space below the tree for the Root Directory, the row highlighting as the drop target, and Upload Files… on the context menu of a directory or that space, which opens the system's picker with several files allowed. A download opens the system save dialog in the directory last used this run, Downloads the first time. Files dropped or picked together are one batch. The GUI checks the batch against the target directory's listing, which Files fetches if it is folded, and asks about the names already there in one dialog, Replace or Skip These, Skip for one; the Server's `ALREADY_EXISTS` remains the guard, and a file that meets it anyway fails with a toast. The batch's transfers then queue: at most four run at once to a Device, the rest wait in the strip. A folder in a drop is refused with a toast saying only files can be uploaded and to archive it first, while the batch's files proceed. Progress collects in a strip at the bottom of the right sidebar, under whichever of Changes, Files and History it shows: hidden with nothing to show, one line such as "⇅ 2 transfers · 45%" while transfers run or wait, unfolding into a row per file with its direction, bar and ✕, then "⇅ 2 finished" until Clear. It lists this Client's transfers in this Workspace. A finished download raises a toast with ADR 0045's reveal action, Reveal in Finder, Reveal in File Explorer or Open Containing Folder; every failure raises one with its reason (ADR 0020); a finished upload says so in the strip alone. With the right sidebar closed a transfer runs on and its toast still comes; the sidebar does not open by itself. Quitting while transfers run or wait asks once whether to cancel them. A local Device offers the same entries with the same behaviour and goes through the same Stream connection, so ADR 0045's checks, its write lock and `WorkspaceFilesChanged` are never bypassed. The strip was chosen from prototypes over progress drawn inside the tree and a toast per transfer, as simpler and in one place.

**The CLI.** `condr --device <name> file download <path> [<dest>] --workspace <id> [--replace]` and `condr --device <name> file upload <file> <path> --workspace <id> [--replace]`. `--device`, or `CONDR_DEVICE`, is required as for `port forward`, since without it the CLI would only copy within this machine, and so, by the existing rule, is `--workspace`. The words match the interface; `get` and `put` would read like `workspace get`, and `cp` would need a way to write a Workspace into `host:path`. `<dest>` defaults to the file's name in the current directory, under the name check above. An existing target, remote or local, fails with `already_exists` unless `--replace` is given. A directory fails. While stderr is a terminal one line there shows the file, bytes done of total and the speed; otherwise nothing. The result is JSON on stdout, `{"download":{"path":"report.pdf","dest":"/Users/me/report.pdf","bytes":50331648}}` or `{"upload":{"source":"./hero.png","path":"public/hero.png","bytes":6291456}}`. Ctrl+C cancels and removes the temporary file; the CLI gains a Ctrl+C handler for it, through `nix`'s signals on Unix and `SetConsoleCtrlHandler` on Windows, a `windows-sys` feature rather than a new crate. Failures use the CLI's error format and a non-zero exit.

**Clipboard images stay where they are.** Moving ADR 0012's images onto the Stream connection was considered and declined: pasting an image is a frequent, quick gesture, and opening a Stream connection for it, a second login on SSH, is heavy for it. Its cost stays: on a slow link a large image holds back the keys after it, about 13 s for 16 MiB at 10 Mbit/s and under a second for a screenshot of a few hundred kilobytes.

## Authority

Every authenticated connection may open Streams, Local, SSH and paired TCP and Peer-to-peer Devices alike, under ADR 0038's rule: a paired Device can already run `nc`, `cat` or `curl` in a Pane, so refusing it guards nothing. When `observe` and `control` exist, opening a Stream needs `control`. The security model does not change. SECURITY.md gains a paragraph with the implementation: a forward binds only the loopback and reaches only the Device's loopback; while it runs, any process on the Client's machine, other users' included, can reach the forwarded port through it, as with `ssh -L`; forwarding through `condr server bridge` is not governed by sshd's `AllowTcpForwarding`, `PermitOpen` or `DisableForwarding`, any more than socat in a shell is; and opening a Stream takes the same rights as typing into a Pane. Its scope list gains nothing about leaving a Workspace, since those checks are not a boundary.

## Observability

`condr server status` reports one more count, `streams`, the Streams open now, and its text output one more aligned line, `Streams       N open`; `clients` does not count Stream connections. Nothing per Stream is reported; which ports and files are the Client's affair and on its screen. Logging follows ADR 0019: `info!` for a Stream connection opening and closing, with its Device or `client_name` and its reason; `warn!` for a protocol violation and for the Server failing to read or write a file; `debug!` for each Stream opening and closing, with its port or Workspace-relative path, so paths appear only there; `trace!` for chunks and credit. The GUI logs nothing more than it shows.

## Not in this decision

Port detection, finding the ports a Pane's process tree listens on and showing them, is its own roadmap item; it calls this forwarding when a detected port is clicked. Forwarding to arbitrary hosts, binding the listener to the local network, reverse forwarding from the Server, UDP, persisting forwards across GUI runs, transferring directories, paths outside a Workspace, resuming or synchronizing transfers, transfers between two remote Devices, dropping a file onto a remote terminal to upload it and paste its path as Paseo does, the Companion's forwarding and transfer, and larger previews in the Preview Tab are all left out. The design keeps the Companion open: it would use `condr-client`'s Stream connection.

Consequences:

- **A second connection per Device.** A TCP Device sees a second handshake, a Peer-to-peer Device a second QUIC connection, an SSH Device a second login from the GUI unless the person's own master carries it; each happens when the first forward or transfer starts. A failing SSH login is retried up to every 30 s while forwards remain.
- **Slow links.** A transfer on a slow link delays the terminal by the bottleneck's queue, up to about 0.8 s per active transfer at 10 Mbit/s, and by seconds where both connections share one TCP connection, the person's own master or the Relay.
- **The Relay.** Transfers that cannot go direct cross Condr's Relay, at Condr's bandwidth and under its per-client limit.
- **Temporary files.** During an upload `.<name>.condr-upload-<random>` sits beside its target, visible in Files and to `git add -A`; a Server killed outright leaves it behind.
- **Older Servers.** They refuse the Stream connection, and the person learns it when they first try, not from a hidden entry.
- **Forwards end with the GUI.** Quitting, Disconnect, Remove and editing the Device end them, and the person forwards again next time.
- **Clipboard images.** Unchanged, with ADR 0012's cost on slow links.

Tests:

- **The terminal is untouched.** A Stream whose consumer never reads, on the Client and on the Server in turn, leaves the same Client's terminal output arriving at cadence, its keys reaching the Pane and another Stream on the same connection flowing. The four terminal performance tests AGENTS.md names, burst coalescing, the final frame, unchanged cells not reshaped and real GPUI drag-selection, pass unchanged. An ignored benchmark, run like `terminal_wire_bench`, reports the keystroke echo's p50 and p99 on loopback with and without a concurrent 1 GiB download, for observation without a gate.
- **Flow control and protocol**, in `condr-client` and core. A Stream's 1 MiB window holds, data beyond credit closes the connection, and repeated or reordered `Credit` is harmless. Five Streams whose consumers never read leave a sixth flowing. Any message for a closed Stream is ignored and one for a never-opened Stream closes the connection. The 65th Stream fails with `TOO_MANY_STREAMS`, port 0 with `INVALID_PORT`, and an unknown `target` answers `UNSUPPORTED` without closing, as an unknown top-level message is ignored. A slow Stream does not hold back a fast one, and after one direction's `Finish` the other still flows. A worker's panic resets only its Stream.
- **Writing files.** An upload onto an existing file without `replace` answers `ALREADY_EXISTS`, and so does a target created by another program between `Open` and `Finish`, which is left untouched. `replace` replaces a file, keeping its permission bits, and refuses a symlink. The temporary file is synced before it is placed. Cancellation, a failed write, a closed Workspace and a lost connection each remove the temporary file and leave the original. A Save of another file completes while an upload runs. The Git watcher does not report the temporary file. A path through `.git` and a directory are refused. A download's name that Windows cannot hold is refused on Windows.
- **Local port choice.** The same port, then up to twenty above, then the system's; a port whose `[::1]` another program holds, or that answers a connection, counts as taken.
- **End to end, on Local, TCP over Noise loopback, the SSH bridge and Peer-to-peer over `Network::Loopback`.**
  - Forwarding: a round trip to an echo server; a response delimited by closing arrives whole; a refused port answers `CONNECTION_REFUSED`; while the terminal connection is down the listener stays bound and new connections close at once, and after the reconnect the Stream connection reopens and the forward works.
  - Transfers: a download and an upload round trip.
  - Lifetime: the Stream connection opens with the first forward or transfer and closes with the last, closes with the terminal connection and on `RevokeDevice`, and is reopened with backoff while forwards remain, until a `Refusal`. A simulated older Server's `Malformed` becomes `feature_unavailable` in the CLI and a message under the GUI's form. The handshake leaves `authorized-clients.json` and the push setting alone.
  - CLI: `port forward` prints its line once bound, `0:` lets the system choose, a taken local port fails, a missing `--device` fails, and a lost connection exits non-zero. `file download` and `file upload` work with `--replace`, fail with `already_exists` without it, and fail on a directory. Ctrl+C removes the temporary file.
- **GUI**, with `gpui-kit/test-support`. The Ports page opens for the window's scope from the sidebar's button and for one Device from its header; the local Device and a Tab window have no button; activating a Workspace leaves the page. A changed local port is noted and every failure of the form shows under it. A batch whose names exist asks once, at most four transfers run per Device, a dropped folder is refused, the strip unfolds and clears, progress repaints at most ten times a second, and quitting with transfers running asks.
- **By hand, on Windows.** A Linux Server limited with `tc qdisc … tbf rate 10mbit`, reached over TCP, over SSH and over Peer-to-peer forced through the Relay, sends a 1 GB download, and then four transfers at once, while a Pane runs Codex streaming and animating and another window pings the Server. Typing, scrolling, drag-selection and the frame rate are observed, and the ping's growth over idle is recorded. Unlimited, nothing may feel slower than without a transfer. At 10 Mbit/s, growth up to 100 ms passes; more starts the delay-based window above.
