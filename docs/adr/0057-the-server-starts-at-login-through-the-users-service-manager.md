# The Server Starts at Login Through the User's Service Manager

Status: accepted 2026-11-02. Builds on ADR 0016, whose installed copy it registers and whose file list gains `condrw.exe`, and ADR 0031, whose desktop-shell launch a login item keeps; takes "Server 开机自启" off the roadmap. A crashed Server is restarted by its Supervisor (ADR 0058), not by the service manager; a graceful stop on SIGTERM was considered and left out.

A Server restored from its Snapshot brings back the Session and resumes Agent Conversations (ADR 0005), but after the machine restarts nothing starts it. Only opening the GUI or an SSH Client's bridge does. TCP, Peer-to-peer and the Companion cannot reach the Device until then, which hurts most on a headless Device and on a machine paired with a phone. Autostart registers `condr server start` with the current user's own service manager: a systemd user unit on Linux, a LaunchAgent on macOS and a value under the `HKCU` `Run` key on Windows. It is off until a person turns it on. It runs as that user, through the layer each platform has for a user's own programs. A system service was rejected: a systemd system unit, a LaunchDaemon or a Windows service needs root or an administrator to install, and runs outside the user's login session. The programs in a Server's Panes are that user's interactive tools and need that session. An Agent CLI's login opens a browser, and Claude Code on macOS keeps its token in the login keychain. A Windows service runs in session 0, with no desktop, clipboard or browser, either as LocalSystem or with the user's password stored by the service manager. Windows offers third parties no per-user service manager, so on Windows a login item is that layer. VS Code's tunnel service registers the same three: a systemd user unit, a LaunchAgent and a `Run` value. The Task Scheduler was rejected too: a boot trigger there needs an administrator, and a task that runs before anyone logs on puts the Server in session 0, away from the desktop shell ADR 0031 parents it under.

The service manager triggers the Server once and does not supervise it. It runs `condr server start`, which returns once the Server answers, by which point the Server has already called `setsid`. On systemd the unit is `Type=oneshot` with `RemainAfterExit=yes`. On launchd it is `RunAtLoad` without `KeepAlive`. Letting the service manager supervise a foreground `condr server run` was rejected because Condr already owns the Server's lifecycle. VS Code's tunnel service does that with `Restart=always` and `KeepAlive`, but it has no restart of its own to collide with. The GUI's Restart, the one its update dialog sends too, makes the Server start `condr server restart` as its own child. Once the old Server exits, systemd would kill everything left in the unit's cgroup and launchd everything in its process group, so the helper and the Server it starts would die with it. `condr server stop` and `restart` from a terminal would also have to go through `systemctl` or `launchctl` to keep the supervisor's view right. Restarting a Server that crashed is the Supervisor's job (ADR 0058), the same for every Server however it was started, and Windows has no service manager that could do it. On systemd the Supervisor, the Server and its Panes live in the unit's cgroup, so `systemctl --user stop condr-server` ends them. `systemctl --user status` reports `active (exited)` whatever the Server is doing, so `condr server status` is the command to ask. The Server handles no SIGTERM and skips its final Snapshot flush there, as it already does at shutdown. The cwds and resume references it records continuously lose only their last few moments.

On Linux, turning Autostart on also runs `loginctl enable-linger`, on a desktop as much as on a headless machine. Without linger, the user's service manager starts at the first login rather than at boot. It stops at the last logout and takes the Server with it. logind then removes `/run/user/<uid>`, which holds the Server's socket and bind lock. If linger cannot be enabled, for example because polkit wants a password the session cannot give, nothing is registered and the command prints what to run instead. Condr writes the unit and the `default.target.wants` link that `systemctl --user enable` would make, then reloads a running user manager if there is one. So turning Autostart on needs no user bus, only systemd as init (`/run/systemd/system`). The unit ignores a failing `start` (`ExecStart=-`). `start` gives up after about a second and a half, and a Server that restores many Panes on a cold boot can take longer. A oneshot unit that fails ends everything in its cgroup, the Server it was starting included. Turning Autostart off removes the unit and leaves linger alone. A person may have enabled linger for other services, and nothing on the machine records whether Condr enabled it. A machine without a systemd user manager is told Autostart is not supported there.

On macOS the CLI writes `~/Library/LaunchAgents/dev.condr.server.plist`. `SMAppService` was rejected because it needs the plist inside an app bundle, and a Mac with only the CLI has none. Turning Autostart on only writes the file, because `launchctl bootstrap` would run a `RunAtLoad` job immediately. Turning it off only deletes the file: the job loaded at this login has already run, and without the file it is not loaded again. macOS 13 and later show a "Background Items Added" notification when the file appears. Turning the item off under System Settings › General › Login Items leaves the file, and Condr cannot read that switch, so it still reports Autostart on. That is the one place the two can disagree.

On Windows the `Run` value `Condr Server` holds `"<dir>\condrw.exe" server start`. Explorer runs it at login, so the Server finds the desktop shell to parent it under (ADR 0031). Task Manager's Startup page and Settings › Apps › Startup turn an item off by marking it under `StartupApproved\Run` and leave the `Run` value. Condr reads that mark as off, and turning Autostart on clears it. `condr.exe` is a console program, and Windows gives it a console window before any of its code runs, so launching it directly would flash a window, or a Windows Terminal window, at every login. `condrw.exe` is a second binary built from `condr-server` for the GUI subsystem. It runs the `condr.exe` beside it with `CREATE_NO_WINDOW`, waits, and returns its exit code. It ships wherever `condr.exe` does, the way the ConPTY files do (ADR 0056): `condr server install` writes it, `uninstall` removes it, and Setup and the release archive include it.

launchd and systemd hand the Server an almost empty environment. A Pane's shell is not a login shell, and `install` puts `~/.local/bin` on PATH through the login profile (ADR 0016). A Server started at login would therefore give its Panes no Homebrew and no `~/.local/bin`, so no `claude` or `codex`. The GUI already adopted the login shell's environment for itself before starting a Server. That capture moves into `condr-server`. On Unix, `spawn_server`, the one place a local Server is spawned, lays it over the caller's environment for every Server it spawns, whoever asked: the GUI, `condr server start` and `restart`, the SSH bridge, or the Server's own restart helper. `CONDR_*` variables and test endpoints still come from the caller, whatever the profile exports. The environment is captured once per process, and a restart captures it before stopping the old Server, so the profile does not lengthen the time without one. The probe shell runs in a session of its own. Started from a terminal, `zsh -i` would otherwise make itself that terminal's foreground group, which takes Ctrl-C away from the caller, and let a prompt theme draw there. The GUI keeps adopting it for itself and still keeps a terminal's environment when launched from one. The Server's environment no longer depends on who started it, the Unix counterpart of ADR 0031. A Server that an SSH Client's bridge starts now gets the login environment instead of the one `ssh` gives a remote command. Every test that spawns a Server runs the login shell. Windows needs none of this, since a Pane's environment already comes from the registry.

`condr server autostart [on|off] [--json]` turns Autostart on or off and shows its state when given neither. Turning it on registers only, so it takes effect at the next login, or the next boot on Linux; `condr server start` serves now. It registers the `condr` that this process would start a Server from (`resolve_server_executable`). From the CLI that is the CLI itself. From the macOS GUI and the AppImage it is the installed copy in `~/.local/opt/condr`, and from the Windows GUI it is the `condr.exe` beside it. Every channel replaces that file in place, so an update keeps the registration valid. Turning it on again rewrites the registration to the current path. `install` never registers anything: installing should not change what runs at login, and the install scripts need no new flag. `uninstall` turns Autostart off before it removes the binary, when Autostart starts that binary; one that starts another `condr`, such as a development build, is left alone. Setup's uninstall runs `condr server autostart off` with no window. Whether Autostart is on is read from the unit, plist or `Run` value itself and never stored in `config.toml`, so only the macOS switch above can disagree with what will actually run. `condr server status` shows `Autostart` with the registered path, and `autostart: {enabled, path}` with `--json`, whether or not the Server is running.

In the GUI, this machine's Settings › General carries a "Start Condr at login" switch, "Start Condr at boot" on Linux. Like "Restart Condr", it never says Server. It calls the same code in-process, so no protocol message is added. A failure is a toast (ADR 0020), and the switch then shows what the login item says. A remote Device shows "Run `condr server autostart on` on that device" in the switch's place. Changing what runs at every login on another machine would need a new message and its authorization, and that machine's own CLI does it already. A disabled switch would have to show a state this window cannot read. Setup gains no checkbox, since the switch is a click away.

Tests: the unit, plist and `Run` value are each generated by a pure function and checked as text, together with the `autostart` command's parsing and `status`'s JSON. Registration with the real service managers is checked by hand on each platform: after a reboot or a new login the Server answers. On Windows no window appears at login. A Pane's PATH holds Homebrew and `~/.local/bin`.
