# TCP Endpoints Authenticate Like WireGuard

Every TCP connection to a Condr Server is one `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` handshake followed by encrypted transport records, implemented with the `snow` crate. The model is WireGuard's: each side holds a persistent X25519 static key, the Client already knows the Server's public key before it connects, and the Server answers only peers whose static key it recognises. There is no separate plaintext or loopback-only path; a loopback listener behind an SSH tunnel authenticates the same way, which also closes the hole that any local user could reach an unauthenticated loopback port.

The Server host keeps its identity in the configuration directory (`CONDR_CONFIG_DIR` overrides it): `server-key` is the Server's static key, `client-key` is the device key that the `condr` CLI and a GUI on the same host connect with, and the Server always accepts that host key. Other devices appear in `authorized-clients`, one `key paired-at name` line each. A peer with an authorized key uses the all-zero pre-shared key, as an unconfigured WireGuard peer does, and its first handshake message already proves it holds the private key.

Pairing a new device uses the pre-shared key slot. `condr server invite` writes one invite secret with a ten-minute expiry to `pending-invite` and prints `<server key>.<secret>@<host>:<port>` for the person to paste into the GUI's Add Server dialog. A Server that does not recognise the Client's static key answers with the pending invite as the pre-shared key; only a Client holding the same secret can decrypt the second message and produce a valid first transport message, so the Server records the device in `authorized-clients` after it has read the Client's `Hello` and before it sends `Welcome` or any Bootstrap data. Recording happens under the store lock and only if the invite the connection handshook with is still the pending one, so the first device to finish wins, a second holder of the same secret is refused, and a handshake made with an older invite cannot consume a newer one. The invite is deleted on success, and a new `condr server invite` replaces the old one. A Client that still holds an invite after a successful pairing, because the connection broke before it saw the Bootstrap, is refused the invite handshake and retries once as a paired device. Before a TCP connection is served the Server also re-reads the authorized list under the same state lock the revocation scan takes, so a device revoked between its handshake and its `Hello` is refused instead of slipping past the scan. `condr server clients` lists devices and `condr server revoke <key prefix>` removes one: it edits the file first, so the device's next handshake fails whether or not a Server is running, then connects to the Server at the given endpoint as the host and sends `RevokeDevice`, which closes every live connection of that key. Only a local connection or a TCP peer speaking with the host's own device key may send that message; a paired remote device gets an error. The Server and CLI serialize edits to the store through `identity.lock`.

The GUI keeps its device key beside `config.toml` and stores each TCP Server as name, address and Server public key; the invite is carried in memory only until the first successful connection, then dropped. A GUI whose device key cannot be read or created reports that and offers no TCP Servers at all, rather than connecting with a predictable key, and it leaves the saved list untouched. On Unix a key or invite file readable by other users is refused instead of trusted. A Pane's `CONDR_SOCKET_PATH` for a TCP Server is `tcp://<server key>@host:port`, and the CLI inside the Pane connects with the host's `client-key`. Error text and `Debug` output show public keys and addresses but never private keys or invite secrets.

The handshake runs on the connecting thread at first use rather than on accept, so a slow or hostile peer cannot stall the accept loop, and it stays inside the existing handshake timeout. Transport records carry at most 64 KiB of ciphertext; the framed protocol above is unchanged and clones of a stream share one transport state so the reader and writer threads keep their separate nonces in step.

Deferred from the roadmap's M3 list: storing the device key in an OS keychain, capability-based authorization, rate limiting, audit logging, and a GUI pairing flow beyond the text dialog. The pattern string and the store format are the only things such work changes; the record layer and handshake driver stay.
