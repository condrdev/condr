# Each Client Owns Its View

Which Workspace and which Tab a client shows is that client's own state. The Session, its Snapshot and the events that carry them describe structure only: Workspaces in order, their Tabs in order, each terminal Tab's Pane layout and the Pane that has focus inside it. `Session::active_workspace` and `Workspace::active_tab` are gone, from the domain, from the wire and from the persisted Snapshot.

Before this, "the active Workspace" and "the active Tab" were part of the Session, so they were global. Every `LayoutChanged` event carried them, every client applied them, and clicking a Tab sent `ActivateTab` to the Server and waited for the round trip. Two GUIs on the same Server, the development setup of a Windows laptop and a Linux Server being the everyday case, could not look at different things: one person's click moved the other's window. The GUI had grown a pending-selection layer to hide the round trip and to hold the locally chosen Tab against an authoritative Snapshot that pointed elsewhere; that layer, its acknowledgement tracking and its supersession rules are gone with the state they compensated for.

The GUI keeps its view per connection: the shown Workspace and, for each Workspace, the shown Tab. Selecting either is immediate and sends nothing. A choice that no longer exists falls back to the first Workspace or Tab, and when a `LayoutChanged` event removes the shown Workspace or Tab the view moves to the one that took its place, else the last, as browser tabs do. A Bootstrap reconciles the same way, so a reconnect to the same Session keeps the user where they were while a stale id degrades gracefully. The GUI opens on the first Workspace; remembering the last shown one across GUI restarts is a client preference that can be added when it is missed. What this client asks the Server for, it shows: `LayoutApplied` names the created Workspace, the created Tab, the shown diff or file, and for `OpenWorktree` on an already open worktree the new result `WorkspaceOpened`, and the requester moves its view to that. Other clients see the structure change and nothing else.

`ActivateWorkspace` and `ActivateTab` remain as the one way to reach into other clients' views, because that is what an agent wants when it says "look here". They validate their target, change no Session state, and are published to every subscriber as `SessionEvent::Activated { workspace_id, tab_id }`; each GUI switches its own view to the target and makes that connection the active one. The `condr` CLI's `workspace focus` and `tab focus` send them, `--focus` on `workspace create` and `tab create` sends one after the creation, and `pane focus <id>` sends `FocusPane` followed by `ActivateTab` for the Pane's Tab, since Pane focus is Session structure but showing the Tab is each viewer's decision. `FocusPaneDirection` and the GUI's own Pane clicks send `FocusPane` alone, so browsing panes never pulls another window along. The `focus` field left `CreateWorkspace` and `CreateTab`; `SplitPane` keeps it, as it means the server-side Pane focus, and a split without focus restores the Tab's previous focus, history and zoom. With no active Tab to inherit from, `CreateTab` takes `cwd_from: Option<PaneId>`: the GUI passes the focused Pane of the Tab it shows, the CLI its own Pane when that is in the target Workspace, and the new shell starts there, else in the Workspace root.

The CLI's JSON lost `focused` on Workspaces and Tabs and `active_tab_id` on Workspaces, since there is no such fact on the Server; `focused_pane_id` on a Tab stays. `condr tab create` without `--workspace` now requires running inside a Pane, where `CONDR_PANE_ID` names the Workspace; the fallback to "the active Workspace" had no meaning left.

Two alternatives were declined. Keeping a per-subscriber view on the Server, so the Bootstrap could carry "your view", would have made the Server remember something only the client uses and would have needed a durable client identity to survive reconnects; the client remembers it itself at no cost. Broadcasting `Activated` for every command with a focus intent, including the GUI's own creations and Pane clicks, was declined because a person creating a Tab on one machine must not move the other machine's window; only an explicit activation does.

ADR 0001 stands: `condr-core` owns structure, and the GUI projects the Tab it shows into the Dock. ADR 0005's Snapshot no longer holds active selections; focus history stays. ADR 0009's "preserves the selection at commit time" is now about Pane focus only, and its list of viewer state the controller owns gains nothing: the view is not controller state either, it is every client's own. ADR 0010 still carries the structure in every event; the view is simply not in it. ADR 0017 and 0018's viewer Tabs are shown by the client that opened them, not activated on the Server. The Snapshot and protocol version constants stay at 1, as ADR 0005 says: the project is unreleased and old Snapshots are simply rejected at startup.
