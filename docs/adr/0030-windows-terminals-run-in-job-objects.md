# Windows Terminals Run in Job Objects

On Windows every Terminal's shell runs in a Job Object of its own, and the Job, not the process table, says which processes belong to the Terminal. This amends ADR 0005: on Windows, stopping "the ConPTY descendant tree with bounded escalation" becomes terminating the Job, and process discovery no longer walks parent PIDs.

Until now Windows rebuilt the tree from a sysinfo snapshot by following each process's parent PID up to the shell. Windows keeps a dead parent's PID on its children and soon hands that PID to a new process, so a new shell could look like the parent of an unrelated orphan. On the Windows CI runner such orphans (`explorer.exe`, `sihost.exe`, `ctfmon.exe`, `vctip.exe`, runner processes) were claimed and killed: a Pane close failed with "terminal process tree did not exit after forced shutdown", and one run hung until GitHub dropped the job with its log. A birth-order check (a parent never starts after its child) stops the misattribution, but the walk still loses a process whose intermediate parent exits (`cmd /c start`, a launcher that returns), loses every descendant once the shell itself has exited, races with processes started after the last scan, and enumerates the whole process table on each poll. Unix has none of this: portable-pty makes the shell a session leader, the kernel records session membership, and orphans are reparented to init.

A Job is created per Terminal with `CreateJobObjectW` and null security attributes, so its handle is not inherited and no child can keep it open. Its limits are `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE | JOB_OBJECT_LIMIT_BREAKAWAY_OK` and nothing else; UI restrictions would stop the Job from nesting inside one the Server already runs in, which Windows 8 and later otherwise allow and ConPTY's minimum of Windows 10 1809 guarantees. The shell is assigned with `AssignProcessToJobObject` on the handle portable-pty returns (`Child::as_raw_handle`) as soon as `spawn_command` returns. portable-pty does not create the process suspended, so a child the shell starts in those first microseconds would escape; pwsh and cmd take hundreds of milliseconds before they start anything, and the code marks this ceiling and its upgrade, creating the process inside the Job through `PROC_THREAD_ATTRIBUTE_JOB_LIST`, which needs a change to portable-pty. A failed assignment is a failed Terminal start, reported like any other spawn error; there is no fallback to the parent-PID walk. The runtime shares the Job handle with the probes it hands out; closing or dropping the runtime terminates the Job, and the end of the Server process closes the last handle.

Everything started in a Terminal belongs to it until it leaves the Job on purpose with `CREATE_BREAKAWAY_FROM_JOB`, the counterpart of `setsid` or `nohup` on Unix. Closing a Pane, Tab or Workspace, removing a Managed Worktree, and stopping or restarting the Server all end in `TerminalRuntime::close()`, which on Windows calls `TerminateJobObject` and waits, bounded, until the Job's active process count is zero; a timeout reports the processes still running. When the shell exits on its own, the existing exit path closes the runtime the same way, so what it left running ends with it, as Unix already does for the session's remaining members. When the Server exits, crashes or is killed, the closed handle ends every Terminal's tree; ADR 0005 already starts a fresh shell in every Pane of a replacement Server, and nothing expects a Pane process to outlive its Server. A GUI program started from a Pane ends with the Pane unless it breaks away, where before its fate depended on whether its launcher was still alive. Shutdown stays forced only: Windows sent nothing but a kill before this change, and a graceful phase (closing the pseudoconsole or sending `CTRL_CLOSE_EVENT` first) is a separate decision.

The other readers of the tree use the Job's member list from `QueryInformationJobObject(JobObjectBasicProcessIdList)` instead of the process table. The idle-shell check before `agent start` treats any member other than the shell as busy, which is what "any descendant" meant before. Agent identification reads command lines only for members; choosing the topmost Agent among them still follows parent PIDs and keeps the birth-order check, since a member's stale parent PID can name a newer member. The Windows parent-PID walk for shutdown and the idle check, the per-process kill loop, and the Windows-only retry that reused recorded identities are removed. `condr-core` calls the Job APIs through its existing `windows-sys` dependency with the `Win32_System_JobObjects` feature and whatever that API's signatures pull in; `windows_spawn::Job`, which `condr-server` uses for SSH, can neither assign a process it did not spawn nor list members, so it is not reused here.

Linux and macOS keep sessions. Linux cgroup v2 would also catch processes that call `setsid`, and `pidfd` would remove the signal-time PID race, but cgroups need a systemd user session or a writable cgroup subtree that headless hosts, containers and WSL often lack, and macOS has no public equivalent; [the research](../research/windows-job-object-process-tree.md) records the comparison.

Not in scope: a graceful shutdown phase on Windows; a notion of foreground that would let a background process leave the shell idle; creating the shell inside the Job at `CreateProcessW`; per-Terminal resource limits; cgroups on Linux.

Tests cover an orphan older than a reused parent PID staying outside the tree, and on Windows: a Job listing and terminating a tree, and ending it when its last handle closes; a sleeper that the shell started in a console of its own before exiting, which no live parent or pseudoconsole ties to the Terminal, ending when the exited Terminal is closed; a helper that left with `CREATE_BREAKAWAY_FROM_JOB` surviving the close; and the idle check treating a background member as busy. Windows CI runs the full workspace suite, where the forced-shutdown timeout and the hang first appeared.
