# Settings Are Organized by Device

Status: accepted 2026-10-09. Replaces the Settings window's Application and Device tabs. Extends ADR 0029's one dependency exception and replaces its sentence on proxies.

Settings had two tabs: Application, this Client's `[client]` preferences, and Device, the `[server]` preferences of one Device picked in its header, edited over the protocol. A setting that every Condr process on a machine needs fits neither. The first is the proxy, which both the Server's relay connection and the GUI's update check go through: under Application a remote Device's proxy cannot be set, and under Device the person whose update check fails does not look for it and is not told it applies to the GUI as well.

The window loses its tab bar. One Device picker heads it, with this machine first and selected whenever the window opens: it holds the most pages, and the About page the update dot points at is its own. The sidebar shows the pages of the picked Device, arranged by topic rather than by which process reads a setting. This machine has General, Appearance, Notifications, Power, Shortcuts, Network, Remote access, Paired devices, Agent integrations, Developer, Licenses and About. A remote Device has General, Network, Remote access, Paired devices and Agent integrations, with the GUI's items left out and a page they leave empty hidden, so every connected Device opens on General. Where it is not obvious that a setting reaches the whole machine, its description says so; there are no badges. A Device that is not connected keeps its connection state in the header, as ADR 0020 places it, and its pages are hidden rather than shown with stale values; when that Device is this machine, the GUI's own pages stay. A tab per Device was declined because tabs overflow and come and go with connections, and one sidebar listing every Device's pages because Kit's Settings sidebar is a flat list without section headings.

A machine-wide setting has one value per machine, read by every Condr process on it: the Server, the GUI and the CLI. A layered value, a GUI default that a Server overrides or the reverse, was declined: nobody could tell which one applies. In `config.toml` the section says who reads a key: `[client.*]` the Clients, `[server.*]` the Server, and any other top-level section every process. Such a section is named by its topic, as `[network]` is, never `[common]`.

Machine-wide settings are written through the machine's Server, for this machine exactly as for a remote one. `ServerSettings` carries them, so they arrive in the Bootstrap and in `ServerSettingsChanged` to every Client. `SetServerSettings` changes from the whole `{ shell }` to one field per message, a oneof, so a Client never sends back a field it may not change, and the Server checks each field on its own. Machine-wide settings are administration by default, accepted only over the local socket, which SSH reaches through the bridge (ADR 0013, ADR 0015); over TCP and Peer-to-peer they show under the existing "Viewing only" (ADR 0020). A field harmless enough can be opened to every Client by itself, as the shell is. The GUI applies a machine-wide value from its local connection's settings, and reads a value it needs before that connection exists once from the file at startup. The CLI reads the file on every run and gets no command to change settings. Letting the GUI write this machine's file directly was declined: it would be a second writer, and the Server would not learn of the change without a file watcher, which nothing in Condr has. A change applies at once where it can; where it cannot, the page shows the saved and the running value with Restart, as Remote access does for `[server] listen`.

The proxy is the first machine-wide setting: `[network.proxy] mode = "system" | "none" | "manual"` and `url`, with `system` the default. Mode and URL are separate keys so that leaving Manual and coming back keeps the URL.

- `system` means the same in both processes: the `HTTPS_PROXY` family and `NO_PROXY`, the Windows Internet settings in the registry, and the macOS system configuration. The GUI's reqwest already does this. The Server drops its own environment lookup for hyper-util's `Matcher::from_system()`, asked for the relay's URL. hyper-util is already in the build through iroh's reqwest, and enabling its `client-proxy-system` feature adds `windows-registry`, which the GUI already builds, and on macOS `system-configuration` 0.7 beside the GUI's older one. Reading the environment alone was declined, because tools that set the system proxy, Clash among them, write only the registry, and a Server installed as a service sees no shell's environment. Neither process runs PAC scripts.
- `none` means no proxy in either process, whatever the environment says.
- `manual` means `url`, which must be `http://` or `https://`: iroh's relay client speaks HTTP CONNECT to a plain or TLS proxy and has no SOCKS. The URL may carry `user:password@`, and a blank one under Manual means no proxy. It is validated beside the field, as the Listen address is (ADR 0020), and again by the Server. Broadcasting it, credentials included, to paired Devices exposes nothing new, since a paired Device can already read `config.toml` from a Pane. Logs name only host and port.

The Server's iroh endpoint takes its proxy when it is built, and applying a change at once would mean rebinding it and dropping every Peer-to-peer connection. A change therefore applies on the next Server start, like `[server.p2p] enabled`: `Status` reports the running mode and URL beside the saved ones, and the page offers Restart while they differ. The GUI applies a change at once by building a new HTTP client and setting it on the App. GPUI's `ReqwestClient` cannot turn system detection off, since `proxy_and_user_agent(None)` is detection. So the GUI builds its `reqwest::Client` itself in all three modes, with `use_preconfigured_tls(tls_config())` for the crypto provider ADR 0029 describes, and converts it with `From`. That means declaring `gpui-pre-reqwest` and `gpui-pre-http-client-tls` beside `gpui-pre-reqwest-client`, at the versions Kit pins in `Cargo.lock`. ADR 0029's one exception to declaring only `gpui-kit` becomes these three crates. Settings shows the proxy on its own Network page, apart from Remote access, which is about who may reach this Device, whereas Network is about how this machine reaches out. The page has a Select of System, None and Manual, and the URL field appears only under Manual.

Tests:
- The Server accepts a machine-wide field over the local socket, refuses it over TCP, and still accepts the shell from there.
- One field's `SetServerSettings` leaves the others as they were, and `ServerSettingsChanged` reaches every Client.
- `none` ignores `HTTPS_PROXY`, `system` reads it and honours `NO_PROXY`, and `manual` refuses `socks5://` and a malformed URL, both beside the field and at the Server.
- `Status` reports a saved proxy that differs from the running one.
- In the GUI:
  - the picker opens on this machine;
  - this machine shows the GUI's pages beside the device pages, and a remote Device shows only the device pages;
  - a disconnected Device hides its pages, except this machine's GUI pages;
  - the URL field shows only under Manual;
  - the HTTP client is rebuilt when this machine's proxy changes, and not when a remote Device's does.
