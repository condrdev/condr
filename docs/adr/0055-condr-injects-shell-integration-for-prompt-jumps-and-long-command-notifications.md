# Condr Injects Shell Integration for Prompt Jumps and Long-Command Notifications

Status: accepted 2026-10-29. Builds on ADR 0051, whose libghostty-vt tracks OSC 133 prompt marks, and ADR 0054, whose notification path a finished command shares; takes OSC 133 prompt navigation off ADR 0051's "left for later". Selecting a command's output and marking a failed command in the gutter were considered and left out.

libghostty-vt knows where each prompt, command and output begins once the shell marks them with OSC 133, and can scroll the viewport by prompts. Plain zsh and bash mark nothing, so for most people none of it would work. Ghostty, VS Code and WezTerm solve this the same way: the terminal loads a small script into the shell it starts. Condr does too.

**What the shell sends.** At each prompt the script sends `133;D;<exit status>` for the command that just ended (not before the first prompt), then `133;A`. As a command starts it sends `133;C`. It never touches the prompt string, so a framework that redraws the prompt (powerlevel10k, starship) keeps working, and the end of the prompt (`133;B`) goes unmarked, which neither feature needs. bash sends `133;C` through `PS0`, so bash before 4.4, macOS's own included, marks prompts but not commands.

**How it gets in.** The Server writes the scripts, embedded in `condr-core`, into `shell-integration/` beside its socket, in the runtime directory, at every start. A test Server's lands in its own temporary directory, and an update rewrites them. A Pane's shell finds them through the variable it reads its startup files by:
- zsh: `ZDOTDIR` points at Condr's directory, whose `.zshenv` puts the person's `ZDOTDIR` back (passed as `CONDR_USER_ZDOTDIR`, or unset), reads their `.zshenv`, and in an interactive shell adds a `precmd` and a `preexec` hook. zsh then reads the person's `.zshrc` from the restored `ZDOTDIR`, and hooks added there run after Condr's, so Condr's sees the command's own exit status.
- bash: the rc file Condr already wraps bash in, for the cwd it reports on exit, sources `~/.bashrc` and then the script, which puts its function first in `PROMPT_COMMAND`. That wrapper now runs on every Unix, not only Linux.
- fish: Condr's directory goes in front of `XDG_DATA_DIRS`, with fish's defaults behind it when the variable was unset. The script in its `vendor_conf.d` takes the directory off again and adds `fish_prompt`, `fish_preexec` and `fish_postexec` handlers.

Programs the shell starts inherit none of these variables. Windows and PowerShell get no integration yet, and neither does any other shell. A shell that marks its prompts itself works without it.

**The setting.** `[server.terminal] shell_integration`, on unless set to `false`, is a Server setting: `ServerSettings.shell_integration` and `ServerSetting::ShellIntegration`, under Settings › General › Terminal. Like the shell, it applies to Panes started afterwards, and any Device may change it, since it decides nothing about who reaches the machine.

**Prompt jumps.** Cmd or Ctrl with Up or Down jumps the viewport one prompt back or forward, but only while the cursor sits at a marked prompt, which libghostty-vt reports (`CURSOR_AT_PROMPT`). That is false without marks, while a program runs and on the alternate screen, so vim, an Agent or a shell without integration still gets the key. The Server decides, as it does for Shift+PageUp, so the protocol and the Client need nothing new. The Shortcuts page lists Cmd on macOS and Ctrl elsewhere; the Server takes either everywhere.

**Long-command notifications.** The PTY reader notes when `133;C` starts a command, and at its `133;D` reports one that ran at least ten seconds as `SessionEvent::CommandFinished { pane_id, exit_code, duration_secs }`. A command during which the Agent probe saw an Agent in the Pane reports nothing: its Agent's own states (ADR 0024) already told the person, and quitting a long Claude Code session must not announce a finished command. The GUI posts it like a program's notification (ADR 0054): under the notifications switch, only when the person is not looking at the Pane, tagged with the Pane, and titled "Command finished" or "Command failed with exit code N", with how long it took. The Companion ignores it for now.

Tests: zsh and bash in a home of their own read the person's startup files, restore `ZDOTDIR`, clear Condr's variables and define the hooks; Cmd+Up and Cmd+Down move the viewport by prompts in both; prompt marks report command starts and ends with their exit codes, and the viewport scrolls by prompts and finds no prompt on the alternate screen; a long command reports, a short one, one an Agent ran in and an end without a start do not; the Server publishes it; the GUI words it; the setting loads on by default, saves, crosses the protocol from a paired Device, and reaches a new Pane's environment only while on. fish is not installed on the development machines, so its script has had no run yet.
