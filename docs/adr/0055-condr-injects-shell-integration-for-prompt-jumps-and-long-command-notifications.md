# Condr Injects Shell Integration for Prompt Jumps and Long-Command Notifications

Status: accepted 2026-10-29. Builds on ADR 0051, whose libghostty-vt tracks OSC 133 prompt marks, and ADR 0054, whose notification path a finished command shares; takes OSC 133 prompt navigation off ADR 0051's "left for later". Selecting a command's output and marking a failed command in the gutter were considered and left out.

libghostty-vt knows where each prompt, command and output begins once the shell marks them with OSC 133, and can scroll the viewport by prompts. Plain zsh and bash mark nothing, so for most people none of it would work. Ghostty, VS Code and WezTerm solve this the same way: the terminal loads a small script into the shell it starts. Condr does too.

**What the shell sends.** At each prompt the script sends `133;D;<exit status>` for the command that just ended (not before the first prompt), then `133;A`. As a command starts it sends `133;C`. It never touches the prompt string, so a framework that redraws the prompt (powerlevel10k, starship) keeps working, and the end of the prompt (`133;B`) goes unmarked, which neither feature needs. bash sends `133;C` through `PS0`, which bash before 4.4, macOS's own included, does not have; a prompt mark without a command mark leaves libghostty-vt taking every program the shell starts for its prompt, so that bash gets no marks at all.

**How it gets in.** The Server writes the scripts, embedded in `condr-core`, into its data directory, which is private to the person and never cleaned up behind it, in a directory named for the scripts' content: written whole beside it, then renamed into place, so a shell never reads half a script, and a build with other scripts gets a directory of its own. A shell gets the integration only while the scripts are still there, since zsh pointed at a directory without Condr's `.zshenv` would read none of the person's startup files. A Pane's shell finds them through the variable it reads its startup files by:
- zsh: `ZDOTDIR` points at Condr's directory, whose `.zshenv` puts the person's `ZDOTDIR` back (passed as `CONDR_USER_ZDOTDIR`, or unset), reads their `.zshenv`, and in an interactive shell adds a `precmd` and a `preexec` hook. zsh then reads the person's `.zshrc` from the restored `ZDOTDIR`, and hooks added there run after Condr's, so Condr's sees the command's own exit status.
- bash: the rc file Condr already wraps bash in, for the cwd it reports on exit, takes `CONDR_BASH_INTEGRATION` out of the environment, sources `~/.bashrc` and then the script, which puts its call first in `PROMPT_COMMAND`. The call checks the function exists, since a `PROMPT_COMMAND` the person exports reaches nested shells without it. That wrapper now runs on every Unix, not only Linux.
- fish: Condr's directory goes in front of `XDG_DATA_DIRS`, with fish's defaults behind it when the variable was unset. The script in its `vendor_conf.d` takes the directory off again, unsetting the variable when Condr supplied the defaults, and adds `fish_prompt`, `fish_preexec` and `fish_postexec` handlers.

Programs the shell starts inherit none of these variables. No shell on a Windows Server gets integration yet, PowerShell included, and neither does any shell but these three. A shell that marks its prompts itself works without it. Known limits: an `/etc/zshenv` that sets `ZDOTDIR` itself skips Condr's `.zshenv`, which leaves zsh without integration, as it does in Ghostty; a nested shell that marks its own commands, such as one reached over ssh, ends the outer command with its own marks.

**The setting.** `[server.terminal] shell_integration`, on unless set to `false`, is a Server setting: `ServerSettings.shell_integration` and `ServerSetting::ShellIntegration`, under Settings › General › Terminal. Like the shell, it applies to Panes started afterwards, and any Device may change it, since it decides nothing about who reaches the machine.

**Prompt jumps.** Cmd or Ctrl with Up or Down jumps the viewport one prompt back or forward, but only while the cursor sits at a marked prompt, which libghostty-vt reports (`CURSOR_AT_PROMPT`). That is false without marks, while a program runs and on the alternate screen, so vim, an Agent or a shell without integration still gets the key. The Server decides, as it does for Shift+PageUp, so the protocol needs nothing new. The Client passes Cmd+Up and Cmd+Down on, the only Cmd chords without a binding it does, and in legacy mode Cmd still types nothing, so away from a prompt a program gets nothing for them unless it reads the kitty keyboard protocol. The Shortcuts page lists Cmd on macOS and Ctrl elsewhere; the Server takes either everywhere.

**Long-command notifications.** The PTY reader notes when `133;C` starts a command, and at its `133;D` reports one that ran at least ten seconds as `SessionEvent::CommandFinished { pane_id, exit_code, duration_secs }`. A command during which the Agent probe saw an Agent in the Pane reports nothing: its Agent's own states (ADR 0024) already told the person, and quitting a long Claude Code session must not announce a finished command. The GUI posts it like a program's notification (ADR 0054): under the notifications switch, only when the person is not looking at the Pane, tagged with the Pane, and titled "Command finished" or "Command failed with exit code N", with how long it took. The Companion ignores it for now.

Tests: zsh and bash in a home of their own read the person's startup files, restore `ZDOTDIR` whether the person set one or not, keep Condr's variables from the person's files and the programs they start, and define the hooks, bash only from 4.4; Cmd+Up and Cmd+Down move the viewport by prompts in both, and a running command keeps them; the GUI passes Cmd+Up and Cmd+Down to the Server and no other unbound Cmd chord; the scripts install once per content, a removed script is put back, and a shell gets no integration while one is missing; prompt marks report command starts and ends with their exit codes, and the viewport scrolls by prompts and finds no prompt on the alternate screen; a long command reports, a short one, one an Agent ran in and an end without a start do not; the Server publishes it; the GUI words it; the setting loads on by default, saves, crosses the protocol from a paired Device, and reaches a new Pane's environment only while on. fish is not installed on the development machines, so its script has had no run yet.
