# A Workspace Above Several Repositories Shows Each One

A common way to work is to keep several repositories under one directory and hand that directory to an agent. Git was discovered upward from the Root Directory only, so such a Workspace had no Changes and no History, and the right sidebar was left with Files. Now, when the Root is in no repository, the Server takes every directory right under it whose own top is a work tree, `.git` being a directory or a file, so a linked worktree placed there counts too. It follows symlinks as Files does, skips no hidden directory, and sorts them by name. A bare repository, a deeper one and a submodule are not taken. A Root inside a repository shows that one alone, as before, and repositories nested in it stay unseen. One repository right under the Root is shown the same way as several. Following the focused Pane's directory instead was declined: the sidebar would jump whenever an agent changes directory, and it would hide what the agent changed in the other repositories.

Every Git path on the wire is relative to the Root, as the Diff and Preview Tabs' already were: Changes entries, a commit's files and every diff and old-file request name `api/src/lib.rs`, and the Server finds the repository by the leading directory. `GitRepository` keeps where its work tree sits under the Root and where the Root sits in its work tree, and converts at its own methods, so the Server and every Client handle one kind of path and the Diff Tab needs no repository beside its path. This also settles a Root below its work tree's top, which listed repository-relative paths that Files, the Preview's change marks and the row actions then read as Root-relative ones: Changes and a commit's files now show only what is under the Root. History still lists every commit.

It is a view only. A Workspace above several repositories has no Base Branch, since each repository would have its own and the one comparison row cannot name them; it cannot create a Managed Worktree, and it is not a Task's repository (ADR 0068). One Workspace keeps one Root Directory; making a worktree in each repository for one piece of work waits for a real need.

`WorkspaceGitSnapshot` keeps its fields for the repository the Root is in and gains `repositories`, each with the same fields plus its `directory`, filled only when the Root is in none. Its top-level `changes` is then present and empty, so a 0.2 Client still decodes it and shows the Workspace detached with no changes. A Client reads one list, the Root's own repository being the entry with an empty directory. `GitLog` and `GitCommit` gain `repository`, that directory; an older Server ignores it and never has such a Workspace. Replacing the message's fields instead was declined although Condr is unreleased: a newer Client meets an older Server right after an update and on a remote Device, and it would lose Git there without any error.

The watcher stays one per Workspace, its Root watched recursively (ADR 0017). A scan rediscovers the repositories and walks the status only of those a changed path under them, a moved ref of theirs or a forced refresh touched; a path that no repository ignores but none contains changes Files only, and a `.git` that appears right under the Root brings a new repository. Each repository keeps its own fingerprint, and its own cap of `MAX_GIT_CHANGES`. There is no limit on how many repositories there are; the first scan of a Root above a hundred of them is slow, and that waits for someone to meet it.

Changes looks as IntelliJ's Changes view does with several roots. The sections stay outermost; inside each, a repository with changes in that section is a node with its name, how many files it holds there and its branch as a tag, and its directory tree follows. Folding a chain of lone directories into one row stops at that node. A repository with no changes is not listed, and its branch is in History. IntelliJ's colour per root is left out. A Root inside a repository shows no node, as before. The Workspace's row in the left sidebar says how many repositories there are, without the ahead and behind counts. History's first row becomes a menu of the repositories, each with its branch, and the chosen one's ahead and behind counts beside it; the choice is each Client's own, per Workspace, and is not saved. Files dims what each repository ignores and marks directories holding changes, and Changes is the default view, as for a Workspace inside a repository.

Tests: in `condr-core`, finding the repositories under a Root (a linked worktree, a symlink, a bare repository and a plain directory beside them) and converting paths both ways, including a Root below its work tree's top; in the Server, a scan that touches one repository leaves the others' status alone, a repository cloned under the Root appears, a diff, an old file, a log page and a commit are answered from the repository a path or `repository` names, and Files dims by the right repository's rules; on the wire, a multi-repository snapshot round-trips and one without `repositories` reads as the Root's own repository; in the GUI, Changes draws a node per repository that folds its tree alone, and History switches repository.
