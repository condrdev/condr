# One Device, One Key

A Device has exactly one persistent key, an Ed25519 seed stored as `device-key` in the identity directory beside `config.toml`. Its public key, written in hex as keys are today, is the Device's only fingerprint: it is what `condr server invite` prints, what another Server records in `authorized-clients`, what `condr server clients` lists and `condr server revoke` removes, what the GUI shows for a paired Device, and, once Peer-to-peer connections exist (ADR 0026), the Device's network identity as well, since iroh's endpoint id is the same 32 bytes. The same key identifies the machine whether its Server is being connected to or its GUI or CLI connects out, so one machine appears exactly once in any authorized list, one pairing admits it over TCP and Peer-to-peer alike, and one revocation removes the whole machine.

Before this a machine held two X25519 keys: `server-key`, which its Server answered TCP connections with, and `client-key`, which its GUI and CLI presented when connecting to other Servers. The split had no purpose beyond history: nothing ever needed the connecting side and the answering side of one machine to be distinguishable, and the split would have turned into a visible defect the moment a Device's fingerprint appeared in more than one place. The files are replaced, not migrated; the project is unreleased. Everything that held an X25519 key becomes unusable with it: a Server creating `device-key` for the first time discards its `authorized-clients`, whose lines could never match again, and every `tcp://<key>@host:port` saved in `[[client.servers]]` has to be added again, since the old key is not this Device's fingerprint. Both stores keep their names and line formats; only the key inside changes.

TCP still runs `Noise_IKpsk2_25519_ChaChaPoly_BLAKE2s` (ADR 0011) with X25519 static keys, so the Noise key is derived from the Ed25519 seed rather than stored: the private scalar is the first 32 bytes of SHA-512 over the seed, clamped, exactly the scalar Ed25519 itself uses and what libsodium's `crypto_sign_ed25519_sk_to_curve25519` returns; the public key is the Edwards point mapped to Montgomery form with `EdwardsPoint::to_montgomery` from `curve25519-dalek`. Both `curve25519-dalek` and `sha2` are already in the dependency tree. `StaticKey` becomes that derived view. Using one key pair for Ed25519 signatures (iroh's TLS) and X25519 key agreement (Noise) is a deliberate cross-protocol reuse; it is the reuse libsodium exposes the conversion for, analysed as safe for this pairing of schemes (Thormarker, "On using the same key pair for Ed25519 and an X25519 based KEM", 2021), and it is what makes one fingerprint possible.

A Noise IK responder learns only the initiator's X25519 static key, and the Montgomery form does not determine the Ed25519 key, since the sign of the Edwards coordinate is lost. `authorized-clients` stores Ed25519 keys, so the two directions are handled separately. To check authorization the responder maps each authorized Ed25519 key to Montgomery form and compares with the peer's static key; a line that does not decompress to a valid point is no match, not an error that refuses every peer. To pair, the Client puts its Ed25519 public key in `Hello`, and the Server accepts it only if its Montgomery form equals the static key the handshake authenticated, so a peer cannot pair a key it does not hold; the Ed25519 key is what `complete_pairing` writes. From the moment a match or a verified claim exists, the connection's remote identity is the Ed25519 key, so `last-seen`, the live peer table (`tcp_peers` today, one table for every remote transport) and `RevokeDevice` all compare in one key space. `tcp://<id>[.<invite>]@host:port` therefore carries the Ed25519 fingerprint, the same `<id>` a `p2p://` address carries. One machine's GUI and CLI both present the same X25519 key as Noise initiators while its Server uses it as responder; Noise IK, like WireGuard, is built for one key in both roles, and each TCP connection is an independent handshake, so any number of processes on one machine may connect at once.

Peer-to-peer connections cannot share a key that way. In iroh the connecting side is an iroh endpoint with a key too, and a key may live in only one iroh endpoint at a time: when a second one with the same id reaches the relay, the relay routes to the newcomer and the earlier one keeps its socket but silently receives nothing more (`iroh-relay`'s `Clients::register`; the client side logs one warning). A GUI, a CLI invocation and a Server on one machine each binding an iroh endpoint would therefore either knock each other out or need a key each, and a key each would put one machine into a remote Server's authorized list several times. So the Server is its machine's only iroh endpoint. A GUI or CLI that wants a Peer-to-peer Device connects to its own local socket and sends `Tunnel { id, invite }` as the first frame. The local Server dials that id, opens one QUIC connection per `Tunnel`, sends the remote Server the `Credential` frame carrying the invite when there is one, and from then on splices bytes both ways: the Client's next frame is the remote `Welcome`, or one `Error` from the local Server if the dial failed because the id did not resolve, the relay was unreachable or the remote refused, after which the local connection closes. Only a local connection may send `Tunnel`; a TCP, SSH or Peer-to-peer peer that sends it gets an error, since otherwise any paired Device could use this machine as a hop under its key. The Client side of a tunnelled connection is a local socket, so the framed protocol, its reader and writer threads, `Bootstrap` and reconnection are unchanged, except that the Client waits for `Welcome` with the inactivity timeout SSH uses rather than the local one, as the dial includes a lookup, a relay connection and hole punching. `condr --device` on a Peer-to-peer Device sends `Tunnel` to its own Pane's Server when it runs inside one, else ensures the machine's default Server as the GUI does and uses that.

The iroh endpoint is bound when `[server.p2p] enabled` is set or when the first `Tunnel` arrives. With `enabled` off it is released sixty seconds after the last Peer-to-peer connection closes and publishes nothing, so a machine that only connects out never holds a standing relay connection and never appears in the DNS zone; with `enabled` on it stays bound and published for as long as the Server runs. Connecting out never requires accepting in. TCP and SSH keep connecting directly from the GUI and CLI: routing them through the local Server would add a dependency on it and buy nothing.

This narrows the boundary ADR 0022 drew when it declined federation because "a Server proxies another" would put remote credentials and connections into a process that outlives the person's intent. The local Server still holds no credential but its own machine's key, owns no remote Session, and applies no policy to the bytes it forwards; it is the machine's network endpoint, as `tailscaled` is for its machine. A process that can reach the local socket could always read `client-key`, so what a `Tunnel` grants is what that process already had. ADR 0013's boundary stands: a Server serves only its own Session, and a Peer-to-peer connection is authorized by the remote Server exactly as a TCP connection is. ADR 0011's handshake, record layer and store rules are unchanged; only the key it identifies a Device by is now derived. CONTEXT.md's Device and Invite entries change with the implementation, as this repository does.

Two alternatives were declined. Keeping two keys per machine and sharing `client-key` between GUI and CLI fails as described: one `condr --device` call while the GUI is connected breaks the GUI's relayed path. A key per process, with the machine key signing per-process certificates that a remote Server verifies, is a certificate scheme invented only to avoid routing through the local Server, and it would change the authorized-list model for every transport.
