# Errors Are Shown Where They Belong

The GUI had one `app_error` string on `Condr` and one `error` string per connection, and every failure went into one or the other: a config file that would not save, a device that could not be reached, a Server that refused a layout request, a clipboard image that was too large, an address typed wrong in a dialog, and the fact that another Condr window held control of a Session. Whatever was last written was drawn as small red text at the right end of the Tab strip or at the bottom of the Welcome page, truncated to one line, never cleared, impossible to copy. A device that could not be reached showed the Welcome page with two of its three "Get started" actions greyed out and no explanation. This record decides which kinds of trouble the GUI distinguishes, where each is shown, and what the user can do from there. It follows a survey of three desktop products that also orchestrate coding agents across machines (Superset, Orca, Paseo), which agree on every point below.

Four kinds are distinguished, and each has exactly one home. A *connection state* is a lasting fact about one Device: not connected, connecting, reconnecting, and why. It belongs to that Device and is shown on it: a mark on the Device's heading in the sidebar that tells the reason on hover and connects on click, and, when the Device is the active one, either a dedicated page or a pill over its Workspace, described below. A *failed operation* is a one-off event: a config file that could not be written, a layout request the Server rejected, an admin command it refused, a clipboard image that could not be converted or was too large, a folder picker that would not open. It is reported once through `Condr::report_error`, which raises a red toast in the main window that stays until dismissed and carries a Copy button, because GPUI text cannot be selected and an error nobody can paste into an issue is an error nobody can act on. A *validation failure* belongs to the field it concerns and is drawn under it, inside the dialog or beside the Settings input, until the value is fixed; the dialog callbacks return `Result<(), String>` for this and never touch shared state. A *mode* is not an error at all: a Session another Client controls is viewable, and the Tab strip says so in the muted colour with "Viewing only", not in red. Two states that used to share the connection's `error` field got their own: `control_denied` for the mode, and nothing for a Bootstrap or subscription the Server rejected on the way to a resync, which recovers by itself and is only logged. The Server's own recent warnings and errors stay on the Daemon settings page, which exists to show them.

The active Device's body depends on its connection state before anything else. A connected Device without Workspaces shows the Welcome page, and there every action is available; the Welcome page is for getting started and never carries a failure. A Device that is not connected and has nothing open shows a page of its own: a title in the Device's name ("Can't reach jpdev", or "Connecting to…" and "Reconnecting to…" with a spinner), one sentence on what to do, the raw reason in full with a Copy button, and Connect and Edit device. The sentence comes from a small table keyed on the wording the connect path already produces: nothing listening, no answer, unreachable, refused, closed, the local Server failing to start, SSH reaching the machine but finding no Server, and SSH failing outright. The raw text is always shown under it, because the table will never cover every case and the sentence must never replace the evidence. While the GUI is connecting or reconnecting on its own the page shows the spinner and hides the previous reason, so a stale failure is not read as a fresh one.

A Workspace whose Device drops keeps its Panes in place, because their frozen output is what the user was waiting on, and shows the state as a pill centred over them: a spinner and "Reconnecting to…" while the GUI retries, then a red dot, "Disconnected from…", a Details button and Connect once it gives up. Details opens a popover with the same sentence, raw reason and Copy button as the page. The pill appears only after a two-second grace from the moment the connection dropped, so a blip that heals inside it is never seen; the dot's colour follows the settled verdict, never the raw transport state, so it is never red under a spinner. The full-width banner that previously reflowed the Tab strip is gone.

Two things are declined. A global Save or an Apply model for Settings was declined in favour of text fields that commit on blur or Enter with a Save button while dirty, because every other setting is a switch or a choice where the click is the whole intent, and a page-level dirty state across several Servers would have to solve partial failure and discard prompts for no gain. And errors are never encoded by colour alone or reduced to an icon: the mark in the sidebar has a tooltip, the pill has Details, the toast has the text. What remains open and is not decided here: humanising the reasons the Server itself produces for rejected requests, escalating the pill's wording by retry count the way Orca's mobile client does, a diagnostics bundle for issue reports, and inline reporting of a failed config write beside the field that caused it rather than as a toast.
