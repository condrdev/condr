# Changes Can Compare Against the Base Branch

The Changes sidebar and the Diff Tab compare the working tree against one of two things: `HEAD`, as ADR 0017 has it, or the Workspace's base, which is the merge base of `HEAD` and the Workspace's base branch. Against the base the list holds everything the branch changed since it forked, committed or not, and nothing the base branch gained since. Agents in Managed Worktrees commit as they go, and against `HEAD` each commit drops its files off the list; reviewing a worktree before removing it is a question about the branch, not about the last commit.

When Condr creates the branch of a Managed Worktree, it records the parent Workspace's branch at that moment as the worktree's base branch. `create_worktree` makes the new branch from the parent's `HEAD`, so the parent's branch is where it forked. The name lives on the Worktree Association beside the parent Workspace and is persisted with it in the Session Snapshot (ADR 0005). It is a branch name, not a commit: a branch rebased onto a newer `main` compares against the new fork point, and a branch already merged into its base shows only what is still uncommitted. Nothing is recorded when the worktree checks out a branch that already existed, when the parent's `HEAD` is detached, or when an existing worktree is opened, since none of those says where the branch forked. A Workspace without a recorded name, or whose recorded branch no longer exists, falls back to the repository's default branch: `refs/remotes/<remote>/HEAD`, which `git clone` writes, for the only configured remote or else `origin`; failing that a local `main`, then `master`. A Workspace has no base when its `HEAD` is unborn, when no merge base exists, or when the base branch is the current branch itself or its upstream. The main repository Workspace on `main` is the everyday case of the last: against itself the view would only repeat `HEAD`'s.

Three alternatives were declined. Recording the fork commit freezes it, so after a rebase the base view would show the base branch's new commits as the branch's own. The remote default branch alone is wrong for a branch forked from another feature branch, and a Condr worktree forks from the local branch, which may be ahead of its remote. Storing the name in Git configuration, for example as the branch's upstream, would change what `git pull` and `git push` do, and Condr writes no Git configuration. ADR 0017 also sketched a view that switched by itself, uncommitted changes for a dirty tree and the branch for a clean one; that hides the commits exactly while an agent is midway, so the choice is the person's.

The Server computes the base list in the same pass as the branch, upstream and `HEAD` list, keeping ADR 0017's one function and one event: `WorkspaceGitChanged` gains an optional `base` beside `changes`, holding the base branch's display name (`main`, `origin/main`) and its list, and a reconnecting client gets it with its Bootstrap. Both lists share one walk of the working tree. Only the tree-to-index comparison runs a second time, against the merge base's tree, and its results fold into one status per path exactly as for `HEAD`: untracked files are listed, renames are tracked, and the 1000-entry cap and the 1 MiB diff limit apply to each list. Line counts are the cost that grows, because a long-lived branch's base list can hold hundreds of files and every refresh diffs each of them again; if that shows in the refresh time, they get cached by the base blob and the file's size and modification time. The fingerprint that decides whether to recompute also watches the base branch's ref, so a fetch that moves `origin/main` past a merged branch refreshes the view.

`DiffBase` gains `MergeBase` (`DIFF_BASE_MERGE_BASE`). The request still names only a path: the Server resolves the base from its latest snapshot of that Workspace, takes a renamed file's old path from the base list, and diffs the file at the merge base against the working tree. `DiffBase` has no fallback value, so ADR 0028 requires the new value to be gated, and the gate is the `base` field itself. A Server older than this never sends it, so the GUI never offers the base view on that Device and never sends `MergeBase` to it; the protocol version stays where it is. An older GUI ignores the field and goes on comparing against `HEAD`.

Which comparison a Workspace's Changes shows is the client's view, like the shown Tab (ADR 0021): a two-way control in the Changes header, `HEAD` and the base branch's name, kept per Workspace and remembered in the GUI state file (ADR 0023). The Diff Tab follows the same choice for its Workspace, and its header names what it compares against. The Diff Tab's Session content stays `Diff { path }`; the client puts its own choice into each `GitDiff` request, so two clients on one Diff Tab can compare differently and nothing about the choice enters the Session or its Snapshot. A Workspace starts on `HEAD`, which is what the sidebar showed until now. A Workspace without a base disables the control and compares against `HEAD`, keeping the remembered choice for when a base appears.

Not in this decision: picking an arbitrary base branch by hand, which can be added per Workspace once the automatic choice proves wrong in use; the CLI, which has no change list today; worktree setup and cleanup scripts, which the roadmap leaves to the person or the agent.

ADR 0017 stands except for `against` accepting only `HEAD` and its self-switching sketch. ADR 0002's Worktree Association gains the base branch name. ADR 0023's state file gains one choice per Workspace.

Tests: base resolution in order (recorded name, the default remote's `HEAD`, `main`, `master`, none, and none for the base branch itself or its upstream); a recorded base followed through a rebase; a branch merged into its base listing only uncommitted files; a committed file absent from the `HEAD` list and present in the base list; a rename across a commit diffing against its old path; the recorded name surviving a Snapshot round trip; the control disabled when `base` is absent.
