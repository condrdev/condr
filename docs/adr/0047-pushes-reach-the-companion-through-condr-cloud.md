# Pushes Reach the Companion Through Condr Cloud

Status: accepted 2026-10-21. Supersedes the roadmap's encrypted `detail` and ADR 0040's note that encrypting the payload stays the plan: pushes are plain text and the Companion has no notification extension. Amends ADR 0011 and ADR 0025, whose `authorized-clients` becomes `authorized-clients.json`; ADR 0033, whose move out of the configuration directory still moves it by its old name; ADR 0028, whose first Client hint in `Hello` is `push`; and ADR 0039, whose shared framework for an extension loses its trigger.

A Companion that is not in the foreground holds no connection (ADR 0040), so an Agent that finishes or waits for its person can reach the phone only through APNs or FCM. Their credentials cannot ship inside every user's Server, so Condr runs a service that holds them: Condr Cloud. A Server asks Condr Cloud to push; Condr Cloud forwards to Apple or Google. It is unrelated to the Relay, which carries Peer-to-peer bytes and stores nothing.

What peers do was checked first (`docs/research/push.md`). Paseo, Happy and Omnara push plain text through Expo; Superset has no mobile push. Of the relays with a published design, Web Push's VAPID and Bitwarden authenticate the caller with a short-lived token, while ntfy, Matrix's Sygnal and Home Assistant authenticate no caller and treat the push target itself as the capability. None signs the body or the path, all accept replay inside TLS, and all bound abuse with scopes and rate limits: ntfy and Bitwarden per IP, Home Assistant per recipient. Condr Cloud takes VAPID's self-signed short-lived token and Bitwarden's limits per IP.

## The service

Condr Cloud is a Cloudflare Worker on the free plan, in its own private repository, `condr-push`: with a handful of users, a machine and a database of its own would cost every month for nothing. A Worker reaches APNs directly, as Pushy, one app's replacement for OneSignal, and t3code's relay show. It answers at `https://push.condr.dev` and versions its API with an `API-Version: 1` header. This ADR covers only pushes.

It has three endpoints under `/api/push`, laid out as Condr's Java service template lays out a module, so a service built on it could take the same host over without a client change. The caller's Device id comes from its token, so no path names one:

- `PUT /api/push/device` registers the calling phone, replacing whatever was there: `platform` (`APNS` or `FCM`), `environment` (`SANDBOX` or `PRODUCTION`, APNs only), the push `token` (at most 200 bytes), and `servers`, at most 64 Device ids allowed to push to it. The Companion sends it on every launch, whenever the token changes and whenever a Device is added or removed.
- `DELETE /api/push/device` removes the calling phone's registration, sent when the Companion finds it has lost notification permission or holds no Device.
- `POST /api/push/send` names up to 16 recipient Device ids, a duplicate counted once, and carries one notification. It succeeds once the request is valid and never says which recipient was delivered, so a caller learns nothing about other people's phones.

A push reaches a recipient only when that phone registered and lists the caller among its `servers`; anything else is dropped silently.

## Authentication

Every request carries `Authorization: Condr <token>`. The token is a compact JWS that the caller signs with its own device key (ADR 0025): header `alg: EdDSA` with `kid` set to the caller's Device id, claims `aud` (the service's base URL), `iat`, and `exp` five minutes after `iat`. Condr Cloud issues nothing. It reads the public key straight out of `kid`, since a Device id is its public key, checks the signature, `aud` and the times with one minute of skew, and refuses an `exp` further out than five minutes. Neither the Server nor the phone gains a credential, and nobody logs in.

Since anyone can make a key, a valid token proves only that its caller holds one: it stops a caller from acting as another Device, not from becoming as many new Devices as it likes. The limits below, not the signature, bound that. A token is also a bearer credential for its five minutes, and one that leaks can be replayed with any body until it expires; it travels only over TLS and is never logged.

The Worker verifies the token with WebCrypto's Ed25519, importing the 32 bytes of `kid` as the key, and needs no library. On the Rust side `condr-client` builds the token by hand from what it already has (`ed25519-dalek`, `base64`, `serde_json`), and both the Server and `condr-mobile` call that one function.

Answers are HTTP 200 with the outcome in a `code` field, the envelope of that Java template: `200` on success, `400` for a malformed request, `401` for a bad or expired token, `413` past 16 KB and `429` past a rate limit. A caller reads `code`, not the HTTP status, which only a proxy in between changes.

## Storage and limits

D1 holds two tables: the phone registrations (Device id, platform, environment, token, last registration time) and their allowed Servers, which go with their registration. A token is deleted when APNs answers 410 or FCM answers `UNREGISTERED`, but only while the registration still holds the token that push went to and, for APNs, was last registered before the time Apple gives for the token going invalid, so a phone that registered in between keeps its new token. A Cron Trigger purges each day a registration not refreshed in 90 days. KV holds only the APNs provider token and the FCM access token, signed once and reused for 50 and 55 minutes: Apple refuses a provider token refreshed more often than about every 20 minutes, and a Worker keeps nothing in memory between requests. Registrations stay out of KV, whose free plan allows a thousand writes a day. Condr Cloud stores no notification and logs only the method, the path, the caller's Device id and the latency, never a body, token or payload.

Rate limits use Workers' Rate Limiting bindings. Before the token is checked, each source IP (`CF-Connecting-IP`, which a client cannot set) gets 10 registrations and 120 pushes a minute; keys are free, so these are what keep one machine from filling the tables with registrations, as ntfy and Bitwarden limit per IP. After it, each calling Server gets 60 pushes a minute, and each phone 10 registrations a minute. Cloudflare counts them per location and only approximately, which is enough to stop a flood. A Server that gets 429 drops that push.

The Worker signs the APNs provider token (ES256, the `.p8` key held as a Worker secret) and posts over HTTP/2 to the sandbox or production host the registration names. It retries only on the codes Apple marks retryable, and once after `ExpiredProviderToken`. FCM goes through its HTTP v1 API with a service account's token (RS256); that path is written but untested until Android exists (roadmap step 8). Delivery runs after the answer, through `waitUntil`.

## What a push says

A push is plain text. Its title is a localization key with the Agent's name as its argument, so the phone shows "Claude Code finished" in its own language; its body is `detail · Workspace · terminal title · Server`, the Server named by its `device_name` (ADR 0040), with empty parts left out. Two custom fields name the Server's Device id and the Pane id. Condr Cloud sets the Device id from `kid` rather than trusting the caller, and folds it with the Pane id into the collapse id, APNs' `apns-collapse-id` and FCM's `tag`, so each Pane keeps one notification, which a newer push replaces; `<Device id>:<Pane id>` fits APNs' 64 bytes. FCM carries the same fields.

APNs and FCM both refuse a payload past 4 KB, and a Workspace name has no length limit, so the Server cuts the body to 1 KB of UTF-8 at a character boundary, and Condr Cloud refuses with 400 a notification whose platform payload would still pass 4 KB. Each push expires an hour after Condr Cloud receives it (`apns-expiration`, FCM's `ttl`, whose default keeps a message four weeks): a phone that comes back later finds the Agent's current state in the app rather than a notification that may no longer be true.

Condr Cloud, Cloudflare, which runs it, Apple and Google therefore see the Agent's name and state, the Workspace, `detail`, the terminal title, the Server's name and both Device ids. They never see terminal contents. Encrypting the body was weighed and set aside: most services with end-to-end encryption send a push with no content and let the app fetch, which the Companion cannot do without a connection, and encrypting for the phone would bring a Notification Service Extension, keychain sharing between it and the app, a dedicated X25519 key and padding (`docs/research/push.md`), all for text people already see on a lock screen.

## The Server

The Server pushes on the same transitions as the desktop notification (`condr-gui/src/app/notifications.rs`): an Agent finished, failed, or needs its person, and a Blocked whose `detail` changes replaces the earlier push through the collapse id. It skips a recipient that is watching that Pane (ADR 0041) and holds back for nobody else. Input from another Client proves no one is there: an orchestrating Agent types through `condr pane` too, and a person may leave the moment they press Enter. So someone at the desktop gets the push as well. There is no `[server.push]` switch; a person who wants none turns notifications off on the phone.

The recipients are the authorized Clients that last said `push` in `Hello`, a new `bool` field and the first of ADR 0028's Client hints; an older Client sends none and gets no push. The Server records it per Client in `authorized-clients.json`, so it still knows after the phone disconnects.

The transition is found where the terminal monitor replaces a Pane's Agent snapshot, the one place that holds the previous state as well as the next; `agent_state_changed` sees only the Pane id. That thread holds the `RuntimeState` lock and has no tokio context, so it hands an owned push, recipients and text resolved, through a channel to one sender task on the Server's runtime. The task keeps only the latest push per Pane and posts with reqwest, already compiled in through iroh and declared directly at the same version, with a five-second timeout. After a timeout or a 5xx `code` it retries once, unless a newer push for that Pane is waiting, then `warn!`s; so a late Blocked never replaces the Done that followed it. Nothing is queued past that or persisted; a push that fails is lost. `CONDR_CLOUD_URL` replaces the base URL for development and tests.

## `authorized-clients.json`

`authorized-clients` becomes `authorized-clients.json`, a JSON array of `{key, name, paired_at, last_seen, push}`, `key` written as the Device id. The `push` flag needs a column, and a fifth space-separated field after a free-text name is fragile; this also ends ADR 0025's exception that the identity files keep hex. It is JSON rather than protobuf (ADR 0028) because it is a short list that people open to see who can connect, like `config.toml`, not state only the program reads. The store rules (lock, atomic write) are unchanged, and `device-key` and `pending-invite` keep their formats. When the new file is missing and the old one exists, whichever process opens the identity store first converts it under the store lock, and deletes the old file only once the new one is written; the Server and the offline `condr server clients` and `revoke` share that path. The conversion runs after ADR 0033's move out of the configuration directory, which keeps moving the file by its old name. Both the name and the conversion are marked `compat(0.1.13)`.

## The Companion

Right after its first successful pairing, the Companion asks for notification permission with the system prompt and no page of its own, and never asks again after a refusal; a Companion paired before it could ask asks once at its next launch. A Companion that was refused, or never registered, never contacts Condr Cloud. It says `push` in `Hello` when it has permission and its registration with Condr Cloud succeeded; the flag is one for the whole app, not per Device. When registering changes that answer, the Companion reconnects its open connections so each Server learns at once rather than on the next connection. The token for Condr Cloud comes from `condr-mobile`; the request goes out through `URLSession`.

Tapping a notification opens its Pane (ADR 0041); if the Pane is gone, the Companion stays on that Device's Workspace list. In the foreground it shows the system banner only for a Device it is not connected to, since a connected Device's change already shows in the app. It fetches the Server's authoritative state as it always does on returning to the foreground.

## Not chosen

A Spring Boot service on Condr's Java template, with Postgres: it was written first, in the private `condr-cloud` repository, and set aside because a machine for it costs every month while the free plan carries this load; its endpoints and answers are the ones above, so it can take `push.condr.dev` over if Condr Cloud grows into more than pushes. A stateless relay, where the phone hands each Server an opaque token and Condr Cloud stores nothing, as Paseo and Home Assistant do: it leaves no single place to stop a lost phone's pushes, and a Server would hold the push token. HPKE to the phone's key: see above. RFC 9421 HTTP message signatures, or a signature header of Condr's own: the libraries on both sides are immature, and no relay studied signs the request.

Not decided here, each with its trigger: a paid Workers plan or the Java service, when the free plan's 100,000 requests a day or 10 ms of CPU per request run short; App Attest and Play Integrity, proving a registration comes from the Companion on a real phone, when registrations grow past what the limits per IP explain; an admin backend, when there is something to administer; FCM on a real device, with Android; muting one Device, when people ask; an encrypted `detail`, if what pushes carry grows past what a lock screen shows.

What changes with the implementation, not before: `SECURITY.md` and the privacy page say Condr Cloud stores Device ids, push tokens, allowed Servers and the last registration time, and what it, Cloudflare, Apple and Google see; the website's security help and configuration reference and `docs/development-build.md` name `authorized-clients.json`.

Tests, in `condr-client`: a token the Rust side signs verifies in Condr Cloud's tests, which keep it as a fixture, and an expired, future-dated or wrong-audience token is refused. On the Server: the old `authorized-clients` converts to the JSON file and is deleted, whether the Server or `condr server clients` opens the store first and straight after ADR 0033's move from the configuration directory, and a missing `push` reads as false; `Hello.push` round-trips through protobuf and lands in the file; the push transitions, found on the monitor's own thread, match the desktop's, and a recipient watching the Pane is skipped; a body past 1 KB is cut at a character boundary; a push against a local stub at `CONDR_CLOUD_URL` carries the expected body and retries once, and a Blocked whose post times out behind a newer Done is not retried. In Condr Cloud, against local D1, KV and rate limits: each endpoint's `code`s and size limits, a notification whose payload would pass 4 KB among them; the APNs request's host, headers and payload; a push to a phone that does not list the caller is dropped, and a duplicate recipient gets one push; a registration replaces the last one with its Servers; a 410 for a token the phone has since replaced deletes nothing; the limit per IP answers 429 before any token is checked; the daily purge removes a stale registration; nothing in the logs contains a token or notification body.
