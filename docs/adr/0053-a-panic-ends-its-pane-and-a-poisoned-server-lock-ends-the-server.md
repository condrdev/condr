# A Panic Ends Its Pane, and a Poisoned Server Lock Ends the Server

Status: accepted 2026-10-29. Builds on ADR 0005, whose Snapshot a restarted Server comes back from, and ADR 0019, whose panic hook already logs every panic with its backtrace.

A panic in a Pane's reader thread while it held that terminal's lock poisoned the lock. The next Client to touch the Pane did so holding the Server state lock, panicked on `expect("terminal state lock poisoned")` and poisoned that lock too. From then on every `state.lock().expect(…)` panicked: the Server answered no Client, not even a new handshake, while the process, its PTYs and its Agents kept running where nobody could see them. One bug in one Pane took the whole Server down, slowly and without a word. `docs/research/lock-poisoning-and-panic-isolation.md` and `docs/research/ffi-callback-panics.md` trace it and survey what other projects do.

Mature Rust projects have no single practice, but they share one rule: catch a panic at the boundary of a unit of work that shares no mutable state and drop that unit, as tokio does with a task and tower-http with a request; when shared state may have been left half-changed, end the process and let it start again, as Zed, zellij, deno and uv do. Whether they use std's locks or parking_lot is a separate choice. In Condr a Pane's terminal is the unit's own state, and the Session behind the Server state lock is what every Pane and Client share, so the two halves of the rule map onto them.

A panic ends its Pane. Each of the Pane's own threads in `condr-core` (reader, writer, resizer and child watcher) runs inside `catch_unwind`. A panic sends `TerminalUpdate::Exited`, so the monitor ends the Pane as if its program had exited, and then goes on to end the thread. Code that runs only on those threads keeps its `expect`, since a panic there now ends only that Pane. Any other thread that takes a Pane's lock, whether a Client's, the monitor or a probe, takes a poisoned lock to mean the Pane has ended. A call that returns `io::Result` fails, a view is blank at the Pane's last size, a query answers nothing and a command does nothing. None of them reads what the lock guards, which may be half-changed. The size lock is the one exception: it only ever holds a whole `TerminalSize` copied in or out, so it is read even when poisoned. The global process-table cache is shared by every Pane but rebuilt from the OS, so a poisoned one is refreshed instead of trusted.

A poisoned Server lock ends the Server. The Server state, Snapshot worker, lifecycle, layout, Git activity and settings write locks guard what every Client shares and what the Snapshot persists. They are taken with `.or_abort()`, which logs where the poisoned lock was taken and calls `process::abort()`. Carrying on with `into_inner` would write a half-changed Session into the Snapshot. The GUI's reconnect starts a new local Server, which restores the Session's structure and resumes Agent conversations (ADR 0005). Programs in every Pane end and any turn in progress is lost. That is the cost, set against a Server that answered no one and had to be killed by hand anyway. A remote Server reached only over TCP or Peer-to-peer has no one to start it until Server autostart lands. The Snapshot worker also runs inside `catch_unwind` and aborts on a panic, since a worker that died would leave every later change unsaved without a word.

The locks stay std's `Mutex`, because its poison bit is what tells other threads that a Pane's terminal or the Session may be half-changed. parking_lot, already in the build through GPUI and gix, would mean rebuilding that bit by hand. `std::sync::nonpoison` is still nightly-only in Rust 1.99. A global `panic = "abort"` was declined: it would end every Agent for one Pane's bug, and Cargo cannot set it for the Server alone, so the GUI would abort too. It would also turn the `catch_unwind` that ADR 0051's callbacks need into dead code, for the same reason a panic hook that aborts would. This is worth revisiting once Edition 2027 settles std's default.

Left for later: a thread that holds no lock when it panics, such as a Pane's monitor or probe thread or the Git watcher, still ends silently. Whether each such thread ends its Pane or the Server is a decision of its own.

Tests: a panic on one of a Pane's threads while it holds the terminal lock ends the Pane with `Exited`. The Pane then answers input with an error, a view with a blank grid of its size and a copy or its text with nothing, and still closes. `or_abort` ends the process, so it has no test of its own.
